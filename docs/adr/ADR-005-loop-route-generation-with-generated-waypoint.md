# ADR-005: 散歩ルートの周回生成に「復路用経由点の自動生成」を採用する

## 日付

2026-08-23（初版。SS-33）

## コンテキスト

sanposcape の中核体験は「目的地まで行き、**往路とは別の経路で戻ってくる**周回（サークル状）の散歩」である。
しかし SS-16 では、選択したスポットまでの**片道ルート**を `POST /explore/routes/walking` で取得して提示し、
往復は「同じ道を戻る」前提（所要時間・距離は片道×2）の近似で扱っていた。SS-15 の「往復◯分」指定も同じ前提である。

起票当初（2026-08-01）この周回化は「MVP のブロッカーではない体験品質の向上」と位置づけていたが、
**2026-08-22 に「片道×2 の近似のままでは MVP として成立しない」というユーザー判断により撤回**され、
MVP 必須タスクへ格上げされた。

技術的な制約は次のとおり。

- [ADR-001](./ADR-001-map-poi-google-maps-platform.md) により、経路は Google Maps Platform の Routes API を
  **backend 経由で**利用する。地図描画は mobile の native SDK が担う。
- Routes API の `computeRoutes` は **「出発地＝到着地の周回ルート」を直接生成する機能を持たない**。
  周回にするには経由点を自分で与える必要がある。
- `computeAlternativeRoutes`（最大3本）は **`intermediates` と併用できない**。
- `intermediates` は最大25件。**`via: true` の経由点は `legs` を増やさず通過**し、
  通常の stopover は `legs` を分割する。
- `intermediates` 10件以下・`TRAFFIC_AWARE` 等を使わなければ Essentials SKU に留まる。
- 外部 API は従量課金でレート制限もあるため、1ルート提示あたりの呼び出し回数を増やしたくない。
- mobile はルートを TanStack Query で `staleTime = 1時間` キャッシュしており、
  **同一入力に対して同一の周回が返る（決定的である）こと**を前提にしている
  （[mobile ADR-008](../../packages/mobile/adr/ADR-008-active-walk-state-and-route-cache.md)）。

## 決定

**復路用の経由点を backend が幾何的に自動生成し、`computeRoutes` の1リクエストで周回を取得する**（下記「選択肢1」）。

```
computeRoutes(origin = O(現在地), destination = O,
              intermediates = [ D(目的地, stopover), V(復路用の経由点, via = true) ],
              travelMode = WALK)
→ routes[0].legs = [ O→D (往路), D→V→O (復路) ]   ※ via は leg を増やさない
```

`via` が leg を増やさない性質を利用することで、**往路と復路が API のレスポンス上で明確に2つの leg に分かれる**。
これにより mobile 側の描き分け・往路/復路判定が素直に実装できる。

### 経由点 V の生成規則

```
V = offset( midpoint(O, D), bearing(O→D) ± 90°, α × haversine(O, D) )      α = 0.25
```

1. 1回目は **右（+90°）**、妥当性チェックに落ちたら 2回目は **左（−90°）** を試す。
2. `haversine(O, D)` が `MIN_LOOP_BASE_DISTANCE_METERS`（50m）未満なら経由点を作らない。
3. **決定的な幾何規則のみを使う。候補分布・ハッシュ・乱数は使わない。**
   - 「直前の探索候補が多く分布している側へ寄せる」という素案は却下した。ルート要求には候補情報が含まれず、
     provider の places キャッシュ（TTL 300s）を覗く実装にすると**キャッシュの有無で同じ入力から別の周回が返る**。
     mobile の `staleTime = 1時間` 前提（同一入力で決定的であること）に違反する。
   - `hash(str)` も `PYTHONHASHSEED` によりプロセスごとに変わるため使えない。
4. 「同じ側で α を縮める」ではなく「反対側を試す」を再試行の既定にした。1回目が落ちる典型要因は
   **水域・線路・大規模施設で道が無い**ことであり、その場合 α を縮めても同じ障害物に当たるため。

### 生成した周回の妥当性チェック

3指標をまとめて評価し、**どれか1つでも外れたら不採用**（＝再試行、または「同じ道を戻る」へフォールバック）。

| 指標 | しきい値 | 意味 |
| --- | --- | --- |
| `MAX_RETURN_TO_OUTBOUND_RATIO` | 1.8 | 復路 leg の時間 ÷ 往路 leg の時間 |
| `MAX_TOTAL_TO_STRAIGHT_RATIO` | 1.4 | 周回の総時間 ÷ (往路 leg × 2) |
| `MAX_PATH_OVERLAP_RATIO` | 0.6 | 往路/復路の折れ線の重複率（10m 間隔に補間し 20m グリッドへスナップした Jaccard 係数） |

**重複率を指標に加えた理由**: 経由点が O→D の直線近傍にスナップされると「復路がほぼ往路と同じ道」になるが、
この状態は**時間比の指標では検出できない**（むしろ理想的な比率に見える）。
本 ADR のゴールは「往路と復路が**異なる**」ことなので、重複率は**周回の成立そのものを測る唯一の指標**である。

**妥当性の基準を「往路 leg 由来の相対値」にした理由**: 素案は「周回全体 ≤ 指定往復時間 × 1.2」だったが、
`WalkingRouteRequest` には往復時間の入力が存在しない（`/explore/places` にしかない）。
リクエストに項目を足さず、往路 leg からの相対値で判定する。

### フォールバック（周回を作れなかった場合）

**周回が作れなくてもエラーにせず、200 で「同じ道を戻る」応答を返す**。
ルート取得失敗として扱うと「散歩を始める」が押せなくなり、MVP の主導線が止まるため。

**フォールバックのために追加の Google 呼び出しはしない。** 不採用になった周回応答の `legs[0]` が
そのまま O→D の片道ルートなので、それを再利用して復路を逆順の折れ線として組み立て、
`return_is_same_path: true` を立てる。

例外・「HTTP 200 だが `routes` が空」・`legs` 不足で**1件も使える応答が得られなかった場合のみ**、
`intermediates` を付けない素の片道呼び出しに落とす（この呼び出しは直前の `/explore/places` が
同じ (origin, destination) でキャッシュに載せていることが多く、実際には Google に出ないことが多い）。

### 候補絞り込み（`POST /explore/places`）との整合

候補ごとに実際の周回を引くと Routes 呼び出しのレイテンシと SKU が上がり、探索のデッドラインを割る。
そのため候補絞り込みは**引き続き片道1回の呼び出し**とし、`片道 × 2 × LOOP_FACTOR`（既定 1.15）で
周回相当へ補正する。フィールド名・型は変更せず、`round_trip_*` の**値だけ**が補正後になる。

### kill switch

`GOOGLE_MAPS_LOOP_ROUTE_ENABLED`（既定 `true`）を設けた。`false` にすると周回の経由点生成を行わず、
常にフォールバック（同じ道を戻る）を返す。周回が実地で破綻した場合や Google の課金が跳ねた場合に
**再デプロイなしで SS-32 相当の挙動へ戻せる**（`AUTH_MODE` / `MAPS_MODE` と同じ fail-safe の作法）。
mobile は `return_is_same_path: true` を扱えるため、UI は無改修で degrade する。

## 検討した選択肢

### 選択肢1: 復路用の経由点を自動生成し、1リクエストで周回を取得（採用）

- **概要**: `origin = destination = 現在地`、`intermediates = [目的地(stopover), 生成した経由点(via)]` で
  `computeRoutes` を1回呼び、返る2つの leg を往路/復路として扱う。
- **メリット**: 呼び出しが1回（再試行込みで最大2回）で済み、Essentials SKU・現行レート制限のまま収まる。
  往路/復路が API の `legs` として明示的に分かれて返るため、mobile の描き分け・現在位置判定が素直に実装できる。
  品質が出ない場合は「同じ道を戻る」へフォールバックできるため、体験が壊れない。
- **デメリット**: 経由点が水域・私有地・道の無い場所に落ちると Routes がスナップして不自然な迂回になりうる。
  品質が経由点生成ロジックに依存し、**決定的な品質保証が無い**（実測分布に基づく確率的な保証にとどまる）。

### 選択肢2: 往路/復路を2回呼び、復路は代替ルートから重複最小のものを選ぶ

- **概要**: `O→D` と `D→O` を `computeAlternativeRoutes: true` で2回呼び、
  復路候補のポリラインを 20m グリッドにスナップして往路との重複率が最小のものを採用する。
- **メリット**: 経由点を捏造しないため、返る経路は必ず Google が引いた実在の歩行経路であり、
  不自然な迂回が原理的に起きない。
- **デメリット**: API 呼び出しが確実に2倍。復路が「必ず往路と異なる」保証が無い
  （代替が返らなければ復路＝往路のまま）。重複率の計算ロジックを自前で持つ必要がある。
- **当初の想定が実測で誤りと判明した点**: 起票時は「短距離の徒歩では代替ルートがほとんど返らない」と想定して
  確実性を低く評価していたが、**実測では WALK でも中央値3本返り、2本以上が返る割合は 89%** だった。
  よって選択肢2 は現実的な選択肢である。今回は選択肢1 が判定基準を満たしたため採用しなかったが、
  **選択肢1 が実運用で破綻した場合の次善策として有効**である。

### 選択肢3: 経由点候補を複数試して最良を選ぶ

- **概要**: 選択肢1 の経由点を N 個（例: ±90° × α ∈ {0.4, 0.6, 0.8} の6通り）生成し、
  それぞれ `computeRoutes` を投げて最良を選ぶ。
- **メリット**: 品質は最も高くできる。
- **デメリット**: **API 呼び出しが6倍**。`/explore/*` の共有レート制限（認証 30req/60秒）と
  デッドラインの全面的な再設計が必要で、レイテンシも増える。MVP のコストに見合わない。
- 選択肢1 の品質が実測で足りなかった場合の次善策として保留する。

### 選択肢4: 復路にも探索候補のスポットを置く「2スポット周回」

- **概要**: `O → D1(stopover) → D2(stopover) → O` として、D2 を既存の `/explore/places` 候補から
  「O から見た方位が D1 と最も離れており、合計時間が予算内」のものとして選ぶ（またはユーザーが2つ選ぶ）。
- **メリット**: 経由点が実在の POI なので不自然な迂回が起きない。呼び出しは1回。
  「2箇所寄って帰る」という体験そのものがプロダクトの価値になりうる。
- **デメリット**: **UX の仕様変更を伴う**。スポット選択が実質2つになり、`WalkDestination` 型・ストア・
  散歩記録の保存 API まで波及する。SS-33 のゴール（目的地を選ぶと現在地に戻る周回が提示される）よりスコープが広い。
- ただし**選択肢1 の経由点を「幾何的に生成した点」から「実在の POI」へ置き換える補強**としては部分採用の余地がある。

### 選択肢5: 別のルーティングエンジンで周回を生成する

- **概要**: GraphHopper 等、round trip 生成アルゴリズムを本来機能として備えるエンジンを使う。
- **メリット**: 周回生成が標準機能として存在する。Google の従量課金から離れられる。
- **デメリット**: [ADR-001](./ADR-001-map-poi-google-maps-platform.md) で採用した
  「Google Maps Platform 単一ベンダー」の決定を覆すことになる。自前ホスティングまたは別ベンダー契約、
  POI と経路のベンダー分離、地図描画との整合が必要で MVP には重すぎる。
- 将来コスト問題が顕在化した時の選択肢として記録する。

## 決定理由

### 実装前に実 API でスパイクを行い、実測で方式と定数を決めた

経由点方式の品質は机上では判定できないため、**実装に着手する前に実 Google Routes API へ 108 試行**
（出発地3点 × 目的地3件 × α 6値 × 左右2方向）を投げて実測した。

- 出発地: 密な市街地（東京駅）/ 川と線路が近い（浅草）/ 郊外の疎な道（若葉台）
- 目的地: 各出発地から直線距離で約 600m / 1.2km / 2km の実在スポット
- 指標:
  - **重複率** = 往路/復路の折れ線を 10m 間隔に補間し 20m グリッドへスナップした Jaccard 係数
  - **迂回率** = 周回総時間 ÷ (往路 leg × 2)
  - **ret/out** = 復路 leg 時間 ÷ 往路 leg 時間

| combo | 重複率 中央値 / p75 | 迂回率 中央値 / 最大 | ret/out ≤ 1.8 の割合 | 判定 |
| --- | --- | --- | --- | --- |
| α=0.15 right | 0.214 / 0.379 | 1.085 / 1.215 | 100% | 通過 |
| α=0.15 left | 0.348 / 0.660 | 1.046 / 1.273 | 100% | 重複率 p75 で不可 |
| **α=0.25 right** | **0.147 / 0.270** | **1.149 / 1.314** | **100%** | **通過** |
| **α=0.25 left** | **0.203 / 0.239** | **1.078 / 1.397** | **100%** | **通過** |
| α=0.35 right | 0.145 / 0.230 | 1.237 / 1.611 | 89% | 不可 |
| α=0.4 left | 0.092 / 0.117 | 1.209 / 1.537 | 89% | 不可 |
| α=0.6 right | 0.100 / 0.130 | 1.395 / 1.611 | 56% | 不可 |
| α=0.8 right | 0.072 / 0.112 | 1.569 / 1.948 | 11% | 不可 |

### ★ 当初の想定が実測で覆った（この ADR で最も残す価値のある知見）

起票時は「**復路が往路と同じ道になってしまう（＝重複率）が最大のリスク**」と考え、
経由点を**大きくずらすほど良い**と想定して α を 0.5〜0.7 と見積もっていた。

実測の結論は**逆**だった。

- **重複率はどの設定でも十分低く**、想定した最大のリスクはほとんど顕在化しなかった。
- **実際の拘束条件は迂回率と ret/out 比**である。α を上げるほど周回が伸びすぎ、
  α=0.8 では迂回率の中央値が 1.56 に達する。これは「**往復30分のつもりが47分**」に相当する体験劣化である。
- つまり **α は小さいほど良い**。ただし α=0.15 まで下げると今度は重複率が跳ねる（left で p75 0.660）ため、
  **0.25 が最適点**になる。

**この逆転を知らずに α を大きめの既定値に設定すると、周回は「成立しているように見えて」体験が静かに劣化する。**
`packages/backend/src/sanposcape/maps/geometry.py` の定数コメントにも実測値を転記してあるが、
判断の経緯としてここに残す。

### しきい値は「最悪ケースをぎりぎり通す値」として確定した

最悪ケースは**郊外 × 短距離**（若葉台〜鶴川 486m: 迂回率 1.397 / ret 1.796 / 重複 0.568）だった。
道の選択肢が少ない条件では周回の余地が小さいという直感どおりの傾向である。
3つのしきい値（1.4 / 1.8 / 0.6）はいずれもこのケースを**ぎりぎり通す**値になっており、
実運用でこの近傍のケースが不採用になって再試行に回ることは想定内とする。

### `LOOP_FACTOR` は実測中央値ではなく、あえて上の値を採った

| 統計量 | 実測（α=0.25・18試行の「周回総時間 ÷ 単独片道×2」） |
| --- | --- |
| 中央値 | 1.099 |
| 平均 | 1.134 |
| p75 | 1.168 |
| p90 | 1.191 |
| 最大 | 1.400 |

既定値は**中央値(1.10)ではなく 1.15** とした。この係数は `/explore/places` の候補絞り込みに使うため、
**誤差が非対称**である。

- **過小評価**は「往復30分で選んだのに実際は35分だった」という**体験劣化に直結する**
- **過大評価**は「候補が少し減る」だけで済む

中央値では約半数が過小評価になるため、p75(1.168) をわずかに下回る 1.15 を採った。
env 設定（`GOOGLE_MAPS_LOOP_DURATION_FACTOR`, `ge=1.0, le=2.0`）なので実運用の観測で調整できる。

### その他の実測（設計判断の裏付け）

- **応答の健全性**: `legs` が2件返らなかった試行、および「HTTP 200 だが `routes` が空」は
  108 試行中いずれも **0件**。ただし**目的地が公道の無い敷地内（皇居の重心）の場合に空応答は実在する**ことを
  別途確認しており、フォールバック経路の実装は必要である。
- **レイテンシ**: 周回1リクエストで p50 約 120ms / p95 約 230ms。判定基準（p95 ≤ 6s）に対し桁で余裕がある。
  `GOOGLE_MAPS_ROUTE_DEADLINE_SECONDS = 12.0` は十分。
- **ペイロード**: 周回1件あたりの折れ線は中央値 126点 / 最大 200点。
  mobile へ返す JSON は概ね 11〜18KB（当初見積もりの 60KB は過大だった）。
  `path`（周回全体）と `legs[].path` の**両方**を実体で返す判断はコスト的に問題ない。

### 確定した定数の一覧

| 定数 | 値 | 置き場所 | 根拠 |
| --- | --- | --- | --- |
| `WAYPOINT_OFFSET_RATIO`（α） | 0.25 | `maps/geometry.py` | 上表。左右とも全基準を通過する最適点 |
| `MAX_RETURN_TO_OUTBOUND_RATIO` | 1.8 | `maps/geometry.py` | α=0.25 の最大実測 1.796 |
| `MAX_TOTAL_TO_STRAIGHT_RATIO` | 1.4 | `maps/geometry.py` | α=0.25 の最大実測 1.397 |
| `MAX_PATH_OVERLAP_RATIO` | 0.6 | `maps/geometry.py` | α=0.25 の最大実測 0.568 |
| `MIN_LOOP_BASE_DISTANCE_METERS` | 50.0 | `maps/geometry.py` | O≒D では経由点を作らない |
| `GOOGLE_MAPS_LOOP_DURATION_FACTOR` | 1.15 | env（`config.py`） | 上記「誤差の非対称性」 |
| `GOOGLE_MAPS_ROUTE_DEADLINE_SECONDS` | 12.0 | env（`config.py`） | 実測 p95 約 230ms に対し十分 |
| `GOOGLE_MAPS_LOOP_ROUTE_ENABLED` | true | env（`config.py`） | kill switch |

**α としきい値は env に出さない。** 値の意味を理解せずに環境変数で動かすと周回の品質が静かに壊れ、
テストで固定している値もすり抜けるため。`LOOP_FACTOR` だけは「実運用の観測で調整したくなる商品パラメータ」として env に出す。

## 影響

### ポジティブな影響

- 本アプリの中核体験である「往路と復路が異なる散歩」が成立し、MVP の要件を満たせるようになった。
- 所要時間・距離が周回全体の**実値**になり、片道×2 の近似による過小評価が解消された。
- 往路/復路が API の `legs` として分かれて返るため、mobile 側で描き分け（往路＝実線 / 復路＝破線）と
  「現在どちらを歩いているか」の判定が素直に実装できた。
- 呼び出し回数・SKU・レート制限のいずれも据え置きで収まった（Essentials SKU、`/explore/*` 共有 30req/60秒）。
- kill switch により、周回が実地で破綻しても再デプロイなしで従来挙動へ戻せる。

### ネガティブな影響・トレードオフ

- **経由点の品質が幾何規則に依存し、決定的な品質保証は無い。** 実測分布に基づく確率的な保証にとどまる。
  郊外×短距離では周回の余地が小さく、しきい値ぎりぎりのケースが再試行に回る。
- Google 呼び出しが 1ルート提示あたり**最大2回**（両経由点とも使える応答が得られなかった場合のみ最大3回）に増えた。
- `/explore/places` の `round_trip_*` が `LOOP_FACTOR` 補正後になるため、**同じ時間指定でも候補が減る**。
- 候補一覧の値（片道×2×係数の**目安**）と選択後の値（周回の**実値**）が異なる API 由来の数値になる。
  前者は一覧の一貫性、後者は正確性を優先した結果で、UI 側は「目安」の語彙で区別している。
- 周回のレスポンスは `path`（全体）と `legs[].path` の両方を実体で持つため、点オブジェクトが約2倍になる
  （実測 11〜18KB。`legs` が壊れていても線が消えない degrade 経路を残す価値を優先した）。

### 移行・対応が必要な事項

- `POST /explore/routes/walking` の API 契約を変更した（破壊的変更。mobile と同時リリース）。
  詳細は [ADR-001](./ADR-001-map-poi-google-maps-platform.md) の SS-33 追補を参照。
- α・しきい値を変更する場合は、**本 ADR の実測表を更新できるだけの再測定**を伴わせること。
  数値だけを勘で動かすと、上記「当初の想定が実測で覆った」と同じ罠を踏む。
- 選択肢1 が実運用で破綻した場合は、**選択肢2（代替ルート選択）→ 選択肢3（複数経由点）→ 選択肢4（2スポット周回）**
  の順で再検討する。選択肢2 は「WALK でも代替が返る」ことが実測で確認済みである。
- 往路で周回を引き直した場合、mobile の往路/復路判定が古いルートの leg を参照し続ける
  既知の課題がある（SS-63）。目的地到達ラッチが上書きするため機能破綻はしない。
  当初は「ルート逸脱による自動再計算」で起きうる問題だったが、SS-33 の動作確認で**自動再計算を廃止**し
  手動ボタンのみにしたため、**ユーザーが往路で明示的に再計算を押したときだけ**に狭まった
  （mobile ADR-008 決定7 の SS-33 動作確認 追補）。
