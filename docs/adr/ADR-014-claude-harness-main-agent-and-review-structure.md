# ADR-014: Claude Code のハーネスは、メインが計画・実装し、レビューは観点で分けたレビュアーに任せる

## 日付

2026-10-12（SS-194 の方針決定、SS-202・SS-203 で実装）

## コンテキスト

Claude Code 側の課題の進め方（`task-workflow`）は、「上位モデルが極めて詳細なプランを書き、下位モデルがそれに沿って実装する」前提で作られていた。
task-workflow → 領域別 workflow（backend / mobile / frontend）→ `*-planner` → `*-developer` → 領域ごとに3種のレビュアー（security / architecture / code-quality）と `doc-maintainer`、という多段構成である。
Opus 5.5 / Sonnet 5.5 ではこの細かな指示と受け渡しが効果に見合わず、次の問題が出ていた。

- **正本の書き写しがずれる**: docs・ADR の規約を agent のプロンプトに書き写していたため古くなり、agent-memory が毎回それを打ち消していた（SS-193 で修正）
- **手順の細かな指示が多すぎる**: 今のモデルが既定で行う汎用的な心得が多い。プランにシグネチャまで求めたため、実装中にコードを読んで分かった事実とぶつかって手戻りになった
- **受け渡しが多く、毎回ゼロから読み直す**: 2領域にまたがる課題では planner と developer の間で5回受け渡し、それぞれが docs と ADR を読み直した。実装中に分かった事実（例: SS-175 の、同じ地図 ID を送る PATCH と地図削除のデッドロック）は planner に戻らなかった
- **レビュアーが多い**: 2領域にまたがる課題で最大8体が走り、指摘が重複した。一方で、API 契約のずれや mobile 側が認証の前提を崩すといった**層の境目の問題は、どのレビュアーの担当にもならなかった**

Codex 側は既に「メインが計画から実装まで担い、独立レビュアーは1体」の構成に移行している（[ADR-010](./ADR-010-codex-astra-harness-and-incremental-import.md)）。

## 決定

1. **計画・実装・検証はメインのエージェントが直接行う。** 領域別 workflow、planner、developer への委譲をやめる。プランは `tmp/<issue-id>/plan.md` に短く書く（方針・影響範囲・更新する文書・完了条件・判断の記録）。シグネチャまでは書かない。
2. **領域の規約は正本にだけ置く。** 各 package の `AGENTS.md` から辿る docs・ADR が正本で、skill・agent には「X を読む」とだけ書く。
3. **サブエージェントは3つの用途に絞る。** 広い範囲の調査（Explore を並列で）、独立したレビュー、意図が明確で量の多い機械的な変更（Sonnet に短いテンプレートで任せる。`task-workflow/references/delegation.md`）。
4. **レビューは層ではなく観点で分ける**（`change-review` skill）。
   - 基本のレビュアー `change-reviewer`（毎回1体、メインと同じモデル）: 変更全体・プラン・関連 ADR を層をまたいで見る
   - `doc-maintainer`（毎回、change-reviewer と並列、Sonnet）: ADR 以外の文書の乖離
   - 観点別のレビュアー（条件付き）: 今は `security-reviewer` だけ。認証・認可、入力の扱い、外部への公開範囲、秘密情報に触れる差分で起動し、変更全体を見せる
   - 早めの打ち切りを防ぐため、観点ごとに「何を確認したか／問題なしならその根拠」を必ず出力させる。指摘は「本当に問題が起きるか」で反証してから返させる
5. **文書の乖離は4段で防ぐ。** (1) プランに「更新する文書」を書いて予防する。(2) 独立した doc-maintainer を毎回起動する。(3) docs-lint の機械検査（SS-205）。(4) knowledge-review の定期棚卸しで、ワークフロー外の変更による乖離を拾う（SS-204）。
6. **agent-memory は agent 名ではなく領域で分ける**（SS-202）。`backend/`・`mobile/`・`common/`。メインは subagent の `memory: project` による自動読込を使えないので、各 `AGENTS.md` の指示で `MEMORY.md` を読む。レビューで繰り返し使える確認項目は、メモリではなく `change-review/references/` に置く。
7. **Web フロントエンド（`packages/lp`）もメインが直接行う**（ユーザー決定）。旧 frontend-* の agent / skill は削除し、中身を参照資料（`task-workflow/references/web-frontend.md`、`change-review/references/web-frontend.md`）として残す。React 前提で lp（Astro）と合わない部分は今回は直さず、資料の冒頭で正本（`packages/lp/AGENTS.md`、ADR-012）を優先すると明示する。
8. **残すもの**: 承認を待たずに推奨案で進め、判断と理由を `handover-notes.md` に記録して PR の申し送り事項に載せる方針。PR 作成 → task-status-sync → knowledge-harvest の順序。同じ失敗を3回繰り返したら中断して報告する、という止まる条件。

## 検討した選択肢

### 選択肢1: 多段構成を維持し、各 agent のプロンプトを直す

- **概要**: planner / developer / 領域別レビュアーを残し、書き写しのずれだけを直す
- **メリット**: 変更が小さい
- **デメリット**: 受け渡しと読み直しの費用、層の境目が担当外になる問題は残る。書き写しはまたずれる

### 選択肢2: レビュアーを反証型の1体だけにする（Codex 側と同じ）

- **概要**: 観点別のレビュアーも doc-maintainer も置かない
- **メリット**: 最も安い。層の境目も1体で見られる
- **デメリット**: 1体に多くの観点を持たせると、目立つ指摘を見つけた時点で残りの観点を流しがちになる。文書の乖離は、毎回それなりの箇所で起きており（2026-08 以降、レビュー指摘や実装に合わせて文書を直したコミットが82件）、最後の観点に回されて取りこぼされやすい

### 選択肢3: 基本の1体 + 毎回の doc-maintainer + 条件付きの観点別レビュアー（採用）

- **概要**: 決定4のとおり
- **メリット**: 層の境目は基本の1体が見る。security と文書は独立した文脈で最後まで見られる。観点別は条件付きなので、通常は2体、security に触れる変更でも3体に収まる
- **デメリット**: 選択肢2より費用がかかる。doc-maintainer は意図を知らないので、わざと変えた点を指摘しがち（プランと申し送りを渡して防ぐ）

### 選択肢4: 文書の乖離は定期の棚卸しだけで見る

- **概要**: doc-maintainer を毎回は起動せず、週次などで main 全体を見る
- **メリット**: 1回の PR あたりの費用が下がる
- **デメリット**: 乖離した文書が main に残っている間、エージェントがそれを読んで誤った作業をする（SS-193 と同じ原因）。定期の棚卸しは補完にとどめる

## 決定理由

- 今のモデルは、コードと正本を読めば汎用的な心得なしで十分な品質の計画と実装ができる。受け渡しを減らすほど、実装中に分かった事実がそのまま計画に反映される。
- レビューの見落としは「担当の切れ目」と「観点の打ち切り」から生じる。前者は層で分けないことで、後者は観点ごとの出力の強制と、文書・security の独立した文脈で防ぐ。
- 正本を一か所にすることで、書き写しのずれ（SS-193）が構造的に起きなくなる。

## 影響

### ポジティブな影響

- 2領域にまたがる課題でも、計画から実装まで1つの文脈で進む
- レビュアーは通常2体（最大3体）になり、指摘の重複が減る
- 規約の更新は正本の1か所で済む

### ネガティブな影響・トレードオフ

- メインの文脈が長くなる。広い調査は Explore に任せて結論だけ受け取ることで抑える
- 参照資料（`change-review/references/`）は、レビューで見つかった確認項目を収穫のたびに足していく必要がある
- 旧 frontend-* の資料は React 前提のままで、lp には合わない部分がある

### 移行・対応が必要な事項

- 削除した agent / skill（backend / mobile / frontend の workflow、planner・developer 6体、reviewer 9体）は Git 履歴から復元できる（SS-203 の直前のコミット）
- task-workflow の終了手順（アクセスログのコミット）の簡素化は SS-204 で行う
- docs-lint の機械検査は SS-205 で行う
- Codex 側への取り込みは SS-206 で `import-claude-skill` を通して確認する。Codex は既に同様の構成のため、多くは対応不要の見込み
