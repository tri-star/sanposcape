# ADR-010: Astra向けハーネスとClaude定義の差分取り込み

## 現在有効な決定（要約）

> 最終更新: 2026-10-14（SS-206）。本節は本文（追補を含む）を要約したもので、一次記録は本文。
> 本文と食い違う場合は本節の誤りとして本節を直す。

### 決定

- **計画・実装・課題操作はメインが担当する。** 領域別の規約は共有の正本から読み、skillへ書き写さない。（本文: 決定1・2、SS-206追補）
- **reviewerの型は1種類、実行文脈は観点別に分ける。** change・docsを毎回、securityを条件付きで新しいインスタンスとして逐次実行し、全観点の確認根拠を必須にする。（本文: SS-206追補1）
- **mainモデルは実行環境の選択に従う。** 独立reviewerの定義はgpt-6-astra/highとし、ユーザー設定は取り込みで上書きしない。（本文: SS-206追補2）
- **Claudeとの差分は比較・適応・検証・基準更新で管理する。** 多対多の対応とadapt/retain/omit/deferを記録し、削除や双方変更を自動上書きしない。（本文: 決定3〜6）
- **Web開発は実在するAstro LPへ接続する。** mobileのPR確認は既存skillの参照へ統合し、端末確認と外部投稿の権限・結果を区別する。（本文: SS-206追補3・4）
- **文書検査と知識整理を組み合わせる。** Codex skillも参照検査の対象とし、PR後にレビュー観点を整理して共有ログを移す。ClaudeのフックをCodexの自動機能とは扱わない。（本文: SS-206追補5・6）
- **計画とsecurityレビューでデータ取扱い台帳との整合を確認する。** 計画に影響の有無と理由を書き、台帳の対象パスや利用者データの扱いを変える差分ではsecurityの6番目の観点で実物を照合する。（本文: SS-206追補・PR #165の追加取り込み）

### 変更・撤回された決定

- メインのAstra固定 → 実行環境の選択に従う（SS-206追補2）。
- 1体で全観点を確認 → 1種類のreviewer型を観点別の独立文脈で逐次起動（SS-206追補1）。

## コンテキスト

Claude用のskill/agentを1:1で移植した構成では、計画・実装・課題管理・複数レビューを細かく委譲し、重複した読込や固定の確認停止が発生する。読み取り専用の計画担当へのファイル保存指示や、Claude固有のメモリ自動読込の前提も残っていた。

Claude Code側で今後も主に定義を管理する。Codex側の最適化を残しながら、その後のClaude側の改善を取り込める必要がある。

## 決定

1. メインのAstraが計画・実装・課題操作を行い、独立レビューを1種類のSubagentに統合する。領域別の専門知識はskillと必要時に読む参照へ配置する。（SS-206追補: メインのモデルは実行環境に従う。reviewer型は1種類のまま、観点別の独立文脈へ分ける。下記追補1・2参照）
2. 規約・ADR・アプリ用scriptsは共有の正本。課題操作はprovider共通の契約とPlane用参照へ分ける。
3. importerは機械的変換器から、比較・適応・検証・基準更新の支援へ変更する。適応の意味判断はCodexが行う。
4. 前回処理済みのClaude内容とCodex内容をGit管理のsnapshotに保存する。git SHAは来歴として併記するが、未コミットの変更も扱うため内容を正本とする。
5. sourceとtargetの対応は多対多。adapt/retain/omit/deferと理由を記録し、未処理sourceの基準は進めない。削除・改名・双方変更は自動上書きしない。
6. 基準更新前に変更を検証する。sourceまたは基準が計画後に変わった場合は古いplanを拒否する。設定とsnapshotは同じ変更単位でコミットする。

## 検討した選択肢

- 1:1の同期継続: 単純だがCodex向けの調整を失い、委譲の構造も引き継いでしまう。
- git SHAのみ: 小さいがdirty worktreeの内容を表せず、履歴の到達性にも依存する。
- source snapshotだけ: source差分は分かるが、Codexで独自修正された箇所を判断しづらい。
- 双方の内容snapshotと判断記録: データ量は増えるが、部分取り込み・独自調整・未コミット変更を表現できるため採用。

## 影響

定義の総数を削ること自体を目的にせず、繰り返しの委譲と矛盾する指示を減らす。独立レビューの費用は残る。snapshotは比較データとしてのみ読み、コンテキストへ丸ごと展開しない。

意味の適応は決定論的ではなく、validatorやテストだけでは品質を保証できない。レビューと具体的なタスクで確認する。実測前にコスト削減率を約束しない。旧agentの復元はGit履歴で可能。

## SS-206追補: 観点別レビューと共有手順への適応

1. **独立レビューは観点別の新しい文脈で行う。** 通常はchangeとdocs、認証/認可・入力・公開範囲・秘密・依存・CI/デプロイに触れる場合はsecurityも行う。型は既存のadversarial_reviewerだけとし、同時実行1体の設定に合わせて逐次起動する。各focusの全観点で確認場所と根拠/対象外理由を必須にする。前のreviewerの結論は渡さない。修正後はそのfocusの同じreviewerへ論点を絞って再確認する。
2. **mainモデルは実行環境が選ぶ。** ユーザーの既存config変更を取り込みで上書き・コミット・acceptしない。reviewerは既存のgpt-6-astra/highの定義を維持する。型の登録・実行は実際の環境で確認する。
3. **短い計画と正本への導線を維持する。** 計画は方針・影響範囲・更新する文書・完了条件・判断を持ち、シグネチャを固定しない。Webはpackages/lp/AGENTS.mdとADR-012へ接続し、未作成のReact構成を既存扱いしない。
4. **mobileのPR確認を既存skillの参照へ統合する。** 画面変更の判定・対象HEADの確認・端末操作・画像確認・依頼範囲内のPR添付を分ける。添付非対応を理由に端末確認を省略せず、未添付や未確認の記録を保持する。Claude固有のsandbox解除指定を移植しない。
5. **Codex skillのMarkdownも文書参照検査の対象にする。** 生成先を前提にしたlaunch-projectの雛形は除外し、新しい違反をbaselineへ追加しない。機械検査が扱わない書き方と意味の乖離はfocus=docsが見る。
6. **知識整理は既存の完了時参照に統合する。** 繰り返し使えるレビュー観点はCodex側の参照へ、メモリの変更は実行環境の許可範囲へ限定する。共有のflush-memory-access-log.shで手元の実ログを移し、確認したファイルだけをstageする。Claudeのフックによる計測をCodexの自動機能とは説明しない。権限で失敗したら、承認済み範囲でSandbox外実行を検討し、難しければ実行用スクリプトを用意して報告する。

### 理由・代替案・影響

[ADR-014](./ADR-014-claude-harness-main-agent-and-review-structure.md)は層の境界と観点の早期打ち切りを問題としている。Codexでも1体の出力項目を増やすだけでは、文書/securityを独立文脈で最後まで読む目的を満たさないため、その案は採らない。Claude同様に異なる型を増やして毎回並列実行する案は、現在の同時実行制限と既存の単一reviewer型に合わせて採らない。

型を増やさず観点別に逐次実行するため、通常のレビュー回数と所要時間は増える。費用や品質の改善率は実測なしに断言しない。今回の独立レビューで実行を確認し、実課題での端末確認・外部投稿・定期棚卸しの運用は別の検証として扱う。

## SS-206追補・PR #165の追加取り込み（2026-10-14）

SS-184の台帳連携を、前回の観点別レビュー構成を保ったまま追加で適応する。計画の「プライバシーへの影響」は必須で、影響が無い場合も理由を書く。台帳の対象パスに触れる差分、またはパス外でも利用者データの取得・送信・保存・削除・公開範囲を変える差分ではsecurityを起動する。6番目の観点で台帳・ポリシー本文/revisedOn・App Privacy申告を実装と照合し、食い違いは攻撃の成立を必要条件とせず台帳の行とポリシーの節で示す。対象パスは台帳へ集約し、別reviewer型や固定パス表は追加しない。ポリシー本文の既知の未反映（SS-210）の修正は今回の取り込み範囲に含めない。
