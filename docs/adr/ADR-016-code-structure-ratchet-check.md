# ADR-016: コードの構造（フォルダのファイル数・接頭辞の集中・ファイルの行数）は CI でラチェット方式で止め、既存の違反は課題つきの baseline で据え置く

## 日付

2026-11-02（SS-252）

## コンテキスト

フォルダ内のファイル過多や長いファイルなど、可読性が落ちている兆候が出ている。SS-252 の時点の実測:

- `packages/mobile/src/features/pin/lib` に実装 48・テスト 47 のファイルがあり、`features/pin/components` は実装 47。`walk/lib`・`src/lib` も 20 を超える
- `features/pin` の中に散歩マップ（`sanpoMap*`・`SanpoMap*`）のまとまりが混ざっている（`pin/components` に 15、`pin/lib` に 9）
- `packages/backend/src/sanposcape/sanpo_maps/pins/tests/test_router.py` が 2,845 行、`pins/service.py` が 773 行

これまでは、分けるかどうかはレビューの目に任されていた。1回の変更では少しずつしか増えないので、レビューでは止まりにくい。
一方で、いま閾値を超えているものを全部直してから検査を入れるのは、課題として大きすぎる。

この課題は、コードの読みやすさを保つ4段の仕組みの1段目にあたる。

1. SS-252（この ADR）: 構造の検査を CI に足す
2. SS-253: ruff・oxlint に、関数の複雑度・長さ・循環 import のルールを足す
3. SS-254: 分け方を判断して実行する skill を作り、change-reviewer に「構造の悪化」の観点を足す
4. SS-255: 月次の定期レポート（変更の多いファイル、一緒に変わるファイル、重複、未使用のコード）

閾値を下げていく進め方と baseline の扱いは、SS-253 の linter のルールでも同じものを使う。

## 決定

1. **`scripts/code-health/check-structure.py` で次の3つを測り、CI（`.github/workflows/code-health.yml`）で止める。** 標準ライブラリだけで書き、依存のインストールが要らないので、paths で絞らずに全 PR と main への push で走らせる（docs-lint と同じ考え方）。

   | 測るもの（kind） | 警告（表示だけ） | 失敗 |
   |---|---|---|
   | ファイルの行数（`file-lines`）: 実装 | 500 行を超える | 800 行を超える |
   | ファイルの行数（`file-lines`）: テスト | 1,000 行を超える | 1,500 行を超える |
   | フォルダ直下の実装ファイルの数（`folder-files`） | — | 20 を超える |
   | 同じフォルダで、名前の最初の語が同じ実装ファイルの数（`prefix`） | — | 7 を超える（8 以上） |

   - テストはケースを並べるので実装より長くなりやすく、閾値を分ける。フォルダのファイル数は、テストを実装の隣に置く mobile で数が倍になるのを避けるため、テストを除いて数える（テストの数は表示する）
   - 警告は失敗にせず、GitHub の注釈にもしない。どの PR にも同じものが並んでノイズになり、注釈の件数の上限にも当たるため。ログの一覧で「次に分ける候補」として見る
2. **対象は git の管理下の `packages/`・`scripts/` のソース**（`.py .ts .tsx .js .jsx .mjs .cjs .astro`）。次は除く。
   - 生成物 `packages/mobile/src/api/generated`（どの検査も）
   - package の `docs/` の下（デザインのモックの JS など、アプリのコードではないもの）
   - `packages/backend/alembic/versions`（マイグレーションは増えていくのが性質なので、ファイル数と接頭辞だけ測らない。行数は測る）
   - `__init__.py`（構造のためだけのファイル。フォルダの数に入れない）
   - テストの判定: `*.test.*`・`*.spec.*`・`test_*.py`・`*_test.py`・`conftest.py`、`tests/`・`__tests__/`・`test/`（mobile の vitest の setup と mock）・`__mocks__/` の下
3. **接頭辞は、ファイル名の最初の語で数える**（camelCase・PascalCase・snake_case・kebab-case を語に分ける）。慣習で付く `use`・`test` は飛ばす。
   最初の語が親フォルダの名前の語と同じとき（`features/pin/lib/pinEditDraft.ts` の `pin`）は、フォルダで既に分かれている語なので次の語（`edit`）で数える。
   機能名を名前に含める命名規約（`features/walk/components/Walk*.tsx`）のフォルダが、それだけで候補にならないようにするため。
   これで `features/pin` の中の `sanpoMap*` のような、別のまとまりが混ざっている所が候補に出る。
4. **ラチェット方式にする。** 既存の違反は `scripts/code-health/structure-baseline.json` に、載せたときの値（行数・ファイル数）つきで据え置く。
   - baseline に無い違反は失敗にする
   - baseline の値を超えたら（悪化）失敗にする。行が1行増えただけでも落ちる
   - 値が減った・閾値以下になった項目は、下げられる・外せると表示するが、失敗にはしない（check-doc-references.py と同じ）。減らした PR で `--baseline` を流して下げておく
5. **baseline の各項目には、片付ける課題（`issue`。`SS-<番号>`）と、今は分けない理由（`reason`）を必ず書く。** 欠けていれば失敗にする。
   載せたまま忘れないよう、`docs/compat-tracker.md` と同じく「いつ片付けるか」を課題で残す。
   - 新しい違反や悪化を baseline に載せて通すこと（`--baseline` で値を上げる・項目を足す）は認めるが、その PR の差分に baseline の変更と理由が現れ、レビューで妥当かを見る。
     値を上げた項目は、再生成で `reason` が空になる（前の理由は上げた後の値の説明にならない）。何のために上げたかを書き直さないと検査が通らない
   - SS-252 の時点の違反は、backend を SS-256、mobile を SS-257 で片付ける（どちらも SS-254 の skill を待つ）
6. **閾値は緩い値から始め、段階的に下げる。**
   - 失敗の閾値は、まず今の値で固定する。下げるのは、その kind の baseline が空になった（または残りに片付けの課題の目処がある）ときに検討する
   - 下げるときは、新しい閾値で増える違反を baseline に載せ、片付ける課題を起票し、この ADR に追補する（閾値の値と理由はこの ADR が正本で、スクリプトの定数と揃える）
   - 警告の閾値は、次に下げるときの目安を兼ねる。警告の件数が少なくなったら、警告の値を失敗の閾値にすることを検討する
   - baseline の件数が減っているかどうかが、この仕組みが機能しているかの指標になる。定期の棚卸し（SS-255 の月次レポート）で、下げられる項目と片付けの課題の進み具合を見る
7. **SS-253 の linter のルールも同じ方針にする。** 閾値（関数の複雑度・長さなど）は緩い値から始めて段階的に下げる。既存の違反は、linter の除外の設定（ファイル単位の ignore など）を baseline として扱い、
   各除外に片付ける課題と理由をコメントで残す。新しいファイルを除外に足して通すときは、この ADR の決定5と同じく差分でレビューする。
8. **失敗したときの案内（`SPLIT_GUIDE`）はスクリプトの1か所にまとめる。** 今は「分け方を決めて分割する。分けられない理由があれば baseline に課題と理由つきで載せる」とだけ書く。
   SS-254 で分割を判断する skill ができたら、そこに skill の名前を足す。

## 検討した選択肢

### 選択肢1: 閾値を超えているものを全部直してから、違反をすべて失敗にする

- **概要**: baseline を持たず、検査を入れる前に既存の違反を片付ける
- **メリット**: 仕組みが単純。例外の管理が要らない
- **デメリット**: mobile の `features/pin` の再編を含み、検査を入れるまでに時間がかかる。その間も悪化は続く

### 選択肢2: 警告だけにする（失敗にしない）

- **概要**: 閾値を超えたものをログや注釈に出すだけにする
- **メリット**: 作業を止めない
- **デメリット**: 警告は見られなくなり、増え続ける。止める仕組みにならない

### 選択肢3: ラチェット方式（新しい違反と悪化だけを失敗にし、既存は課題つきの baseline で据え置く）（採用）

- **概要**: 決定4・5のとおり
- **メリット**: 今日から悪化を止められる。既存の違反は課題として見え、減っていくのが分かる。リポジトリに既にある方式（docs-lint）と同じで覚えることが少ない
- **デメリット**: baseline に載ったファイルを触る変更が、先に分割を求められる（下の「影響」）

### 行数を linter のルール（oxlint・ruff の行数のルール）で測る案

- **概要**: ファイルの行数は linter のルールで測り、フォルダと接頭辞だけをスクリプトで測る
- **メリット**: エディタ上で気づける
- **デメリット**: backend と mobile で設定と baseline の持ち方が分かれ、Python と TypeScript で行数の数え方も揃わない。フォルダと接頭辞はどのみち linter では測れない。
  関数の単位（複雑度・長さ）は linter が得意なので SS-253 で linter に任せ、ファイルとフォルダの単位はこのスクリプトにまとめる

### baseline をテキストの1行形式にする案（check-doc-references.py と同じ）

- **概要**: `kind:path:value` のような行を並べる
- **メリット**: 既存の検査と同じ形
- **デメリット**: 課題・理由・値を1行に詰めると読みにくく、壊れやすい。JSON にして、再生成（`--baseline`）でも課題と理由を引き継ぐ

## 決定理由

- 1回の変更では少しずつしか増えないものは、機械で「増えた」ことを止めるのが効く。悪化だけを止めれば、既存の違反を片付ける前でも今日から入れられる
- baseline の各項目に課題を必須にすると、据え置いたものが課題として管理され、放置されにくい
- 標準ライブラリだけで書けば、依存のインストールが要らず、全 PR で数秒で走る。backend と mobile をまたいで同じ基準で測れる

## 影響

### ポジティブな影響

- フォルダのファイル過多・同じ接頭辞の集中・長いファイルが、増える時点で CI に止められる
- 既存の違反が baseline と課題（SS-256・SS-257）で一覧になり、減っていくのが追える

### ネガティブな影響・トレードオフ

- baseline に載ったファイルやフォルダを触る変更は、1行・1ファイル増えるだけでも落ちる。例えば `pins/tests/test_router.py` にテストを足すと、先に分割する（SS-256）か、その PR で baseline の値を上げて理由を書く必要がある
- 名前の最初の語による接頭辞の判定は粗い。語の区切りが命名と合わないと、まとまりを見落としたり、関係の無いファイルを同じ接頭辞として数えたりする。候補を出すだけで、分け方は人（SS-254 の skill）が決める
- 行数は空行・コメントも数える。整形の差で行数が変わる

### 移行・対応が必要な事項

- SS-256・SS-257 で、SS-252 の時点の baseline を片付ける
- SS-254 で、`SPLIT_GUIDE` に分割の skill の名前を足し、change-reviewer に「構造の悪化」の観点を足す
- SS-253 で、決定7のとおり linter のルールを同じ方針で入れる
- SS-255 の月次レポートで、baseline の件数と下げられる項目を見る
- `code health` の job を必須のチェックにするかは決めていない。main のルールセットには必須のステータスチェックが無く（2026-11-02 時点。docs lint も同じ）、失敗したまま merge できる
