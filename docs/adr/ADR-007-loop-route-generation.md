# ADR-007: 周回ルート（往路と異なる道で戻る）の生成方式

## 日付

2026-09-15（初版。実 API 検証（下記「移行・対応が必要な事項」参照）は未実施）

## コンテキスト

sanposcape の中核体験は「現在地から指定時間で往復できる範囲のスポットを提示し、選んだ先まで歩く」ことである。SS-16 では選択スポットまでの片道ルートを `/explore/routes/walking` で取得し、往復は「同じ道を戻る」前提（片道×2）で扱っていた。SS-33 の課題は、「現在地 → 目的地 → 往路とは異なる経路 → 現在地」という周回ルートを提示し、所要時間・距離を片道×2の近似ではなく周回全体の実値にすることである。「往路と異なる道で戻る」は体験の中核であり、MVPとして成立するために必須のタスクとされた。

Google Routes API（`computeRoutes`）は周回ルートを直接サポートしない。目的地を `origin`=`destination` にして往復を1回で計算する API は無く、`computeAlternativeRoutes`（代替ルート）と `intermediates`（経由点指定）は併用できない。そのため、何らかの形で「往路と異なる道を通る」ルートを間接的に作り出す必要がある。

ユーザーから今回の実装にあたり次の追加指示があった。

1. **散歩中にルートを再計算しない**。散歩開始時にゴールと帰りのルート（=周回ルート全体）を決めたら、その後はユーザーが自由に歩ける（参考表示に留める）。SS-35 で実装した散歩中の再計算（逸脱検知による自動再計算・手動再計算ボタン）は撤去する。
2. **ゴール（折り返し地点）への到着判定はしない**。「現在が往路/復路のどちらか」の判定ロジック（折り返し検知・ラッチ等）は実装しない。

この指示により、ルート API は「スポット選択時の1回」だけになり、前回試行（後述）の複雑さの大半を占めていた「再計算」「往路/復路判定」との整合という制約が消えた。

### 前回試行（PR #62、クローズ済み）の経緯

`origin/tri-star/SS-33`（25コミット、mainに未マージ）で一度実装を試みたが、「時間が経ちすぎた」「動作確認でうまく行っていないポイントがある」という理由でクローズされた。前回の複雑さの大半は、散歩中の再計算（`route_type: loop|one_way` の切替）と往路/復路判定（ラッチ+投影距離）との整合から来ていたが、「動作確認でうまく行かなかった点」の詳細自体はどこにも記録されておらず、backend の品質そのものに問題があったのかは切り分けられていない。

前回の骨格（後述の決定1で仔細に検討）は今回も参考にしたが、指標・しきい値の設計には次の弱点があった（今回の対策は決定3参照）。

| # | 弱点 | 根拠・想定される現象 |
|---|---|---|
| W1 | 「3指標」は実質2指標だった | 「総時間/(往路×2) ≤ 1.4」は数学的に「復路/往路 ≤ 1.8」と同値。直線距離に対する迂回の上限は誰も見ていなかった |
| W2 | Jaccard の重複率は長い復路で薄まる | 復路が長ければ和集合が大きくなり値が下がる。短距離ほど O・D 付近の道の共有が避けられず値が悪く出る |
| W3 | 経由点が川・線路・大きな公園・私有地の中に落ちる | 経由点は最寄りの道にスナップされ、橋や入口まで大回りしたり「行って戻る」ひげ（スパー）ができたりする。ひげは往路との重複率では検出できない |
| W4 | 短距離では周回の余地が小さい | α=0.25 だと 200m の目的地で横ずらしが 50m しかなく、同じ道か隣の路地にしかならない。E2E が選ぶ fake-place-1 も約200m |
| W5 | 先に合格した方を採用するので、良い方を選べない | 右が辛うじて合格すると左がずっと良くても使われない。逐次呼び出しなので最悪で「読み取りタイムアウト×2」待つ |
| W6 | サンプル数が少なく地形の偏りを見ていない | α=0.25 の実測は18試行のみで、川沿い・線路沿い・大きな公園の縁などの難所を意図して含めていない |
| W7 | 動作確認の不具合点が特定されていない | mobile 側（再計算・判定）の問題だった可能性が高いが backend 単独の品質は未検証のまま |

前回スパイクの主要な実測値（α=0.25、3地点×3目的地×左右2方向=18試行。旧ブランチが参照できなくなる可能性があるためここに転記する）:

- 重複率（Jaccard、10m補間→20mグリッド）の中央値: 右 0.147 / 左 0.203
- 迂回率（総時間/(往路×2)）の最大: 1.397（郊外の短距離 486m、若葉台〜鶴川周辺）
- 「周回総時間 ÷ 片道×2」: 中央値 1.099、p75 1.168、最大 1.400

## 決定

### 決定1: 周回生成方式 —「経由点の幾何生成 + 左右並列 + スコア選択」

前回の骨格（1回の `computeRoutes` に `intermediates=[destination(stopover), via(via点)]` を渡し、`origin=destination=O` として2 leg を取る）は残し、上記の弱点を潰す形で改良する。左右の経由点を**常に並列取得**し、判定した指標からスコアが良い方を採用する。逐次（右→左、先に合格した方を採用）だった前回方式からの変更点である。

再計算がなくなり、ルート API は「スポット選択時の1回」だけになったため、提示1回あたりのコストは品質優先で配分できる。`/explore/places` は1検索で最大20回の Routes 呼び出しをしているため、周回の+1回（常に2回、両候補とも失敗（Quota以外）かつ残り時間がある場合のみ発生する往路取り直しを含めても最大3回）はそれに比べて小さい。逐次呼び出しより並列の方が待ち時間の最悪値が短くなる。結果は決定的（乱数・時刻を使わない。同点のときは右を優先）。

### 決定2: 経由点の生成規則

- `d = haversine(O, D)`。`d < 50m` なら周回を作らない（往路を1回取得して同じ道で返す）
- `offset = max(0.25 × d, 80m)`。0.25 はスパイクの実測値、80m は下限（W4への対策）
- 経由点は `midpoint(O, D)` から `bearing(O→D) ± 90°` に `offset` だけずらした点（右を+90°、左を−90°）
- 経由点の座標は**小数5桁に丸めてから** Google へのリクエストとキャッシュキーの両方に使う（浮動小数の揺れでキャッシュを外すのを防ぐ）

### 決定3: 妥当性の指標と選択

leg の path を10m間隔に補間し、20mグリッドのセルに割り当てたうえで、次の4指標で判定する（すべて `maps/loop_route.py` の純粋関数）。

| 指標 | 定義 | しきい値 | 対応する弱点 |
|---|---|---|---|
| `detour_ratio` | (往路 + 復路の duration) / (往路 duration × 2) | ≤ 1.4 | W1（3指標だったものを1つにまとめる） |
| `return_overlap_ratio` | 復路の補間点のうち、往路のセル＋周囲8近傍（約30mバッファ）に入る点の割合。O・D から `clamp(0.2d, 30m, 100m)` 以内の点は分母・分子の両方から除く | ≤ 0.5 | W2（片方向・除外半径で長い復路の希釈を防ぐ） |
| `return_backtrack_ratio` | 復路の補間点のうち、「同じセルを8サンプル（約80m）以上離れてから再訪した」点の割合 | ≤ 0.15 | W3（ひげ） |
| `via_snap_distance_meters` | 経由点から、復路の補間点までの最短距離 | ≤ 250m | W3（川・大きな公園） |

合格した候補の中から `score = return_overlap_ratio + 0.5 × (detour_ratio − 1)` が最小のものを採用する（同点なら右）。合格した候補がなければ同じ道フォールバックにする（決定5）。**しきい値・係数・下限オフセットはすべて `maps/loop_route.py` のモジュール定数**にした（env にしない。運用で動かすものではなく、検証とコード変更で決めるものであるため）。

初期値は前回スパイクの実測（α=0.25、`detour_ratio` 相当の分布 p75=1.168・max=1.400 等）を踏まえて設定したが、**下記「移行・対応が必要な事項」のとおり、実 API での検証は本 ADR 執筆時点で未実施**であり、これらの値は暫定である。

### 決定4: コスト・キャッシュ・レート制限

- **コスト**: 1回の散歩で places 検索（Places 1回＋Routes 最大20回）＋周回2回（両候補とも失敗（Quota以外）かつ残り時間がある場合のみ往路を取り直し、3回になる。片方だけ成功した場合はその往路 leg を逆順にするだけで追加呼び出しはしない）。変更前は places＋walking 1回＋散歩中の再計算（最大1回/分）だったため、再計算が無くなった分、散歩1回あたりの総呼び出しは同等か減ると見込む。
- **キャッシュ**: `HttpGoogleMapsProvider` に周回専用の `_loop_cache`（TtlCache）と `_loop_flight`（SingleFlight）を追加した。キーは `loop:{O 5桁}:{D 5桁}:via:{V 5桁}` とし、片道の `route:` とは名前空間を分ける。TTL・上限は既存の `google_maps_cache_ttl_seconds` / `max_entries` を共用する。service 層でのキャッシュは追加しない（判定は純粋関数で安く、二重キャッシュは不整合の元になる）。
- **レート制限**: 変更しない（30req/60s、`/explore/places` と共有）。受信リクエストは「walking 1回＋再計算」から「loop 1回」に減り、1リクエストあたりの外部呼び出しの増幅は最大3倍で、places 検索の最大21倍より小さいため、新しい悪用経路にはならない。
- **待ち時間の上限**: 新しい設定 `GOOGLE_MAPS_ROUTE_DEADLINE_SECONDS`（既定12秒、上限25秒）。これは1リクエスト全体（並列2候補＋同じ道フォールバックの単発取得まで含む）の時間予算であり、1候補あたりの上限ではない。並列の各呼び出しは `min(read_timeout, route_deadline_seconds)` で打ち切り、両候補失敗時の往路取り直しは残り予算（`deadline - 経過時間`）で判定する（無ければ503）。Lambda の29秒制約より十分短くする。`_request()` は `httpx.Timeout(timeout_seconds, connect=min(connect_timeout_seconds, timeout_seconds))` を使い、connect フェーズだけは `GOOGLE_MAPS_CONNECT_TIMEOUT_SECONDS`（既定3秒）のまま短く保つ（ARCH review: 単一の float を渡すと connect にも同じ値が適用され、接続詰まり時に最大25秒待ってしまう問題への対策）。

### 決定5: フォールバックとエラーの扱い

1. `GOOGLE_MAPS_LOOP_ROUTE_ENABLED=false`、または O-D が50m未満 → 往路を1回取得 → 同じ道で返す
2. 左右を `ThreadPoolExecutor(max_workers=2)` で並列取得する
3. 成功した候補を判定し、合格があればスコア最小のものを返す（`return_is_same_path=false`）
4. 合格がなく成功した候補が1つでもあれば、その候補の往路 leg を逆順にして同じ道で返す（追加の呼び出しはしない）
5. 成功した候補が無ければ: 1つでも Quota エラーなら429、それ以外で残り時間があれば往路を1回取得して同じ道、それも失敗すれば503

**周回を作れない・全候補が不合格・kill switch オフのいずれの場合も 200 + `return_is_same_path=true` を返し、エラーにはしない**。ログは INFO で候補ごと（side・合否・reason・各指標）と採用結果を1行ずつ出す。**座標・place_id は出さない**（利用者の現在地が分かってしまうため）。

### 決定6: provider のインターフェースは既存を拡張せず、別メソッドにする

`GoogleMapsProvider` に `get_walking_loop_route(origin, destination, via, *, timeout_seconds) -> ProviderLoopRoute` を新規追加した（`ProviderLoopRoute` は outbound/inbound の2 leg。既存の `ProviderRoute` を再利用する）。既存の `get_walking_route` へ `intermediates` 引数を足す案は採らなかった（決定理由を参照）。

### 決定7: `/explore/places` の往復値は片道×2のまま（補正係数は入れない）

一覧（`/explore/places`）の候補絞り込みは従来どおり片道×2の近似のままとし、選択後の周回ルートだけが `/explore/routes/loop` の実測値になる。前回試行では係数1.15を掛けていたが、今回は選択規則（スコア選択・下限オフセット・迂回の上限）が変わっているため、そのまま流用する根拠が無い。`detour_ratio ≤ 1.4` の上限があるため、一覧の値と選択後の周回値のずれは最大1.4倍に収まる。

### 決定8: fake provider（`MAPS_MODE=fake`）の周回対応

`FakeGoogleMapsProvider.get_walking_loop_route` は、往路に既存の `get_walking_route(O, D)`（直線）を再利用し、復路は `D → via → O` を直線で結ぶ（経由点の幾何生成は service 側の `maps/loop_route.py` の責務であり、fake は直線で結ぶだけ）。乱数・時刻は使わない。

**E2E の生命線**: `MapsService(FakeGoogleMapsProvider())` で、fake-place-1〜5（origin から200m〜1000m）のすべてに対して `return_is_same_path` が `false` になることをテストで固定した（`integrations/google_maps/tests/test_fake.py`）。mobile の Maestro subflow が選ぶ最短候補（fake-place-1、約200m）が最も判定に引っかかりやすいため、しきい値を調整した場合は必ずこのテストを再確認すること。

同じ道フォールバックを手動で再現する方法は `GOOGLE_MAPS_LOOP_ROUTE_ENABLED=false`（real/fake いずれでも有効）。

## 検討した選択肢

### 周回生成方式

| 方式 | 呼び出し回数/提示 | 品質 | 判断 |
|---|---|---|---|
| A. 前回方式（右→左の逐次、先に合格した方） | 1〜2（最悪3） | W1〜W5 あり | 不採用（改良して採用案にする） |
| B. 往路と復路を別々に呼び、復路は `computeAlternativeRoutes` の候補から重複最小を選ぶ | 2 | 徒歩の短距離では代替ルートが返らないか、ほぼ同じ道になりやすい。`intermediates` と併用できず経由点による誘導もできない | 不採用 |
| **C. 経由点を左右並列に取得し、改良した指標で判定してスコアで選ぶ（採用、決定1）** | 常に2（最大3） | 良い方を選べる。ひげ・スナップ・短距離を検出できる | **採用** |
| D. 経由点候補を多数（α×左右で4〜6本） | 4〜6 | 最良 | 段階2として条件付きで検討（本 ADR「移行・対応が必要な事項」参照）。最初の実装には入れない |
| E. 経由点を実在する POI にスナップ（places の結果を流用） | +Places 呼び出し（キャッシュが外れると高価） | 川・私有地の問題に強い | 将来案。loop リクエストはカテゴリを持たず、Lambda のプロセス内キャッシュには当たりにくい |

### レスポンスの `legs` の形

- **配列（`legs: [outbound, return]`。採用）**: `kind` フィールドで種別を判定する。将来「2スポット周回」等で leg が増える余地を残せる。mobile プランが配列前提で詳細化済み。
- **固定フィールド（`outbound_leg` / `return_leg`）**: kind の欠落・重複を型で防げる利点はあるが、拡張性が低く、mobile 側の実装との整合も取り直しになる。不採用。

### エンドポイントの形

- **新エンドポイント `POST /explore/routes/loop`（採用）**: 既存 `/explore/routes/walking` の意味・スキーマを変えずに済み、配布済みビルドが周回値を片道として誤表示する事故を避けられる。前回試行にあった `route_type: loop|one_way`（再計算用）は再計算の撤去で不要になった。
- **既存 `/explore/routes/walking` を拡張**: `duration_seconds` 等の意味を変えると配布済みの旧ビルドが誤表示する。不採用。

## 決定理由

- 「前回試行（PR #62、クローズ済み）の経緯」で洗い出した W1〜W7 のうち、W1（指標の冗長性）・W2（Jaccardの希釈）・W3（ひげ・スナップ）は指標の再設計（決定3）で、W4（短距離での余地不足）は下限オフセット（決定2）で、W5（先着採用）は並列化＋スコア選択（決定1）で、それぞれ対応した。W6（サンプル不足）・W7（不具合の切り分け不能）には、検証スクリプト（`scripts/loop_route_probe.py`）による再現・可視化と、座標を含まないログ出力で対応する。
- ユーザー指示で再計算が無くなり、ルートAPIは「スポット選択時の1回」に集約された。そのため提示1回あたりのコストは品質優先で配分してよいと判断した（決定1・決定4）。
- 決定6（既存 `get_walking_route` へ `intermediates` 引数を足さず、別メソッドにした理由）: 戻り値の形（片道は1 leg、周回は2 leg）が呼び出し引数で変わると、20回呼ぶ places 検索側の経路にも型として波及しうる。また `loop:` と `route:` はキャッシュの名前空間を分けているため（決定4）、1メソッドに統合するとキー生成のロジックが分岐だらけになる。`**kwargs` を受けるテスト用スタブが呼び出しを黙って吸収してしまう問題（決定6本文）と合わせ、別メソッドの方が実装漏れに気付きやすいと判断した。
- しきい値の妥当性は本来、実 API 検証で確定させる設計であり、初期値は前回スパイクの実測（上記「前回試行の経緯」に転記した値）を根拠にした。**実 API 検証は本 ADR 執筆時点で未実施**であり、判断の完全性としてはこの点が最大の留保事項である（「移行・対応が必要な事項」参照）。

## 影響

### ポジティブな影響

- 「往路と復路が異なる周回ルート」という中核体験を成立させられる。
- 判定ロジックを純粋関数（`maps/geometry.py` / `maps/loop_route.py`）に切り出したことで、DB・HTTPを介さずに単体テストでき、検証スクリプトからも同じロジックを再利用できる。
- 既存の `/explore/routes/walking` の意味・スキーマ・挙動は変えていない（`deprecated=True` の付与のみ）。

### ネガティブな影響・トレードオフ

- 周回の品質は確率的にしか保証できない（合格候補が無ければ同じ道フォールバックになる）。
- 一覧（`/explore/places`、片道×2）と選択後（周回の実測値）の値にずれが生じる（最大 `detour_ratio` の上限＝1.4倍程度）。
- Routes の呼び出しは常に2回（両候補とも失敗（Quota以外）かつ残り時間があるときのみ往路取り直しで最大3回）になり、`/explore/routes/walking` 単体（1回）より増える。
- プロセス内キャッシュ（`_loop_cache`）は Lambda では効きにくい（ADR-005 の前提から変わらない）。

### 移行・対応が必要な事項

- **実 API 検証を実施する**（本 ADR 執筆時点で未実施。`GOOGLE_MAPS_SERVER_API_KEY` を持つ開発者が対応する）。`scripts/loop_route_probe.py` と `scripts/loop_route_probe_cases.yaml` を使い、次を確認・記録する。
  - WALK + `via: true` で legs が2つに分かれて返ること
  - Cloud Billing 上の SKU が Compute Routes **Essentials** であること（Pro 以上なら決定4のコスト試算を見直す）
  - 採用ルートを GeoJSON で目視し、ひげ・川の対岸への大回り・私有地の突っ切りが無いこと
  - フォールバック率（`return_is_same_path=true` の割合）が20%以下であること
  - `detour_ratio` の分布（中央値・p90・最大。最大は上限1.4そのもの）
  - 1提示あたりの待ち時間（並列2呼び出し）の p90 が3秒以下であること
  - 上記の結果、決定3のしきい値・下限オフセットに誤判定（目視では良い周回なのに不合格、悪いのに合格）があれば定数を調整し、**調整後は fake の E2E 生命線テスト（決定8）が通ることを必ず再確認する**
  - 検証結果（数値の表、調整した定数と理由）を本 ADR に追記する
- 実 API 検証でフォールバック率が目標（20%）を超え、かつ段階2（α拡大）で改善が確認できた場合のみ、`d = 50m 以上かつ左右とも「重複だけ」で不合格` のケースで α を0.4に拡大して再試行する処理を追加する。最初の実装には入れない。
- `/explore/places` の補正係数（決定7）は、本番ログに出る `detour_ratio` の分布を見て再評価する。
- 経由点を実在する POI にスナップする案（検討した選択肢のE）は、Places 呼び出しのコストとキャッシュ命中率の観点から見送った。将来、川沿い・私有地の問題が実運用で顕著になった場合に再検討する。
- `/explore/routes/walking` の削除判断は、配布状況を見て別課題で行う（今回は `deprecated=True` の付与のみ）。
- （security review SEC-L1）`origin`/`destination` の距離には上限を設けていない（`GeoPoint`/既存 `/explore/routes/walking` と同様）。`evaluate_loop` の `resample()` 処理コストが距離に比例して増える点は、`maps/loop_route.py` の `_resample_step_meters()` で1 leg あたりの再標本化点数に上限（既定2000点）を設けて緩和した。原点・目的地そのものの距離バリデーションは入れていない（既存 walking との一貫性を優先）。
- （security review SEC-L2）周回1回あたりの外部呼び出しは常に2〜3回で、受信側のレート制限は `/explore/places`（最大21倍の増幅）と共有のままにしている（意図的な設計判断）。本番運用開始後は Google Cloud Billing のクォータ・アラートで実際のコスト増幅を監視することを推奨する。
