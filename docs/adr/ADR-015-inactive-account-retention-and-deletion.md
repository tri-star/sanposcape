# ADR-015: 最終利用から 3 年使われていないアカウントは、メールで事前に通知したうえで削除する

## 日付

2026-10-13（SS-188 で方針を決定。実装は後続課題）

## ステータス

採用（方針とプライバシーポリシーへの反映まで）。最終利用の記録・通知メール・定期削除は未実装で、後続課題で実装する（「移行・対応が必要な事項」）。

## コンテキスト

プライバシーポリシー（`packages/lp/src/pages/privacy.astro`）の「6. 保存期間」は、アカウント情報・散歩の記録・ピン・写真を
「利用者が削除するか、アカウントを削除するまで保存する」としており、期限が無い。
SS-158（プライバシーポリシーの公開）のレビューで、長期間利用がないアカウントを事前通知のうえ削除する余地を持たせるかを検討するよう指摘された
（[ADR-012](./ADR-012-lp-static-site-astro-s3-cloudfront.md) の要約「未解決・持ち越し」）。

決定時点の状況:

- 散歩の記録には位置の軌跡が含まれる。使われなくなったアカウントの情報を持ち続けるほど、漏洩時の影響が大きくなる。
- backend には「最後に使われた日時」を表す列が無い。`users.updated_at` は IdP から受け取るプロフィールが変わったときにしか動かない。
  セッションは自前のトークンで、access token は 15 分、refresh token は 30 日でローテーションする（[ADR-002](./ADR-002-auth-google-signin-and-stub-strategy.md)）。
- メールを送る仕組み（SES など）も、定期実行の仕組み（EventBridge Scheduler など）も無い。
- アカウント削除は `AccountDeletionService`（`packages/backend/src/sanposcape/users/service.py`）が行う。Apple ユーザーはトークンを失効させてから、
  `ON DELETE CASCADE` で関連する行を消す。写真の画像ファイルは保存領域に残る（[ADR-009](./ADR-009-sanpo-map-pin-data-model-and-photo-upload.md) の BK-2、SS-109 で対応予定）。
- 本番の LP は `/privacy/` を含む版をまだ公開していない。アプリもストアで公開していない。
- 利用規約は SS-187 で作成中で、まだ main に入っていない。

## 決定

1. **最終利用から 3 年が経過したアカウントを削除する。** 削除の対象は、利用者がアプリの「アカウントを削除」で削除するものと同じ範囲
   （アカウント情報、散歩の記録、ピン、写真、その他アカウントに関連する情報）。
2. **「利用」は、サーバーがその利用者のセッションを発行・更新した時点とする。** サインイン（`POST /auth/session`）と
   refresh token による更新（`POST /auth/refresh`）が成功したときに、`users` に追加する最終利用日時（列名は実装で決める。仮に `last_active_at`）を更新する。
   - アプリを開いて使っていれば、access token の期限（15 分）ごとに更新が走るので、粒度は十分に細かい。
   - 導入時の既存ユーザーの値は、マイグレーションを実行した時点とする（判定を厳しい側に倒さないため）。
3. **削除の 30 日以上前に、登録されているメールアドレスへ通知する。** 通知から削除までの間に利用（決定2）があれば、削除を取り消す。
   - 通知: 最終利用から「3 年 − 30 日」が経過し、最終利用より後にまだ通知していないアカウントに送る。送った日時をアカウントに記録する。
   - 削除: 「最終利用から 3 年が経過している」かつ「最終利用より後に送った通知から 30 日以上が経過している」の両方を満たすアカウントを削除する。
     - 通知が最終利用より後かどうかで判定するので、取り消しのために通知の記録を消す処理は要らない。通知の後に利用があれば、
       その通知は判定に使われなくなり、次に使われなくなったときにあらためて通知する。
     - 定期実行が止まったり遅れたりしても、通知から削除までの猶予は 30 日を下回らない。
   - メールアドレスが登録されていないアカウントは、通知せずに、最終利用から 3 年が経過した時点で削除する。
     送信を試みた後に届かなかった場合（宛先不明など）も、送った扱いとして同じ判定で削除する（ポリシーの「お知らせせずに削除することがあります」）。
   - Apple の「メールを非公開」で登録した利用者のアドレスは Apple の転送用アドレスで、送信元のドメインを Apple Developer に登録しないと届かない。
4. **削除は 1 日 1 回の定期実行で行い、利用者による削除と同じ `AccountDeletionService` を通す。** Apple のトークンの失効や、
   写真の画像ファイルの扱い（BK-2）を、利用者による削除と食い違わせないため。定期実行の仕組みは backend の Lambda（[ADR-005](./ADR-005-backend-serverless-deployment-lambda-function-url.md)）に
   EventBridge Scheduler などで起動するハンドラーを足す想定で、具体的な構成は実装の課題で決める。
5. **プライバシーポリシーの「6. 保存期間」に、この扱いを「削除することがあります」として書く（SS-188 で反映済み）。**
   実装の前から書くのは、公開前に入れておけば、公開後に保存期間を短くする変更（ポリシー「12. 本ポリシーの変更」の告知が要る）を避けられるため。
   「ことがあります」なので、実装までの間に削除していなくても事実に反しない。通知の方法と期限（3 年・30 日前）は書く。
   利用規約（SS-187）にも同じ扱いを書く。

## 検討した選択肢

### 期限

- **1〜2 年**: 情報を持つ期間は短くなる。一方で、散歩の記録は季節や生活の変化で間をあけて見返す性質があり、1〜2 年離れていた利用者の記録を失わせやすい。却下。
- **3 年（採用）**: 季節が一巡りしてもう一度離れる程度の空白は許しつつ、使われなくなったアカウントを持ち続けない。
- **5 年以上・期限なし**: 利用者の不利益は最も小さいが、保有を最小にする効果が薄い。期限なしは SS-158 の指摘に答えない。却下。

### 「利用がない」の判定

- **最終サインイン日時**: refresh token で使い続けている利用者はサインインし直さないため、使っていても「未利用」と判定される。却下。
- **認証済みのすべての API 呼び出しで更新**: 最も正確だが、リクエストごとに `users` へ書き込みが発生する。refresh の時点で十分な粒度が得られる。却下。
- **既存の `refresh_tokens` の最新の `created_at` から求める**: 列を足さずに済むが、refresh token の行を掃除したときに判定が壊れ、意図も読み取りにくい。却下。
- **セッションの発行・更新時に専用の列を更新（採用）**: 書き込みは既に refresh token の行を書いている箇所に足すだけで、判定の意味も明確。

### 事前通知

- **通知しない**: 実装は最も軽いが、散歩の記録を予告なく失うのは利用者の不利益が大きい。却下。
- **アプリ内の表示だけ**: 長期間アプリを開いていない利用者には届かない。却下。
- **登録メールアドレスへのメール（採用）**: Google・Apple とも登録時にメールアドレスを受け取っている。送信の仕組み（SES のドメイン検証・本番利用の申請）を新たに用意する必要がある。

### いつ実装するか

- **この課題で実装まで行う**: メール送信と定期実行は infra（sanposcape-infra）側の作業を含み、「決める」課題の範囲を超える。却下。
- **方針とポリシーだけ先に決め、実装は後続課題にする（採用）**: ポリシーへの反映は公開前に済ませたい（決定5）。実際に削除が起きるのは導入から 3 年後なので、実装の着手が遅れても利用者への影響は無い。

## 決定理由

- 位置の軌跡を含む情報を、使われなくなった後まで持ち続けない。一方で、散歩の記録を見返す価値を損なわない長さとして 3 年を選んだ。
- 判定・通知・削除のいずれも、利用者が予測でき、取り消せる（通知後に使えば削除されない）形にした。
- 削除の経路を利用者による削除と 1 つにまとめ、Apple の失効や写真の扱いの対応漏れを構造的に起こさない。

## 影響

### ポジティブな影響

- 使われなくなったアカウントの位置情報を持ち続けないため、漏洩時の影響を抑えられる。
- 公開前にポリシーへ入れたため、公開後に保存期間を短くする改定と告知が要らない。

### ネガティブな影響・トレードオフ

- 3 年使わなかった利用者は、通知を見落とすと散歩の記録を失う。メールアドレスが無い・届かない利用者には通知できない。
- メール送信の仕組みを新たに運用する必要がある（送信元ドメインの認証、バウンスの扱い、Apple の転送用アドレスへの送信元登録）。
- 招待・メンバー管理（ADR-009 の BK-7）を実装した後は、削除する利用者が他の人と共有している地図やピンの扱いが問題になる。
  これは利用者による削除と同じ問題で、BK-7 で決める扱いに従う。

### 移行・対応が必要な事項

- [ ] 後続課題（実装）: `users` に最終利用日時を追加し、`POST /auth/session`・`POST /auth/refresh` の成功時に更新する。既存ユーザーはマイグレーション時点で埋める。
- [ ] 後続課題（実装）: 通知メールの送信（SES のドメイン検証・本番利用の申請は infra 側。Apple の転送用アドレスへの送信元登録）。通知した日時を記録する（判定は決定3）。
- [ ] 後続課題（実装）: 1 日 1 回の定期実行で、通知の対象の抽出・通知・削除を行う（削除は `AccountDeletionService`）。
- [ ] 後続課題（実装）: 実装と同時に、プライバシーポリシーの 1-2（アカウント情報）・1-5（アクセスに伴う情報。保存は最長 400 日と書いている）・6 と
  [`docs/app-privacy-label.md`](../app-privacy-label.md) を見直す。最終利用日時をアカウントに紐づけて最長約 3 年保存すること、
  通知メールにメールアドレスを使うことが、本文・申告と食い違わないようにする（ADR-012 の SS-159 追補: 実装・ポリシー・申告を同時に揃える）。
  また、`users.updated_at` は `onupdate` で動くため、最終利用日時を ORM で更新すると `updated_at` も毎回動く。`updated_at` の使い道に影響が無いかを確かめる。
- [ ] SS-187（利用規約）: 同じ扱い（最終利用から 3 年、30 日以上前のメール通知、通知できない場合）を条項に入れる。
