# ADR-017: 関数の複雑度・長さ・依存の数・循環 import は ruff・oxlint のルールで止め、既存の違反はファイル単位の除外に課題と理由をつけて据え置く

## 現在有効な決定（要約）

> 最終更新: 2026-11-23（SS-259: mobile の SS-253 由来の除外を片付け、残すピンの4画面は今の実測値を上限にしたファイルごとの閾値にした）。本節は本文（追補を含む）を要約したもので、一次記録は本文。
> 本文と食い違う場合は本節の誤りとして本節を直す。

### 決定

- **backend は ruff の `C901`・`PLR0912`・`PLR0913`・`PLR0915` を使う**。閾値は max-complexity 15・max-branches 15・max-statements 60・max-args 8（既定は 10・12・50・5）。（本文: 決定1、SS-258 追補 決定10 で据え置き）
- **mobile は oxlint の `complexity` 20・`max-depth` 4・`max-lines-per-function` 200・`import/no-cycle`・`import/max-dependencies` 20 を使う**。（本文: 決定2）
- **mobile の SS-253 由来の除外は SS-259 で片付けた。分けられずに残すものは、"off" ではなくそのファイルの今の実測値を上限にした閾値（ラチェット）にし、課題（SS-282）と理由をコメントに書く**。値は上げない。（本文: 決定3、SS-259 追補 決定11・12）
- **backend は、分けない関数を定義の行の `# noqa: <ルール>` にし、直前のコメントに理由を書く。ファイル単位の除外（`per-file-ignores`）は使わない**。SS-253 由来の除外は SS-258 で片付けた。（本文: SS-258 追補 決定8・9）
- **恒久の除外はルールの趣旨に合わないものだけ**（mobile のテストの関数の長さ、`iconRegistry.ts` の依存の数）。（本文: 決定4）
- **閾値は既存の違反を片付けてから段階的に下げ、値と理由はこの ADR が正本**。backend は SS-258、mobile は SS-259 の時点で、どの閾値も新しい違反なしには下げられない。（本文: 決定5、SS-258 追補 決定10、SS-259 追補 決定13）
- **mobile の `lib/` から `react-native` を値として import することを `no-restricted-imports` で止める**。glob は深さに依存しない形。（本文: 決定6、SS-260 追補）
- **backend のモジュールの境界は import-linter ではなく AST のテストで守る**。（本文: 決定7）

### 変更・撤回された決定

- backend の既存の違反をファイル単位の除外で据え置く（決定3）→ 片付けた。分けない関数は行単位の noqa にする（SS-258 追補 決定8）
- mobile の既存の違反をファイル単位の `off` で据え置く（決定3）→ 片付けた。残すものは今の値を上限にしたファイルごとの閾値にする（SS-259 追補 決定11・12）

## コンテキスト

コードの読みやすさを保つ仕組みを4段で入れている（SS-252〜SS-255）。SS-252 ではファイル・フォルダの単位（ファイルの行数・フォルダのファイル数・接頭辞の集中）を
`scripts/code-health/check-structure.py` で測り、ラチェット方式で止める（ADR-016。SS-252 で作成。この ADR の作成時点では未マージ）。 <!-- doc-ref-ok: SS-252 で足すスクリプト。この ADR の作成時点では main に未マージ -->
関数の単位の兆候（複雑度・長さ・引数の多さ）と、依存関係の兆候（循環 import・1ファイルの依存の多さ）は、既存の linter のほうが得意なので linter のルールで止める。それがこの課題。

ADR-016 決定7 は、SS-253 の linter のルールも同じ方針にすると決めている。閾値は緩い値から始めて段階的に下げる。既存の違反は linter の除外の設定を baseline として扱い、各除外に片付ける課題と理由をコメントで残す。

SS-253 の時点の実測（既定の閾値での既存の違反）:

- backend（ruff 0.17.1。既定は max-complexity 10・max-branches 12・max-statements 50・max-args 5）: 68 件。
  そのうち PLR0913（引数の数）が 43 件ある。大半は pytest の fixture の注入と、キーワード専用引数を並べたリポジトリ・mapper の関数
- mobile（oxlint 1.89.0）: `max-lines-per-function` を 50 行にすると 275 件。React のコンポーネントは JSX を含めて1関数になるため。
  `complexity` は既定の 20 で 6 件。`import/no-cycle` と `max-depth`（既定の 4）は 0 件

## 決定

1. **backend は ruff の `C901`・`PLR0912`・`PLR0913`・`PLR0915` を `select` に足す**（`packages/backend/pyproject.toml`）。閾値は次のとおり。

   | ルール | 既定 | 採用 |
   |---|---|---|
   | `C901`（`mccabe.max-complexity`） | 10 | 15 |
   | `PLR0912`（`pylint.max-branches`） | 12 | 15 |
   | `PLR0915`（`pylint.max-statements`） | 50 | 60 |
   | `PLR0913`（`pylint.max-args`） | 5 | 8 |

2. **mobile は oxlint に次のルールを足す**（`packages/mobile/.oxlintrc.json`）。

   | ルール | 閾値 |
   |---|---|
   | `complexity` | 20（既定） |
   | `max-depth` | 4（既定） |
   | `max-lines-per-function` | 200。空行・コメントは数えない |
   | `import/no-cycle` | 循環があれば失敗（`@/` のエイリアス越しも検出する） |
   | `import/max-dependencies` | 20。型だけの import は数えない（実行時の結合を作らないため） |

3. **既存の違反は、linter のファイル単位の除外を baseline として据え置く。** backend は `[tool.ruff.lint.per-file-ignores]`、mobile は `overrides` でルールを `off` にする。
   - 除外するのは、そのファイルで実際に違反しているルールだけにする。違反の無いルールまで除外すると、そのファイルの悪化を止められない（mobile の override で複数のファイルをまとめるときは、違反しているルールが同じファイルだけをまとめる）
   - 各除外のコメントに、片付ける課題（backend は SS-258、mobile は SS-259）と、今は分けない理由（どの関数が何をまとめて持っているか、実測の値）を書く
   - 除外を足して通すことは認めるが、課題と理由を書き、その PR の差分でレビューする（ADR-016 決定5 と同じ）
   - 片付けた PR で除外の行を消す。ruff・oxlint は使われなくなった除外を教えないので、消し忘れは検査では見つからない
   - （**SS-258 追補**: backend のファイル単位の除外はすべて片付けた。分けない関数は行単位の noqa に移した（決定8）。mobile は引き続きこの決定で SS-259 が片付ける）
   - （**SS-259 追補**: mobile も片付けた。分けずに残すピンの4画面は `off` ではなく今の値を上限にした閾値にした（決定11・12））
4. **恒久の除外は、ルールの趣旨に合わないものだけにする。** 課題ではなく、恒久であることと理由をコメントに書く。
   - mobile のテスト（`*.test.ts(x)`）は `max-lines-per-function` を数えない。describe のコールバックが1つの関数になり、ケースを足すほど長くなるため。ファイルの長さは SS-252 の構造の検査が見る
   - mobile の `src/components/ui/icon/iconRegistry.ts` は `import/max-dependencies` を数えない。アイコンを並べる登録簿で、依存の数がそのまま登録したアイコンの数になるため
5. **閾値は既存の違反を片付けてから段階的に下げる。** 除外が減ったら（SS-258・SS-259）、閾値を既定へ近づけられるかを検討し、この ADR に追補する。
   下げるときに増える違反は、課題を起票して除外に載せる。閾値の値と理由はこの ADR が正本で、設定ファイルの値と揃える。
6. **mobile の `lib/`（`src/lib/**`・`src/features/*/lib/**`）から `react-native` を値として import することを `no-restricted-imports` で止める。**
   `lib/` は判定・整形の純粋関数の層で、Vitest でテストする（`packages/mobile/docs/folder-structure.md`）。この規則は文書にあったが、機械的な検査が無かった。SS-253 の時点の違反は 0 件。
   - 型だけの import（`import type`）は許す（`allowTypeImports`。トランスパイルで消える）
   - `no-restricted-imports` の override は後勝ちで置き換わる。そのため `lib/` の override に devTools の制限を再掲する。
     さらに `features/{walk,history,pin}/lib/**` には、その後ろの override で認証の制限も再掲する。
     順序と再掲は `src/config/oxlintRestrictedImports.test.ts` で検査する
   - （**SS-260 追補**: feature の中を領域で分ける方針（ADR-M-001 決定2）で lib/ が `features/sanpo-map/pin/lib/` のように深くなり、1段の `*` の glob では制限が黙って外れる。
     glob を深さに依存しない `src/features/**/lib/**`・`src/features/{walk,history,sanpo-map}/**/lib/**` に直し、同期検査のテストで `**/lib/**` の形を確かめる。
     認証の制限の対象は `features/pin` から改めた `features/sanpo-map/**` になった）
7. **backend のモジュールの境界（ADR-011）に import-linter は入れない。** `sanpo_maps/tests/test_architecture.py` が、ADR-011 の規則のうち AST で判定できるもの（M1・M2・M4・M7・M8 と、M3 の import・M5 の Protocol の port）を検査している（M6 と M3 のコンストラクタの引数はレビューで見る）。
   その中には、import の向きだけでは書けない規則（commit は `service.py` だけ、Protocol の port を作らない）も含まれる。import-linter を足すと、境界の定義が2か所に分かれる。

## 検討した選択肢

### 選択肢1: 既定の閾値のまま、既存の違反をすべて除外に載せる

- **概要**: ruff・oxlint の既定の閾値を使い、違反しているファイルをすべて除外に載せる
- **メリット**: 新しく書く関数は最初から既定の閾値で止まる
- **デメリット**: backend で約 40 ファイル、mobile で 100 を超える関数が除外になる。除外したファイルでは、そのルールが新しい関数にも効かなくなる。
  除外が多すぎると「載せれば通る」ものになり、ADR-016 が避けたかった状態になる

### 選択肢2: 閾値を今の最大値に合わせる（除外を持たない）

- **概要**: 既存の最悪の値（backend の複雑度 28、mobile の関数 410 行など）を閾値にする
- **メリット**: 除外の管理が要らない
- **デメリット**: 閾値が緩すぎて、ほとんどの新しいコードを止めない。直すべき関数も課題として見えない

### 選択肢3: 緩い閾値から始め、残る違反はファイル単位の除外で据え置く（採用）

- **概要**: 決定1〜5のとおり。既存の違反の分布を見て、除外が十数ファイルに収まる値から始める
- **メリット**: 大きく外れた関数は今日から止まる。据え置いた違反は、課題と理由つきで一覧になる。ADR-016 と同じ進め方で覚えることが少ない
- **デメリット**: 既定より緩い閾値の間は、既定を超えるが採用の閾値には収まる関数を止めない

### 除外を行単位の `# noqa` / `oxlint-disable` コメントにする案

- **概要**: 違反している関数の定義の行に抑止のコメントを書く
- **メリット**: 除外が関数の単位になり、同じファイルの新しい関数には効く。ruff の `RUF100` で、使われなくなった `noqa` を検出できる
- **デメリット**: 除外がコードのあちこちに散り、一覧と課題の対応が見えにくい。ADR-016 決定7 の「設定の除外を baseline として扱う」と合わない。
  片付けが進んで除外が関数の数件になったら、行単位に寄せることを検討してよい
- （**SS-258 追補**: backend は片付けで除外が関数の10件（すべて引数の数）になったので、行単位に寄せた（決定8））
- （**SS-259 追補**: mobile は寄せない。残すのは片付け待ちの4ファイルで、`import/max-dependencies` はファイルの単位のルールで行に結べないため（決定12））

## 決定理由

- 関数の単位の兆候は linter のルールが正確に測れて、エディタ上でも気づける。ファイル・フォルダの単位は SS-252 の検査に任せ、役割を分ける
- 緩い閾値から始めれば、除外を少なく保ったまま今日から入れられる。除外に課題を必須にすると、据え置いたものが放置されにくい
- `lib/` の react-native の禁止は、違反が 0 件のうちに入れれば既存のコードを直さずに済む

## 影響

### ポジティブな影響

- 大きく外れた複雑な関数・長い関数・依存の多いファイル・循環 import が、増える時点で CI（`backend-ci`・`mobile-ci` の lint の step）に止められる
- 既存の違反が、設定ファイルの除外と課題（SS-258・SS-259）で一覧になる

### ネガティブな影響・トレードオフ

- 除外はファイル単位なので、除外したファイルに足した新しい関数には、そのルールが効かない
- 除外の消し忘れは検査で見つからない（決定3）。片付けの課題で消す
- PLR0913 はキーワード専用引数も数える。キーワード専用で取り違えの起きにくい関数でも、引数をまとめる型に寄せるか、除外の理由を書く必要がある
- `no-restricted-imports` の override の順序に意味がある。override を足すときは同期テストを通す

### 移行・対応が必要な事項

- ~~SS-258（backend）・SS-259（mobile）で除外を片付け、閾値を下げられるか検討する~~（→ backend は SS-258、mobile は SS-259 で決着。閾値は据え置き（決定10・13）。mobile のピンの4画面は SS-282 で片付ける）
- SS-252 がマージされたら、この ADR の ADR-016 への言及をリンクにする
- feature 間の直接 import（walk ⇔ pin ⇔ history など）は禁止だが、まだ機械的な検査が無い。`no-restricted-imports` で止めるかは別の課題で決める

## SS-258 追補: backend の除外の片付けと行単位の noqa（2026-11-20）

### コンテキスト

SS-253 で `per-file-ignores` に据え置いた 12 ファイルを片付けた。据え置きの間に、除外していたファイルの関数は悪化していた
（`main.py` の `register_exception_handlers` 28 → 31、`update_pin` 複雑度 19 → 20・文 64 → 66、`MapsService.__init__` 引数 9 → 10）。
ファイル単位の除外ではそのファイルのルールが丸ごと効かなくなる、という決定3 のネガティブな影響が実際に起きた。

### 決定

8. **backend は、分けない関数を定義の行の `# noqa: <ルール>` にし、直前のコメントに理由を書く。`per-file-ignores` は使わない。**（SS-258 追補）
   - 行単位なら、同じファイルに足す新しい関数にはルールが効き続ける（ファイル単位の除外で起きた悪化を防ぐ）
   - noqa を足して通すことは認めるが、理由を書き、その PR の差分でレビューする（決定3 と同じ）。片付ける予定があるなら課題もコメントに書く
   - `pyproject.toml` の `per-file-ignores` の節は消し、この方針をコメントで残した
   - mobile（SS-259）は決定3 のまま。片付けの後に同じ形に寄せるかは SS-259 で決める（**SS-259 追補**: 寄せない。決定12）
9. **SS-253 で据え置いた違反の片付け方**（SS-258 追補）
   - 複雑度・分岐・文の数（`C901`・`PLR0912`・`PLR0915`）は、すべて責務で関数を分けた。
     例外ハンドラの登録はドメインごとの関数に（あわせて `main.py` から `exception_handlers.py` へ移した。`main.py` が構造の検査の警告の 500 行を超えたため）、周回ルートは候補の取得と判定に、`update_pin` は権限の確認・タグの適用と、
     DB に触れない変化の算出（`sanpo_maps/pins/update_plan.py`）に分けた。長いテスト2本はスレッドの中身・検証をヘルパーに出した
   - 引数の数（`PLR0913`）の10件は分けずに行単位の noqa にした。7件はキーワード専用の引数で、repository の列・一覧の条件、
     応答の組み立てに要る値、テストの部品（ID トークンのクレーム、ミドルウェアの入力）を並べている。
     残る3件は service の `__init__` で、依存（repository・ストレージ等）を個別に受け取り、設定値はキーワード専用で受け取る。
     引数をまとめる型を作っても列やクレーム・依存を写すだけの型になり、取り違えの防止にならない
   - `MapsService.__init__` だけは前4つが位置引数で、テストの約 40 か所が `MapsService(provider, 20, 20, 10, 8)` と書いている。
     本番の生成は `maps/dependencies.py` の1か所でキーワードで渡しているので今回は変えず、位置引数をキーワード専用にするか型にまとめるかは別の課題で判断する
10. **閾値は据え置く。**（SS-258 追補）片付けの後の実測（`src`・`scripts`。行単位の noqa の関数を除く）:

    | 閾値（複雑度・分岐・文・引数） | C901 | PLR0912 | PLR0915 | PLR0913 |
    |---|---|---|---|---|
    | 15・15・60・8（現在） | 0 | 0 | 0 | 0 |
    | 15・15・60・7 | 0 | 0 | 0 | 5 |
    | 15・15・60・6 | 0 | 0 | 0 | 17 |
    | 12・12・50・5 | 4 | 2 | 6 | 38 |
    | 10・12・50・5（ruff の既定） | 10 | 2 | 6 | 38 |

    - 複雑度の最大は 15（`strip_jpeg_metadata`・`instrument_fastapi_app`）、引数の最大は 8 で、どの閾値も1段下げると新しい違反が出る
    - 下げるなら決定5 のとおり違反を課題にして除外に載せる必要があり、片付けたばかりの除外を増やすことになる。
      次に下げる候補は、複雑度 12（違反4件: `strip_jpeg_metadata` 15、`instrument_fastapi_app` 15、`config._validate_environment_settings` 14、`PinService.add_photos` 13）と
      文の数 50（違反6件。5件はスレッドで競合を再現するテスト）。引数の数は違反が多く、既定の 5 は当面目指さない

### 影響

- `per-file-ignores` が無くなり、除外は関数の定義の行の noqa とコメントだけになった。一覧は `grep -rn "noqa: PLR09\|noqa: C901" src` で引ける
- 使われなくなった noqa は ruff の `RUF100` で検出できるが、今は足していない。既存の noqa に、有効にしていないルールのコード（`BLE001` など約 30 件）があり、それも検出されるため。
  足すなら、それらの noqa を消すか `lint.external` に載せる作業と一緒に行う
- `sanpo_maps/pins/service.py` は 792 行（main の SS-140 の型の対応を取り込んだ後）で、構造の検査の失敗（800 行。ADR-016）の手前にある。ADR-011 の持ち越し（写真確定処理の切り出し）の条件「約800行を超えたら」にも近い。
  このファイルに次に機能を足す課題では、先に写真確定処理（`_prepare_photos`・`_commit_photos`）を `photos/` の部品へ切り出す
- `maps/service.py` は分けたことで 484 → 514 行になり、構造の検査の警告（500 行）に入った。警告だけなので据え置いた。
  次に足すときは、候補の並列取得（`_fetch_loop_candidates`）を provider を引数で受ける別モジュールに出す
  （判定だけの純粋な `maps/loop_route.py` には入れない）。そのとき、候補ごとの警告ログのロガー名（`sanposcape.maps.service`）が変わらないよう名前を固定するかを決める
- `main.py` は登録の分割で 478 → 515 行になったので、例外ハンドラを `exception_handlers.py` に移した（`main.py` 200 行）

## SS-259 追補: mobile の除外の片付けとファイルごとの閾値のラチェット（2026-11-23）

### コンテキスト

SS-253 で `overrides` に据え置いた 15 ファイルを片付けた。backend（SS-258）と同じく、据え置きの間に除外していたファイルの関数は悪化していた
（`SanpoMapDetailView` の行 410 → 445、`usePinEdit` の複雑度 21 → 26、`WalkDetailView` の行 204 → 221、`PinDetailView` の依存 37 など）。

`features/sanpo-map/pin/components` の4画面（`PinDetailView`・`PinEditView`・`PinRegisterView`・`PinTabView`）は分けられない。
このフォルダは構造の検査（ADR-016）の baseline 32 ちょうどで、セクションの部品のファイルを足すと CI が落ちる。pin を下位の領域に分けるのは SS-275 の範囲。

### 決定

11. **SS-253 で据え置いた mobile の違反の片付け方**（SS-259 追補）
    - 画面は、表示の節（上端・本文・状態の案内・ダイアログ）のコンポーネントと、データと状態の判定の hook に分けた。
      例: `SanpoMapDetailView` → `useSanpoMapDetail`（地図・ピン・メンバー・削除の流れと本文の状態）・`SanpoMapDetailContent`（地図の情報とピン一覧）・`SanpoMapDetailStateCard`（地図を出さない状態の案内）。
      ほかに `SanpoMapListView`・`SanpoMapMembersView`・`WalkActiveView`・`WalkStartView`・`WalkDetailView`・`DesignSystemGallery`
    - hook は責務ごとの下位の hook（`usePinEdit` → `usePinEditSanpoMap`・`usePinEditTags`）か、同じファイルのモジュールの関数（`usePinPhotos` のキューの1件の処理）に分けた
    - 分岐の多い関数は表で引く形にした（`toPinSaveErrorCode`）。見た目の分岐は関数に出した（`Input`）
    - testID・文言・見た目・取得の挙動は変えない。画面の状態のうち、本文が作り直されても残すもの（地図詳細の絞り込みの語）は画面に残す
12. **分けられずに残す除外は、`off` ではなく、そのファイルの今の実測値を上限にした閾値（ラチェット）にする。**（SS-259 追補）
    - `overrides` でルールのオプションの `max` をそのファイルだけ上書きする（例: `PinRegisterView` は複雑度 31・関数の行 288・依存 30）。
      据え置きの間に悪化すると lint が落ちる（決定3 の「除外したファイルでは悪化を止められない」を、ファイルの単位で止める）
    - 値は上げない。分けて値が下がったら値を下げるか行を消す。コメントに片付ける課題（SS-282）と理由を書く（決定3 と同じ）
    - 行単位の `oxlint-disable-next-line`（backend の決定8 の形）には寄せない。`import/max-dependencies` はファイルの単位のルールで行に結べず、
      残すものは片付け待ちのファイルで、恒久に分けない関数ではないため。恒久に分けない関数が出たら、行単位の抑止と理由のコメントにする
    - 恒久の除外（決定4。テストの関数の長さ・`iconRegistry.ts` の依存の数）は `off` のまま
13. **閾値は据え置く。**（SS-259 追補）片付けの後の実測（`src`・`app`。ピンの4画面を除く）:

    | 閾値（複雑度・関数の行・依存・深さ） | complexity | max-lines-per-function | max-dependencies | max-depth |
    |---|---|---|---|---|
    | 20・200・20・4（現在） | 0 | 0 | 0 | 0 |
    | 18・180・18・4 | 2 | 4 | 4 | 0 |
    | 15・150・15・3 | 7 | 12 | 11 | 6 |
    | 12・120・12・4 | 20 | 23 | 20 | 0 |

    - 1段（18・180・18）下げても10件出る。今回分けた画面（`SanpoMapListView` 194 行・依存 20、`WalkActiveView` 依存 20、`WalkDetailView` 186 行）が閾値の手前にあり、
      ほかは `TagListView` 194 行・`SettingsView` 依存 20・`createSessionAuthService.doRefresh` 複雑度 19・`PinTabView` 183 行・複雑度 19
    - ピンの4画面を片付けた後（SS-282）に、もう一度測って判断する

### 影響

- `.oxlintrc.json` の SS-253 由来の据え置きは、ピンの4画面のファイルごとの閾値だけになった。一覧は `.oxlintrc.json` の末尾の overrides
- 画面を分けたことで `features/sanpo-map/map/components` は 19 ファイルになり、構造の検査の上限（20）の手前にある。
  次にこのフォルダへ部品を足す課題では、地図の領域を下位（一覧・詳細・メンバーなど）に分けるかを先に決める
- ファイルごとの閾値の行は、片付けで値が下がっても oxlint は教えない（決定3 の消し忘れと同じ）。片付けた PR で値を下げるか行を消す
