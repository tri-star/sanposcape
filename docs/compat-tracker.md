# 互換性台帳

配布済みのアプリ・稼働中の backend のために残しているもの（フラグ、非推奨の API、後で必須にする項目、後で NOT NULL にする列・消す列）と、
**いつ片付けてよいか**を1行ずつまとめる（SS-233、[ADR-008](./adr/ADR-008-deploy-release-separation.md) の SS-233 追補 D41）。

- mobile・backend とも任意のタイミングで本番にデプロイしてよい。そのたびに公開済みのアプリへ影響を出さないよう、フラグか互換の維持で吸収する
  （ADR-008 決定1・2・7、[リリース運用手順](./release-runbook.md) §7）。互換のために残したものは、条件を満たしたら片付ける。
  残したことを忘れると、分岐と古い経路が積み上がる。
- **守る範囲**は、iOS・Android それぞれの本番の最低サポートバージョン以上（上げてから1日の間は、上げる前の値以上）の version で、ストアの審査に提出したビルド（審査中・公開待ち・公開中・過去に公開した版。審査で却下されたもの・取り下げて公開しなかったものは除く）。
  埋め込みの JS と、その version に配ったすべての OTA を含む。TestFlight だけのビルド（外部テスターへの配布を含む）は守らない。
  最低サポートバージョンが `null` の間は、審査に提出したすべてのビルドを守る。`/app-config` のエンドポイントと、案内の判定に使う部分（応答の形・`minimum_supported_versions`）は版に関わらず互換を保つ（フラグのキーの削除は D40 に従う）（ADR-008 SS-233 追補 D43）。
- この台帳は**今の状態の一覧**で、決定の記録ではない。なぜ残すかの判断は ADR に書き、ここからリンクする。
- プライバシーポリシー・App Privacy の申告に残している古いアプリの挙動の記述は、[データ取扱い台帳](./privacy/data-inventory.md)の
  「6. 古いアプリのための記述（contract 待ち）」が正本で、ここには写さない。

## 1. いつ見るか・いつ書くか

| いつ | やること |
|---|---|
| 計画（`task-workflow` のプランの「配布済みアプリとの互換」） | 互換のために何かを残すなら、この台帳に行を足すことを影響範囲に含める |
| フラグを本番で ON にした後 | mobile が見るフラグなら行を足す（この時点から削除に2段階が要る。2.1） |
| 最低サポートバージョンを上げるとき（runbook §7.3） | 「最低サポートバージョン」が条件の行を見て、上げてから1日経ったら、満たした行を片付ける。データ取扱い台帳 6 も見る |
| backend を全環境にデプロイ・migrate したとき | 「全環境の backend」が条件の行を見る |
| 片付けたとき | 行をこの表から外す（経緯は課題・PR に残す） |

## 2. 片付けてよい条件の種類

- **最低サポートバージョン**: 配布済みのアプリが原因で残すもの。iOS・Android の最低サポートバージョンが、古い挙動を持たないコードを
  **ストアのバイナリに埋め込んだ**最初の version 以上になり、本番で上げてから1日経った後（ADR-008 決定7、SS-233 追補 D43）。
  1日待つのは、散歩中と未保存の散歩を保存できる間は、最低サポートバージョン未満でもアップデートの案内が出ないため（ADR-008 D31）。
  24時間近い散歩や、サマリ画面に置いたままの散歩は例外で、1日を過ぎても待たない（ADR-008 D43）。
  OTA で直した JS を届けた version は数えない（OTA を当てていない端末や、埋め込みの JS へ戻した端末に古い挙動が残るため）。
  - 対象: mobile が見るフラグの固定値、非推奨のエンドポイント・フィールド、リクエストの任意の項目の必須化、応答のフィールドの削除・意味の変更
  - 最低サポートバージョンは人が決め、フラグ切り替えワークフローの入力で変える（[リリース運用手順](./release-runbook.md) §7.3、ADR-008 SS-271 追補 D44）。上げるかを決める材料（バージョン別の利用状況）の出どころも決めていない（ADR-008 SS-233 追補の未解決）。
- **全環境の backend**: 稼働中の古い backend が原因で残すもの。片付けの前提になる変更が dev・prod の両方にデプロイされ、マイグレーションが流れた後。
  - 対象: 列の NOT NULL 化・古い列の削除（runbook §7.4）、backend だけが見るフラグ
- 条件が「既に満たしている」行は、片付けの課題を起こせば消せる。

### 2.1 mobile が見るフラグの片付け方

mobile は `/app-config` の未知のキーを OFF として扱うため、backend がキーを返さなくなると、配布済みのアプリではそのキーで出し分けている機能が消える。
そのため2段階で消す（ADR-008 SS-233 追補 D40。手順は runbook §3「フラグを追加する / 削除する」）。

1. **フラグの削除**: backend の分岐と `feature-flags.json` のキーを消し、登録簿ではキーを固定値 `true` を返すキーに移す（AppConfig の取得の状態に関わらず返す）。
   mobile の分岐・キー定数・テストも消してよい。この台帳の行の「状態」を「固定値で返している」にし、条件のバージョンが決まったら書く。
   この行がある間は、どのフラグの切り替えでも `prune` を付けない。`prune` は定義ファイルに無いキーをまとめて消すので、別のフラグのための `prune` でもこのキーの値が消え、
   段階1 より前の backend へ戻したときに機能が消える（runbook §3）。
2. **固定値の削除**: 最低サポートバージョンが、分岐を消したコードを**ストアのバイナリに埋め込んだ**最初の version 以上になり、上げてから1日経ったら、固定値を消して行を外す。他に「固定値で返している」行が残っていなければ、AppConfig の値を `prune` する。
   OTA で分岐の無い JS を届けた version は数えない（OTA を当てていない端末や、埋め込みの JS へ戻した端末に分岐が残るため）。

本番で現在 OFF のフラグ（一度も ON にしなかった・OFF に戻して廃止する）と、backend だけが見るフラグは1段階で消す。
