# マイルストーン計画: sanposcape

> 作成日: 2026-07-19
> 対象範囲: MVP達成まで

## マイルストーン一覧

```
M1 ─────► M2 ─────► M3 ─────► M4 ─────► M5 ─────► MVP 達成
基盤整備   デザイン/UI基盤  認証・骨格   探索・散歩開始  記録・履歴
```

> MVPフロー: スプラッシュ → サインイン/サインアップ → 散歩開始（往復時間内スポット検索・選択で開始）→ 散歩中の状況表示 → 散歩終了（歩いたルートの記録）→ 散歩履歴。加えてログアウト・アカウント削除。

---

- **期間目安:** 立ち上げ期

  - [ ] モノレポ（pnpm workspace）と packages/backend・packages/mobile が構成されている
  - [ ] backend が Docker Compose で起動し、ローカルDB・テスト用DBが分離されている
  - [ ] backend が OpenAPI(openapi.yaml) を出力でき、pytest が実行できる

  - [ ] Orval で OpenAPI から APIクライアント + MSWモックが生成できる
  - [ ] oxlint/oxfmt(mobile)・ruff(backend) と GitHub Actions CI が動く
  - [ ] Maestro による E2E が実行できる土台がある

## M2: デザイン取り込み・UI基盤

- **目的:** 実装を本格化する前に、Claude Design からデザインをインポートしてアプリのUI基盤を作る。デザイントークンを Unistyles のテーマとして整備し、MVPフローの主要画面を（データ結線前の）静的な状態で先行実装する。以降のマイルストーンは、ここで用意した画面へロジック/APIを結線していく形にする。
- **期間目安:** 基盤第2弾
- **完了条件:**
  - [ ] Claude Design からデザインをインポートし、UI基盤の土台にできる
  - [ ] デザイントークン（primitive / semantic）を Unistyles のテーマとして整備している
  - [ ] 横断利用する共通UIコンポーネント（Button・Text・Card・Input 等）がデザインに沿って実装されている
  - [x] MVPフローの主要画面（スプラッシュ / サインイン / サインアップ / 散歩開始 / 散歩中 / 散歩終了 / 履歴）が静的（スタブデータ）で表示できる
  - [x] Expo Router のルーティングで各画面へ遷移できる（ロジックは仮）

### 含まれるタスク（概要レベル）

| # | タスク概要 | 備考 |
| --- | --- | --- |
| 1 | Claude Design からのインポート・デザイントークン整備 | Unistyles theme（primitive/semantic） |
| 2 | 共通UIコンポーネント実装 | src/components/ui |
| 3 | MVP主要画面の静的実装・ルーティング配線 | app/ + src/features/*、UIとロジックは分離を維持 |
| 4 | スタブデータでの画面表示確認 | development build + `/dev-screens`（画面カタログ）でユーザーが確認 |

### 依存関係・前提

- M1 が完了していること

### リスク・懸念事項

- デザイントークンと Unistyles テーマのマッピング粒度（primitive/semantic の切り分け）。
- 画面数が多く、静的実装の範囲（どこまで作り込むか）を M3 以降の結線とのバランスで見極める必要がある。
- 画面を先行実装しても「UIとロジックの分離」を崩さない（app/ を薄く保ち、features 側に寄せる）。

## M3: 認証・アプリ骨格

- **目的:** MVPフローの入口である「スプラッシュ → サインイン/サインアップ → （認証後）ホーム」の骨格と、ログアウト・アカウント削除を通す。M2で用意した画面に認証ロジックを結線し、外部API（Google Maps）に依存しない範囲で認証の縦通しを先に固める。
- **期間目安:** コア第1弾
- **完了条件:**
  - [ ] スプラッシュ画面で認証状態を判定し、遷移を振り分けられる
  - [ ] Auth0 によるサインアップ / サインイン（mobile OIDC / backend 検証）が動作する

  - [ ] アカウント削除（mobile操作 → backend削除API → 関連データ削除）ができる
  - [ ] 認証は services 層で real/stub 切り替え可能で、ユニット/E2Eが通る

## M4: 探索・散歩開始

- **目的:** 「往復できる範囲のスポット検索 → スポット選択で散歩開始 → 散歩中の状況表示」という本アプリの中核体験を実装する。M2で用意した探索・散歩画面にロジックとGoogle Maps連携を結線する。
- **期間目安:** コア第2弾
- **完了条件:**
  - [ ] 現在地取得と地図表示（react-native-maps）ができる
  - [ ] 「往復◯分」指定でスポット候補を地図・リスト表示できる
  - [ ] スポットを選択して徒歩ルートを提示し、散歩を開始できる
  - [ ] 散歩中の状況（現在地・経過時間・目的地/ルート）を表示できる
  - [ ] Google Maps Platform 連携は backend 経由（キャッシュ/プロキシ層）で行う
  - [ ] 探索・開始・散歩中のロジックが認証に不可分に依存しない構成になっている

### 含まれるタスク（概要レベル）

| --- | --- | --- |
| 1 | backend: Places/Routes プロキシ・キャッシュ層 | コスト/レート対策 |
| 2 | mobile: 地図表示・往復範囲指定UI・候補表示 | features/walk |

## マイルストーン順序の設計方針

このプロジェクトでは以下の方針に基づきマイルストーンの順序を決定しています:

1. **開発基盤の早期整備** — CI/CD・Lint/Format・Orval連携・services層のスタブ差し替え機構を M1 で前倒しし、後続全体に効かせる。
2. **UI基盤を先に固める** — 実装本格化の前に M2 で Claude Design からデザインを取り込み、デザイントークン（Unistyles）とMVP主要画面を静的に用意する。以降のマイルストーンは「既にある画面へロジック/APIを結線する」形にでき、UIとロジックの分離も保ちやすい。
3. **入口から縦に通す** — MVPフローの入口である認証（外部の地図APIに依存しない）を M3 で先に縦通しし、以降の全画面が乗る土台を固める。
4. **コア体験を段階実装** — 地図/外部API連携が必要な「探索・散歩開始（M4）」と「記録・履歴（M5）」を分割し、動く範囲を段階的に広げる。
5. **将来のゲスト散歩を意識** — 認証はMVPの必須ゲートだが、探索・散歩ロジックを認証から分離し、後から「記録なしゲスト散歩」を足せる余地を残す。
