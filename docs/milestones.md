# マイルストーン計画: sanposcape

> 作成日: 2026-07-19
> 対象範囲: MVP達成まで

## マイルストーン一覧

```
M1 ─────► M2 ─────► M3 ─────► M4 ─────► M5 ─────► MVP 達成
基盤整備   デザイン/UI基盤  認証・骨格   探索・散歩開始  記録・履歴
```

> MVPフロー: スプラッシュ →（保存済みセッションがない場合はサインイン/サインアップ）→ 散歩開始（往復時間内スポット検索・選択で開始）→ 散歩中の状況表示 → 散歩終了（歩いたルートの記録）→ 散歩履歴。加えてログアウト・アカウント削除。

## M5: 散歩記録・履歴

- **目的:** 散歩終了時に歩いたルートを記録し、履歴として振り返れるようにして MVP を達成する。M2で用意した履歴・終了画面にロジックとbackendを結線する。
- **期間目安:** MVP達成
- **完了条件:**
  - [x] 散歩終了時に実際に歩いたルート（軌跡・所要時間・距離）を保存できる（backend API は SS-18、mobile 結線は SS-19 で完了）
    - 留保: 保存はメモリ上のドラフトを終了直後に送る方式で、**保存が確定する前にアプリが強制終了されると記録は失われる**（ローカル永続化は SS-19 スコープ外。フォローアップ課題へ）
  - [x] 保存した散歩がユーザーに紐付く（backend は SS-18 で完了。`walks.user_id` + `ON DELETE CASCADE`、repository の全メソッドが `user_id` 必須。mobile は SS-19 で認証付きの `POST /walks` を結線）
  - [x] 散歩履歴の一覧・詳細を閲覧できる（backend API は SS-18、mobile 結線は SS-20 で完了。`/walk-history`・`/walk-history/[walkId]` + 記録タブの「最近の散歩」）
    - 実績（SS-42）: 記録タブの集計表示（週/月チャート・合計距離・連続日数・今日の歩数）を実データ化した。backend に集計 API `GET /walks/stats`（JST 固定。今日 / 直近7日=1日×7バケット / 直近28日=7日×4バケット + `streak_days`）を新設し、mobile の `useHistorySummary` が `queryKey: ["walks","stats"]` で参照する（ADR-003 決定10〜12）。streak は非正規化カラムを持たずサーバーのクエリで算出する形で決着し（決定11）、歩数は API に持たせず mobile が距離から歩幅 0.7m で推定して UI に「推定」と明示する（決定12）
    - 留保: 目標歩数（`features/history/data/stepGoal.ts` の 8,000 歩）はスタブのまま。目標歩数のユーザー設定は別課題。期間フィルタ（`started_after`/`started_before`）は集計を専用 API に一本化したため使わない方針（ADR-003 決定10）
    - 実績（SS-29）: 記録タブのユーザー名は認証セッション（`useAuthSessionStore.user.displayName`）から供給するようになり、静的スタブ（`data/profile.ts`）は廃止した。あいさつ文は `app/(tabs)/history.tsx` → `HistoryView` → `useHistorySummary` の経路で表示名を受け取り、`features/history/lib/greeting.ts` の純粋関数が組み立てる。
    - 実績（SS-53）: 削除 API `DELETE /walks/{walk_id}` を追加した。物理削除・成功時 204・削除済み ID への再送は404（冪等にしない、ADR-003 決定13）。他ユーザーの散歩・存在しない ID はいずれも 404 で区別しない（決定6と同じ扱い）。
    - 実績（SS-60）: mobile の削除導線を実装した。履歴詳細画面（`/walk-history/[walkId]`）のヘッダーのゴミ箱アイコン → 取り消し不能であることを伝える確認ダイアログ → 削除 → 履歴一覧へ `replace` で遷移する。DELETE の 404 は「既に削除済み」として成功扱いにし（`features/history/api/walkDeleteApi.ts`）、成功時は `invalidateQueries({ queryKey: ["walks"] })` で一覧・詳細・集計をまとめて更新したうえで、削除した個票は `removeQueries({ queryKey: ["walks","detail",id], exact: true })` で捨てる（`useWalkDetail` の `staleTime` が1時間のため）。保存待ちドラフトは `src/lib/walkDeletionCleanup.ts` のレジストリ経由で `savedWalkId` 一致時のみ破棄し、同じ `client_walk_id` の再送で削除した散歩が復活しないようにしている（ADR-003 決定13 の申し送り）。**一覧側（`/walk-history`・記録タブの「最近の散歩」）からの削除は非スコープ**（受け入れ条件が「履歴詳細から削除を開始できる」に限定されているため）。削除フローの E2E（Maestro）は追加していない（dev ユーザーが `e2e-user-1` 固定の共有アカウントで、取り消し不能な削除が他フローと干渉するため）。

## マイルストーン順序の設計方針

このプロジェクトでは以下の方針に基づきマイルストーンの順序を決定しています:

1. **開発基盤の早期整備** — CI/CD・Lint/Format・Orval連携・services層のスタブ差し替え機構を M1 で前倒しし、後続全体に効かせる。
2. **UI基盤を先に固める** — 実装本格化の前に M2 で Claude Design からデザインを取り込み、`src/theme` のデザイントークンとMVP主要画面を静的に用意する。以降のマイルストーンは「既にある画面へロジック/APIを結線する」形にでき、UIとロジックの分離も保ちやすい。
3. **入口から縦に通す** — MVPフローの入口である認証（外部の地図APIに依存しない）を M3 で先に縦通しし、以降の全画面が乗る土台を固める。
4. **コア体験を段階実装** — 地図/外部API連携が必要な「探索・散歩開始（M4）」と「記録・履歴（M5）」を分割し、動く範囲を段階的に広げる。
5. **将来のゲスト散歩を意識** — M3 の認証実装（SS-13）時点では認証を必須ゲートとしつつ、探索・散歩ロジックを認証から分離し、後から「記録なしゲスト散歩」を足せる余地を残す設計にした。この余地は SS-49（backend合意）・SS-56（backend実装）・SS-57（mobile実装）で実際に使われ、ゲスト散歩は実装済み（記録の保存・履歴・統計のみ認証必須）。
