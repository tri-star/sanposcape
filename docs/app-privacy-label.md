# App Store の App Privacy（プライバシー栄養ラベル）の申告内容

App Store Connect の「App のプライバシー」に入力する内容と、その根拠をまとめる（SS-159）。
入力はこの文書を正本として手作業で行う。App Privacy の回答は App Store Connect からいつでも更新でき、
アプリの更新（審査）は要らない。
実装の事実（何をどこへ送り、どこに保存するか）の正本は[データ取扱い台帳](./privacy/data-inventory.md)で、この文書は台帳から書く。

> ⚠️ **成熟度（2026-10-19 時点）**: App Store Connect に入力済み（SS-215）。
> 入力時に画面の項目名・選択肢がこの文書と違った記録は無い。次に更新するときに違いに気づけば、この文書を訂正すること。

## 1. 前提: Apple の定義の要点

出典: [App privacy details on the App Store](https://developer.apple.com/app-store/app-privacy-details/)

- **収集（collect）**: データを端末の外へ送り、リクエストへの応答に必要な時間より長く、
  運営者または第三者パートナーが読める形で保持すること。送って処理後すぐ捨てるもの、端末の中だけで処理するものは対象外。
- **ユーザーに紐づく（linked）**: 収集前に匿名化などの措置をしていなければ、原則として紐づく扱い。
  法令上の個人情報は紐づく扱いになる。
- **トラッキング**: 収集したデータを他社のデータと結び付けて広告のターゲティング・効果測定に使うこと、
  またはデータブローカーに渡すこと。
- **第三者パートナー**: アプリに組み込んだ SDK などが収集するデータも申告する。**Apple（MapKit など）が収集するデータは申告不要**。
- **IP アドレス**: 使い方に応じて、該当するデータの種類（位置、デバイス ID、診断など）として申告する。

## 2. 申告内容（App Store Connect に入力するもの）

### 2.1 全体の回答

| 質問 | 回答 |
| --- | --- |
| このアプリでデータを収集しますか | **はい** |
| トラッキングに使うデータがありますか | **いいえ**（すべてのデータの種類で「トラッキングに使用しない」） |
| プライバシーポリシーの URL | `https://sanposcape.com/privacy/` |
| ユーザーのプライバシー選択の URL（任意） | `https://sanposcape.com/privacy/#delete`（削除方法の節） |

### 2.2 データの種類ごとの回答

「目的」の略記: **機能** = App Functionality（アプリの機能）、**分析** = Analytics（分析）。
「出どころ」は 3.1 の根拠の区別で、App Store Connect には入力しない（入力するのはデータの種類ごとの合算）。

| カテゴリ | データの種類 | ユーザーに紐づく | トラッキング | 目的 | 出どころ |
| --- | --- | --- | --- | --- | --- |
| 連絡先情報 | 名前 | はい | いいえ | 機能 | 運営者、Google SDK |
| 連絡先情報 | メールアドレス | はい | いいえ | 機能 | 運営者、Google SDK |
| 連絡先情報 | 電話番号 | はい | いいえ | 機能 | Google SDK |
| 健康とフィットネス | フィットネス | はい | いいえ | 機能、分析 | 運営者 |
| 位置情報 | 正確な位置情報 | はい | いいえ | 機能、分析 | 運営者 |
| 位置情報 | おおよその位置情報 | はい | いいえ | 機能 | Google SDK |
| ユーザコンテンツ | 写真またはビデオ | はい | いいえ | 機能 | 運営者 |
| ユーザコンテンツ | その他のユーザコンテンツ | はい | いいえ | 機能、分析 | 運営者 |
| ID | ユーザ ID | はい | いいえ | 機能、分析 | 運営者（機能）、Google SDK（機能・分析） |
| ID | デバイス ID | はい | いいえ | 機能、分析 | Expo（機能・紐づかない）、Google SDK（分析・紐づく） |
| 使用状況データ | その他の使用状況データ | はい | いいえ | 分析 | Google SDK |
| 診断 | クラッシュデータ | いいえ | いいえ | 機能 | Expo |
| 診断 | パフォーマンスデータ | はい | いいえ | 機能、分析 | 運営者 |
| 診断 | その他の診断データ | はい | いいえ | 機能、分析 | 運営者 |
| その他のデータ | その他のデータタイプ | はい | いいえ | 機能、分析 | Google SDK |

上の表に無いデータの種類は、すべて「収集しない」。
同じデータの種類を複数の出どころが収集する場合は、目的を合算し、どれか 1 つでも紐づくなら「紐づく」と答える。

## 3. 根拠

### 3.1 申告するもの

#### 運営者（backend・アクセスログ）が収集するもの

| データの種類 | 実際のデータ | 根拠（実装） | ポリシー |
| --- | --- | --- | --- |
| 名前 | Google から受け取る表示名、または Apple のサインイン時に端末から受け取る氏名（`users.display_name`） | `auth/providers/google.py`、`auth/providers/apple.py`、`auth/schemas.py`、`users/service.py`、`users/models.py` | 1-2 |
| メールアドレス | Google / Apple から受け取るメールアドレス（`users.email`。Apple は非公開リレーのアドレスの場合がある）。重要なお知らせの連絡にも使うが、マーケティングには使わない | 同上 | 1-2、2 |
| フィットネス | 散歩の記録の歩いた時間・距離（`walks.duration_seconds` / `distance_meters`）。Motion & Fitness API・HealthKit は使っていないが、運動の記録にあたるため申告する | `walks/models.py` | 1-1 |
| 正確な位置情報 | 散歩の軌跡（小数 6 桁）、目的地の座標、ピンの座標。ピン地図の表示範囲（小数 4 桁）は `GET /pins` のクエリに載るため、CloudFront のアクセスログに残りうる。Apple の定義では小数 3 桁以上は「正確」。なお、スポット・ルート検索の現在地（小数 4 桁 ≒ 11m）と、ピン名の初期値に使う住所を引くためのピンの座標（SS-138。Google Geocoding API へ送る）は POST のボディで送り、サーバーのメモリに数分（既定 300 秒）キャッシュするだけで、DB にもログにも残らない | `walks/models.py`、`sanpo_maps/models.py`、mobile の `walkTrackPayload.ts` / `pinFetchBounds.ts` / `placeSearchRequest.ts`、backend の `config.py`（キャッシュの TTL） | 1-1、1-5 |
| 写真またはビデオ | ピンに添付する写真（S3）と、写真に付随する撮影日時（`pin_photos.taken_at`。SS-163）。Google のプロフィール画像の URL（`users.photo_url`）もここに含める | `sanpo_maps/photos/`、`users/models.py` | 1-2、1-3 |
| その他のユーザコンテンツ | ピンの名称・メモ・タグ、地図（sanpo map）の名称 | `sanpo_maps/models.py`、`pins/schemas.py` | 1-3 |
| ユーザ ID | Google / Apple アカウントの ID（`users.provider_subject` = sub）、アカウントの内部 ID（`users.id`） | `users/models.py` | 1-2、1-5 |
| パフォーマンスデータ | CloudFront のアクセスログの処理時間（IP アドレスと同じ行に残る）、backend のトレースの処理時間（トレースは IP・UA を消している。アカウントの内部 ID を `enduser.id` として持つ。アプリの起動ごとの乱数を `session.id` として持つ受け口もあるが、mobile はまだ `X-App-Session-Id` を送っていない。SS-181） | `core/tracing.py`、`core/logs.py`、`core/access_log.py`、`aws_lambda/tracing.py`、ADR-013 | 1-5 |
| その他の診断データ | backend のログ（アカウントの内部 ID を含む行がある。アプリの起動ごとの乱数のセッション ID の受け口もあるが、mobile はまだ送っていない）、CloudFront のアクセスログ（IP アドレス、URL、ブラウザ・アプリの種類）。最長 400 日保存 | `core/logs.py`、`core/access_log.py`、`template.yaml`（ロググループの保持期間）、ADR-005（アクセスログ S3 は infra 所有） | 1-5、6 |

「紐づく」は、アカウント（内部 ID）と結び付けて保存しているため。診断データも、ログにアカウントの内部 ID や IP アドレスが含まれるため「紐づく」とする。

#### 第三者 SDK が収集するもの

Apple の定義では、アプリに組み込んだ SDK が収集するデータも申告する。各 SDK の申告はその SDK の
プライバシーマニフェスト（`PrivacyInfo.xcprivacy` の `NSPrivacyCollectedDataTypes`）で確認する。

| SDK | 収集するデータ | 根拠 | ポリシー |
| --- | --- | --- | --- |
| Google Sign-In for iOS（`GoogleSignIn` ~> 9.0。`react-native-nitro-google-signin` の podspec が依存する） | マニフェストの申告どおり、すべて「紐づく」「トラッキングしない」: 名前（機能）、メールアドレス（機能）、電話番号（機能）、その他のデータタイプ（機能・分析）、おおよその位置情報（機能）、ユーザ ID（機能・分析）、デバイス ID（分析）、その他の使用状況データ（分析） | [GoogleSignIn-iOS の PrivacyInfo.xcprivacy](https://github.com/google/GoogleSignIn-iOS/blob/9.0.0/GoogleSignIn/Sources/Resources/PrivacyInfo.xcprivacy)（2026-10-10 に 9.0.0 と main が同一であることを確認） | 1-7、3（Google でサインインの行） |
| expo-updates（`app.json` の `updates.url` で本番ビルドでも有効） | 更新を確認するリクエストのヘッダー: インストールごとのランダムな ID（`EAS-Client-ID`）→ デバイス ID（機能・紐づかない）。前回の起動時の致命的なエラーのメッセージ（`Expo-Fatal-Error`、最大 1024 文字）→ クラッシュデータ（機能・紐づかない）。Expo がこれらを保持するかは公開情報で確認できないため、保守的に申告する | `expo-updates` の `FileDownloader.swift` / `FileDownloader.kt`、[Expo: Privacy explained](https://expo.dev/privacy-explained) | 1-7、3（Expo の行） |
| react-native-maps（iOS は Apple MapKit） | マニフェストで正確な位置情報（紐づかない）を申告している。運営者の「正確な位置情報（紐づく）」に含まれる。MapKit 自体が収集するデータは Apple のため申告不要 | `react-native-maps` の `PrivacyInfo.xcprivacy` | 3（Apple Inc.: マップの行） |
| expo-apple-authentication（iOS の AuthenticationServices。SS-199） | プライバシーマニフェストを持たない。認可のシートは Apple のフレームワークで、Apple が収集するデータは申告不要（1. の前提）。アプリが受け取る氏名・メールアドレス・ユーザ ID は運営者の収集として上の表に含めている | expo-apple-authentication のパッケージ（PrivacyInfo.xcprivacy が無い） | 1-2、3（Apple Inc.: Apple でサインインの行） |

### 3.2 申告しないもの

| データの種類 | 申告しない理由 |
| --- | --- |
| 検索履歴 | アプリから検索語を送っていない。`GET /pins` の `q` / `tags` は API にあるが、mobile で `GET /pins` を呼ぶ `pinFetchBounds.ts` と `sanpoMapPinList.ts` のどちらも送らない。スポット探索の条件は POST のボディで送り、DB にもログにも残さない（メモリに数分キャッシュするだけで、利用者の識別子と結び付けない） |
| 認証トークン | セッションのトークンは、サーバーには照合用のハッシュだけを保存し、読める形で保持しない。Apple でサインインした場合の Apple の refresh token は平文で保存する（アカウント削除時に Apple で失効させるため。ADR-002 の SS-198 追補）が、利用者についての情報ではなく Apple の定義のデータの種類に当たらない。ポリシーには 1-4・9 に書いている |
| 製品の操作（Product Interaction） | アクセス解析のツールを組み込んでいない。backend のアクセスログはリクエスト単位の記録で、診断データとして申告している（Google SDK の利用状況は「その他の使用状況データ」として申告している） |
| 広告データ・購入履歴・財務情報・連絡先・健康・機密情報・音声・閲覧履歴など | 該当する機能が無い（マイクの権限も要求しない）。組み込んだ SDK のマニフェストにも無い |

### 3.3 判断が分かれたもの

| 論点 | 判断 | 理由 |
| --- | --- | --- |
| 第三者 SDK のマニフェストの申告をそのまま取り込むか | 取り込む | Apple の定義で SDK の収集も申告対象。Google Sign-In が電話番号・おおよその位置情報などを申告している理由は公開されていないが、マニフェストに反する申告をすると、Xcode のプライバシーレポートとラベルが食い違う |
| 運営者の収集に「分析」の目的を付ける範囲 | 正確な位置情報・フィットネス・その他のユーザコンテンツ・診断データ | ポリシーの「2. 利用目的」に「本アプリの改善や新しい機能の開発」「統計情報の作成」があり、Apple の Analytics は「機能の効果の把握・新機能の計画・利用者の規模の把握」を含む。想定している集計は、散歩の回数・距離・地域の傾向、ピンの登録数・タグの傾向、API のルート別の利用量と処理時間で、これらに使うデータの種類に付けた。名前・メールアドレス・写真は集計に使わないので付けない。ユーザ ID は Google SDK の分の「分析」が付く |
| フィットネスを申告するか | 申告する | 散歩の時間と距離は運動の記録にあたる。位置情報から算出した値で、Motion & Fitness API は使っていない（`NSMotionUsageDescription` の文言どおり）が、データの種類としては該当する |
| ピン・写真を申告するか | 申告する | ピンの登録（写真の添付を含む）は `pin_registration` フラグの裏にあり既定 OFF だが、フラグはアプリの更新なしに ON にできる（`packages/backend/feature-flags.json`）。写真については、プロフィール画像の URL も保存している |
| Expo の送信を申告するか | デバイス ID・クラッシュデータ（いずれも紐づかない）として申告する | Expo が保持するかを公開情報で確認できない。ポリシーの外部サービスの表にも書いており、申告しないとポリシーと食い違う。Expo が保持しないと確認できたら外してよい |
| 問い合わせのメール（`support@sanposcape.com`）を「カスタマーサポート」として申告するか | 申告しない（SS-220） | Apple の申告は「この App から収集」するデータが対象。問い合わせは利用者のメールソフトから届く。アプリには問い合わせの画面も mailto も無く、アプリから開けるのはブラウザで表示するプライバシーポリシー・利用規約のページ（`packages/mobile/src/config/legalLinks.ts`）で、窓口のアドレスはそこに載っているだけ。取得・保存期間・削除はポリシー 1-6・6・7 に書いている。アプリ内にフォームや窓口への導線を足すときは、Apple の任意の開示の条件（アプリの画面で毎回利用者が選んで送る、など）に当たるかを確かめ、当たらなければ「その他のユーザコンテンツ > カスタマーサポート」を申告する |

## 4. 入力手順

1. App Store Connect でアプリを開き、「App のプライバシー」を選ぶ
2. 「プライバシーポリシー」に `https://sanposcape.com/privacy/` を入力する（「ユーザーのプライバシー選択」は任意）
3. 「はじめに」から、データを収集するかに「はい」と答える
4. 2.2 の表のデータの種類にチェックを入れて保存する
5. データの種類ごとに、2.2 の表のとおり目的・ユーザーに紐づくか・トラッキングを答える
6. プレビューを確認して「公開」する（審査とは別に公開できる）

## 5. 見直すタイミング

次のいずれかを変えたら、[データ取扱い台帳](./privacy/data-inventory.md)を直したうえで、この文書と App Store Connect の回答、[プライバシーポリシー](../packages/lp/src/pages/privacy.astro)の 3 つを揃えて更新する。
どの変更が対象になるか（対象パス）は台帳の「1. 対象パス」にある。

- 新しく保存・送信するデータを増やす（例: ピンの検索 UI を付けて検索語を送る → 検索履歴を申告する）
- SDK を足す（クラッシュ解析・アクセス解析・広告など）。SDK が収集するデータも申告対象になる
- データを他の利用者と共有する機能を作る（地図の共有など）
- データを広告・マーケティングに使う、または他社のデータと結び付ける（トラッキングの回答が変わる）

## 6. この文書の対象外

- **Google Play の「データ セーフティ」**: 項目の分け方が App Store と違うため、別に整理する。Android は地図に Google Maps SDK を使うので、App Store にない申告が要る。
- **プライバシーマニフェスト（`PrivacyInfo.xcprivacy`）**: アプリのビルドに含めるファイルで、App Privacy の回答とは別物。
  `app.json` に `ios.privacyManifests` の設定は無い。
