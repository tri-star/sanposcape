# mobile PRの確認証拠

task-workflowのPR作成・review-fixのpush後、または明示的な依頼で使う。PR番号、対象コミット、課題の作業ディレクトリを照合する。

1. PR全体はbaseとのmerge-baseから、review-fixはpush前後のコミット範囲から画面変更を判定する。mobileのapp、tsx、theme、design/tokens、assetsが対象。テストと生成APIは除外する。tsだけでも表示や画面遷移を変えるなら対象とし、理由を残す。対象外なら画面変更なしと報告して終える。
2. [端末確認](device-verification.md) と [起動ガイド](../../../../packages/mobile/docs/app-startup-guide.md) で実際の環境を確認する。adb等の接続・権限エラーは結果から診断し、Claude固有のsandbox解除指定を引き継がない。必要な権限が得られなければ理由を報告する。
3. 対象HEADのコードが配信されていることを確認し、変更した画面の通常・空・エラー・ダイアログ等の関連状態を操作する。fake/mockと実APIの確認を区別する。画面と操作・期待値・結果を作業ディレクトリに残し、取得した画像は画像表示ツールで確認する。オーバーレイ、トークン、メール、実在の位置情報を含む画像は掲載しない。
4. 外部投稿が依頼範囲に含まれる場合だけ、対象PRへ確認結果のコメントと画像を添付する。`gh pr comment --help` で `--attach` の有無を確認して使う。本文はファイルから渡し、画像は絶対パスで指定する。対象コミット・端末/AVD・backendのモード・操作と結果・未確認状態を記載する。NGも成功に読み替えない。
5. 失敗・タイムアウト時はコメントと添付の有無を再取得し、作成済みなら重複投稿せず欠落分だけを扱う。再試行は1回まで。コメントURL、画像枚数、結果または省略理由を報告する。画像は投稿成功を確認するまで保持する。

端末確認とPR添付は別の検証。ghの添付非対応なら画像をローカルに保持して添付未実施と報告し、それだけを理由に端末確認を省略しない。APIキー等の不足で確認不能なら未確認操作と理由を報告する。この証拠添付の失敗だけで他の完了処理は止めないが、見つかった不具合はメインに返して修正要否を判断する。添付や再開に必要な記録が残る場合は、完了処理でも削除しない。
