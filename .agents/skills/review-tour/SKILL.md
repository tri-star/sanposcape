# レビューツアー

ユーザーが自分の観点で変更を確かめられるよう案内する。対象packageの `AGENTS.md` と該当ADRを読む。ツアー中に見つけた問題は根拠と影響を添えてその場で伝え、確認前の推測は「未確認」とする。実装修正やGitHubへの投稿はツアーに含めず、依頼された場合に別途扱う。

## 対象と進捗

PR番号を受け取ったら `gh pr view <番号> --json title,body,baseRefName,headRefOid,url` と `gh repo view --json nameWithOwner` で対象を特定し、`git fetch origin <baseRefName>` と `git fetch origin refs/pull/<番号>/head` で比較対象を取得する。`headRefOid` と取得したheadが一致するか確認し、baseとheadのmerge-baseを取る。対象指定がなければ現在のブランチのPRを調べ、特定できない場合は候補を示して選んでもらう。`--local [base]` では指定base（既定main）とHEADのmerge-baseを使う。作業ツリーをcheckoutで切り替えない。

`tmp/review-tour/<対象ID>/` に `state.md` と `findings.md` を作る。対象IDはモード・リポジトリ・PR番号またはブランチ名・指定baseから安全な短いhashで作り、PRとローカル、異なるbaseを分離する。stateにはその識別情報、対象URL、base/headのSHA、選択済み・候補の観点、各観点の訪問順・現在位置・結論を記録する。既存記録を再開する前に識別情報が完全一致するか確認し、不一致なら別の対象IDに作り直す。headが動いていたら行番号の変化を伝え、固定済みheadのまま続けるか、最新headに更新して訪問先を見直すかユーザーに選んでもらう。`tmp/` の記録はコミットしない。

## 概要と観点

PR本文と変更ファイル一覧・追加/削除行数から、目的、規模、領域別の変更地図、注意を要する変更を簡潔に示す。両モードともファイル一覧は `git diff --name-status <base_sha> <head_sha>`、行数は `git diff --numstat <base_sha> <head_sha>` から得る。PRが途中で更新されても、概要と後続の説明は同じ固定SHAを参照する。生成物・同型の変更はまとめる。この段階で全ファイルのdiffを読まない。目的が本文だけでは不明な場合のみ関係する少数のdiffを読む。

[観点の型](references/viewpoints.md) を参考に、その変更に固有の問いを4〜8件、理由・根拠ファイル・案内の長さとともに提示する。ユーザーに選んでもらい、自由記述も受け付ける。複数選ばれたら依存の少ない観点から案内する。未選択の候補も進捗に残す。

## 一か所ずつ案内する

選ばれた問いに答える最短の訪問順を3〜7か所で作り、先に一覧を示す。呼び出し関係は実コードで確かめる。対象ファイルだけ `git diff <base_sha> <head_sha> -- <path>` で読み、変更後のコードは `git show <head_sha>:<path>` で読む。削除されたファイルだけbase版を読み、その旨を明記する。PRモードで現在の作業ツリーを変更後のコードとして読まない。

訪問先ごとに、開く場所（headの `file:line`。PRならcommit固定のGitHubリンク）、そこで何が起きるか、前の場所とのつながり、問いについて分かったこと、ユーザーに確かめてほしい点を示す。既存コードは「既存」と明記する。問題は重要度、発生条件、影響、根拠を `findings.md` に連番で記録する。ユーザーの指摘は確認済みと混同せず、そのまま記録する。図を求められた場合は実在を確かめた要素だけで描き、各ノードに根拠の `file:line` を付ける。

一か所を案内したら位置を保存して止まり、「次へ／質問／指摘を記録／この観点を終える」を提示する。質問には必要な範囲を調べて答え、元の位置へ戻る。観点を終えるときは問いへの答えを短く記録し、次の観点に進むか聞く。中断では再開方法と保存場所を伝える。全観点の終了時は答えと指摘を示し、未選択の候補や追加質問があるか聞く。

PRの変更ファイル一覧を完全に取得できない場合は、その範囲を明示する。大規模PRでも保存済みbase/headのローカル比較から全件確認する。コード引用は短くし、各主張の根拠をhead時点の行番号で示す。
