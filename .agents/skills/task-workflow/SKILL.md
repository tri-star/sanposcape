# 課題から開発する

メインが要件・計画・実装・検証を担当する。ユーザー指定の範囲を優先し、計画のみなら実装・課題更新・PR作成へ進まない。依頼範囲内の判断は推奨案で進め、理由を申し送りに残す。計画/実装を領域別agentに委譲しない。独立レビュー以外の調査・大量の機械変更への委譲は、ユーザーまたは適用される指示が明示的に求める場合だけ検討する。

1. 課題ID/URLなら [issue-tracker](../issue-tracker/SKILL.md) で本文・受け入れ条件・関連課題・必要なコメントを取得し、取得完了後に計画する。本文が直接渡された場合はその本文で進め、未取得の外部情報を推測しない。
2. 作業ツリーと対象packageを確認する。既存変更は保持する。Orca管理下のworktree操作が必要なら利用可能な `orca-cli` に従う。ディレクトリ名だけで課題・ブランチを変更しない。
3. 関係する領域だけ読む: [backend](../backend-development/SKILL.md)、[Web](../frontend-development/SKILL.md)、[mobile](../mobile-development/SKILL.md)。各packageのAGENTS.mdから正本と指定された領域メモリを辿る。インフラ・CIは対象構成と既存ADRをメインで調べる。
4. 方針と却下案、影響範囲とAPI/データ契約、更新する文書、完了条件と必要な検証、判断の記録を短く計画する。変更する名前・パス・コマンド・設定キーから文書を逆引きし、更新対象を列挙する。シグネチャやProps型まで固定しない。複数領域では共通API契約を先に決め、backendスキーマ → OpenAPI生成 → Orval生成 → クライアント実装の依存順を守る。API変更のない画面は独立して進めてよい。
5. 実装依頼では実際の着手時に課題の `start` を反映する。メインで実装し、関連テストと必須チェックを実施する。`.env` 不在に気づいたら [local-env-setup](../local-env-setup/SKILL.md)。
6. [change-review](../change-review/SKILL.md) で変更全体・文書・条件付きsecurityの独立レビューを逐次行う。範囲内の確かな不具合は修正し、関連する検証を実施する。仕様選択は推奨案・理由・影響を申し送りに記録する。
7. コミット規約に従う。push・PR作成が依頼範囲に含まれる場合は実行する。レビュー指摘対応では新規PRを作らず、対象を確認した既存PRのブランチへpushする。`handover-notes.md` があれば、未完了・検証結果を整理してPR本文の「申し送り事項」に含める。作成または修正のpush成功を確認して、対象PR URLとともに `pr-created` を反映する。ローカル実装だけならその完了を報告し、PR作成済みや課題完了と扱わない。
8. PR作成・レビュー修正のpush後は [mobile PRの確認証拠](../mobile-development/references/pr-verification.md) で画面変更の対象判定と確認証拠を扱う。その後 [完了時の知識整理](references/completion.md) を行い、今回の決定を同じPRに含める。計画のみ・ローカル実装のみの場合は一時記録を保持し、この完了処理は行わない。

## 記録と再開

計画・レビュー・申し送りは `tmp/<issue-id>/`（IDなしなら `tmp/<YYYYmmdd-HHMM>/`）。IDはパス区切りや `..` を含まない安全な名前にする。小変更に複数の記録を強制しない。複雑な課題は `plan.md` に領域別の節を作り、`handover-notes.md` に決定・未完了・検証結果・外部更新の成否を残す。

再開時は対象課題の記録と現状を照合する。重要な設計判断は [adr-writing](../adr-writing/SKILL.md)。永続文書から一時メモへリンクしない。レビュー修正の再着手は `review-fix`、マージによる完了は対象PRの実際のマージ確認後だけ反映する。

同じテスト・同じ手順で3回失敗したら、その手順を繰り返さず、失敗・試したこと・現状・推奨する次の手を報告する。ブランチ操作はメインが対象を確認して行い、reviewerにはさせない。
