# 文書整合性

README、共通docs/adr、変更packageのAGENTS.md・README・docs・adrが対象。ハーネスではskill、agent設定、参照スクリプト、テンプレートも確認する。関連文書だけを読む。

差異を分類する。

- 実装の不具合: 受け入れ条件や有効な設計判断への違反。
- 文書の更新漏れ: 合意した振る舞いに対し操作・設定・生成手順等が古い。
- 設計変更: ADRの前提を変える。理由・影響を残し、過去の判断を無言で置き換えない。
- 未確認: 外部サービスや実機などの証拠不足。

配置・命名・リンク・コマンドとscriptsの一致も確認する。永続文書から一時メモへ参照を作らない。

## focus=docsでの確認

ADRの決定との整合はfocus=changeの責任。docsはAGENTS.md・CLAUDE.md・README・docs（ADR以外）・skill/agent定義・scriptsの使用説明・CIのコメントを対象にする。

各項目で、確認した場所と内容、問題なしの根拠/指摘/対象外の理由を返す。

1. 差分の新旧の名前・パス・関数・コマンド・設定キー・APIフィールド・testIDを拾い、対象文書を `rg` で逆引きする。改名/削除は旧名、挙動の変更は機能名でも探す。
2. プランの「更新する文書」が更新済みか、今回変えた振る舞い・手順・設定と一致するかを確かめる。
3. 文書のリンク・実行コマンド・参照先を実物で確かめる。スクリプトの実行方法、生成物と手編集の境界、権限、成功/未確認の扱いも見る。
4. `scripts/knowledge/check-doc-references.py` が検査しない書き方を補う。CIが見るのはインラインのMarkdownリンク、ルート相対か ./・../ で始まるインラインコード単体のパス、pnpm --filterのpackage/script。package相対のsrc/app、コマンド中やコードブロック内のパス、参照形式リンク、記述と動作の意味の一致はreviewerが見る。
5. 永続文書からtmpへの参照、正本の書き写し、未作成のpackageを既存扱いする記述が増えていないかを確認する。

無関係な既存の古い記述や言い回しの好みは必須修正にしない。機械検査が通っても意味の整合や全観点の確認が済んだとは扱わない。
