# 変更レビュー

要求・実装・文書の一致を反例と証拠で確認する。レビューのみの依頼では修正や外部投稿を行わない。

依頼された比較対象を使う。PRならbaseとのmerge-base、ローカルならコミット差分・未コミット・新規ファイルを区別し、他の作業を混ぜない。対象コミットと作業ツリー状態を記録する。

変更に応じて [backend](references/backend.md)、[frontend](references/frontend.md)、[mobile](references/mobile.md)、[文書](references/docs.md) を読む。

## 独立レビュー

通常のコード変更や重要なハーネス変更では、`adversarial_reviewer` を1つ起動する。定型文言・書式だけならメインで確認してよい。ユーザーがSubagent不使用を指定した場合もメインで確認し、独立性の制約を明示する。

渡すのは要求、比較対象、パス、規約への導線、検証結果、返す形式。実装者の結論や誘導を渡さず実物を確認させる。会話の自動継承に依存せず必要情報を明示する。

reviewerは編集・外部更新・追加Subagent起動を行わず結果を返す。保存はメインが行う。レビュー中は対象ファイルを変更しない。メインは並行して対象外の検証証拠や完了報告を整理できる。

## 指摘への対応

指摘は重要度、場所、発生条件、影響、証拠を含める。根拠のない好みや無関係な既存問題を必須修正にしない。指摘ゼロも有効。未確認は未確認とする。

実装依頼の範囲内の明確な不具合はメインが修正し、関連チェックを行う。再レビューは同じreviewerへ変更箇所と未解決の論点だけ依頼する。懸念解消後は終了し、全領域のレビューを毎回やり直さない。仕様判断が必要なら影響を具体化して確認する。
