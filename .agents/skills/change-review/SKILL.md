# 変更レビュー

要求・実装・文書の一致を反例と証拠で確認する。レビューのみの依頼では修正や外部投稿を行わない。

依頼された比較対象を使う。PRならbaseとのmerge-base、ローカルならコミット差分・未コミット・新規ファイルを区別し、他の作業を混ぜない。対象コミットと作業ツリー状態を記録する。

変更に応じて [backend](references/backend.md)、[Web](references/frontend.md)、[mobile](references/mobile.md) を読む。文書確認では [文書](references/docs.md)、security確認では [security](references/security.md) を必ず読む。規約は対象packageのAGENTS.mdと関連docs・ADRを正本とし、参照資料は見落としやすい確認項目を持つ。

[データ取扱い台帳](../../../docs/privacy/data-inventory.md)の対象パスに触れる変更、または利用者のデータの取得・送信・保存・削除・公開範囲が変わる変更では台帳も読み、実装と台帳・ポリシー・App Privacyの申告の整合を確認する。

## 独立レビュー

通常のコード変更や重要なハーネス変更では、同じ型の `adversarial_reviewer` を以下の観点で、新しいインスタンスとして逐次起動する。前のレビューが完了してから次を起動し、同時に走らせるのは1体まで。定型文言・書式だけならメインで確認してよい。ユーザーがSubagent不使用を指定した場合もメインで確認し、独立性の制約を明示する。

| focus | 起動条件 | 責任 |
| --- | --- | --- |
| change | 毎回 | 変更全体を層をまたいで見る。要求・契約・設計・正しさ・テスト・ADR |
| docs | 毎回 | 変更した名前から逆引きし、ADR以外の文書の乖離を確認 |
| security | 下記条件に当たるとき | 変更全体の攻撃・漏洩の経路と既存の防御を確認 |

securityは認証・認可・セッション、入力検証・ファイル・URL・外部値のSQL/シェル/HTMLへの受け渡し、新規エンドポイント・CORS/CSP・ストレージの公開範囲、秘密情報・端末への保存、依存/lockfile、CI・デプロイのトリガー/権限/環境に触れるときに起動する。迷ったら対象にする。

さらに、[データ取扱い台帳](../../../docs/privacy/data-inventory.md)の「対象パス」に触れる差分、またはパスに当たらなくても利用者のデータの取得・送信・保存・削除・公開範囲を変える差分ではsecurityを起動する。対象パスの一覧はskillへ書き写さず台帳を正本として参照する。プランが「影響なし」でも対象パスに触れるなら省略しない。

メインはfocus・比較対象・起動した回数・結果を記録する。前のreviewerの結論を次の依頼に入れない。セッションに型が未登録なら、利用可能なreviewerに定義とfocusを明示し、代行したことを報告する。起動できなければメインで確認し、独立レビュー未実施とする。

渡すのはfocus、要求、比較対象、プラン・申し送りのパス、規約と領域メモリへの導線、検証結果、返す形式。実装者の結論や誘導を渡さず実物を確認させる。会話の自動継承に依存せず必要情報を明示する。

changeは要求との一致・層をまたぐ契約・設計と責務・正しさ・テスト・ADRの6観点、docsは参照資料の各確認項目、securityは認証・認可/所有者・入力・公開範囲/漏洩・秘密情報・台帳との整合の6観点をすべて報告する。「確認した場所と内容」「問題なしの根拠/指摘/対象外の理由」を観点ごとに書き、目立つ指摘があっても残りを飛ばさない。台帳との整合は攻撃の成立ではなく食い違いの実在を確かめ、変更後のコードと台帳の行・ポリシーの節を並べる。結果は観点ごとの確認、指摘、未確認、範囲外の順で返す。

reviewerは編集・外部更新・追加Subagent起動を行わず結果を返す。保存はメインが行う。レビュー中は対象ファイルを変更しない。メインは並行して対象外の検証証拠や完了報告を整理できる。

## 指摘への対応

指摘は重要度、場所、発生条件、影響、証拠を含める。根拠のない好みや無関係な既存問題を必須修正にしない。指摘ゼロも有効。未確認は未確認とする。

実装依頼の範囲内の明確な不具合はメインが修正し、関連チェックを行う。再レビューはそのfocusの同じreviewerへ変更箇所と未解決の論点だけ依頼する。懸念解消後は終了し、全領域のレビューを毎回やり直さない。仕様判断が必要なら依頼範囲内の推奨案で進め、判断・理由・影響を申し送りに記録する。権限や必要な入力が不足する場合は、その理由を示して確認する。
