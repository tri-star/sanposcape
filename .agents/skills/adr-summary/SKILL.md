# 目的

ADR は `adr-writing` の追補ルール（経緯を消さず `（<課題ID> 追補: …）` で注記・追記する）により、
時系列の意思決定記録としては正確だが、**追補が重なるほど「今どうなっているか」が読み取りにくくなる**。
追補同士が「下記『SS-79 追補』参照」のように相互参照し始めると、読み手は全文を読んで
頭の中で差分を適用しないと現在の決定にたどり着けない。

このスキルは、ADR の冒頭に**現在有効な決定だけを抜き出した要約セクション**を置くことでこれを解消する。
本文（追補の履歴）はそのまま残すため、「経緯を消さない」追補ルールと両立する。

- 要約 = 「今どうなっているか」を最短で知るための索引
- 本文 = 「なぜ・いつそうなったか」を追うための一次記録

# パラメータ

- `<ADRのパス or 番号>`: 対象の ADR（例: `docs/adr/ADR-002-...md`、`ADR-002`、`mobile ADR-009`）
- `[課題ID]`: 要約を付与・更新する契機となった課題ID（例: `SS-93`）。無ければブランチ名から推測し、
  推測できなければ省略してよい（注記行の課題IDを省く）

# 要約セクションの書式

H1 タイトルの直後、`## 日付` の前に置く。

```markdown
# ADR-00X: タイトル

## 現在有効な決定（要約）

> 最終更新: 2026-09-21（SS-93）。本節は本文（追補を含む）を要約したもので、一次記録は本文。
> 本文と食い違う場合は本節の誤りとして本節を直す。

### 決定

- **<決定の要点を現在形で1文>**。<必要なら補足1〜2文>（本文: 決定1）
- **<追補で加わった決定>**。<補足>（本文: 決定4-1、SS-81 追補）
- **<追補で内容が変わった決定は、変わった後の内容だけを書く>**（本文: 移行・対応事項、SS-81/SS-79 追補）

### 未解決・持ち越し

- <現時点で残っている未達・未作成・別課題で継続中の事項>（本文: SS-81 追補。SS-82 で継続）

### 変更・撤回された決定

- <初版の決定> → <現在の決定>（SS-70 追補）

## 日付
...
```

## 各パートの書き方

### 注記行（必須）

- `最終更新: <YYYY-MM-DD>（<課題ID>）` で要約をいつ・どの課題で書き直したかを示す。
- 「一次記録は本文」「食い違ったら要約を直す」を必ず書く。要約は派生物であり、
  要約を正として本文を読み替える運用にすると、要約の書き漏れがそのまま決定の改変になってしまうため。

### `### 決定`（必須）

- **現在有効な決定だけ**を、**現在形**で書く。「SS-xx で〜に変更した」のような経緯は書かない
  （経緯は本文と `### 変更・撤回された決定` の役目）。
- 1項目は太字の要点1文＋補足1〜2文まで。詳細（コード例・表・理由）は本文に任せる。
- 各項目の末尾に **`（本文: <節>、<課題ID> 追補）` の形で本文上の位置**を書く。
  - 節は本文の見出し番号・名前で示す（`決定3`、`決定6-1`、`移行・対応事項`、`SS-79 追補` 節 など）。
  - 初版から変わっていない決定は課題IDを省略してよい（`（本文: 決定1）`）。
  - 複数の追補が同じ決定に効いている場合は全部並べる（`SS-81/SS-79 追補`）。
  - Markdown のアンカーリンク（`#3-スタブは...`）は使わない。日本語見出しのアンカー生成規則は
    レンダラ依存で、見出しに追補注記を足しただけでリンクが切れるため。
- 他 ADR に決定の本体がある場合は、その ADR へのリンクを添える（例: ヘッダー名の変更理由は ADR-005 決定4）。
- 目安は 5〜15 項目。これを大きく超えるなら ADR の対象範囲が広すぎる兆候なので、
  ユーザーに ADR の分割を提案する（分割自体はこのスキルでは行わない）。

### `### 未解決・持ち越し`（該当があれば）

- 本文中に散らばっている「未達」「未作成」「別課題で継続」「実装タスク側で決定する」を集約する。
- 可能なら継続先の課題ID を書く。
- 既に解消済みか確信が持てない項目は、コード・他 ADR・Plane で確認してから載せる（後述の手順3）。

### `### 変更・撤回された決定`（該当があれば）

- 初版（または途中の追補）の決定が後の追補で覆った・置き換わったものを `旧 → 新（課題ID 追補）` で1行ずつ書く。
- 本文には旧い記述が注記付きで残っているため、読み手が本文で旧い記述に出会ったときの混乱を防ぐ目的。
- 「決定は変えずに記述を実装に合わせた」だけの追補（例: ヘッダー名の変更）もここに入れてよい。
- 本文のコンテキストや影響に、初版時点の見込みが注記なしで残っていて現在の決定と食い違う場合も、
  「本文の○○にある『…』は初版時点の見込みで、現在は…」の形で1行入れてよい。
- ADR 以前の前提（例: 別ドキュメントが当初想定していた構成）が変わっただけのものは、この ADR の決定の変更ではないので入れない。

# 更新のタイミング

| 場面 | 要約の扱い |
| --- | --- |
| ADR の初版を書く | **付けない**。初版では `## 決定` がそのまま現在有効な決定であり、要約は重複になる |
| 要約の無い ADR に初めて追補する | 追補と同じ変更で要約を**新設**する |
| 要約の有る ADR に追補する | 追補と同じ変更で要約を**更新**する（注記行の日付・課題IDも更新） |
| 長い ADR を後から整理したい | このスキルを単独で使い、要約を新設・再作成する |

要約だけを書き直した場合は、`## 日付` 節には追記しない。`## 日付` は「決定がいつ変わったか」の記録であり、
要約の書き直しは決定の変更ではないため。要約をいつ書き直したかは注記行の `最終更新` で追える。

# 手順

## 1. ADR を全文読む

途中から読まない。追補は ADR のどこにでも入り得る（本文中の注記、節末の追補、末尾の独立した追補節、
`## 日付` 直下の説明文、`## 関連情報`）。要約が既にある場合も、要約ではなく本文を読み直すこと。

## 2. 決定と追補のチェーンを洗い出す

次の表を頭の中（長ければ作業メモ）で作る。

| 決定（本文上の位置） | 初版の内容 | それに効く追補（課題ID・位置） | 現在の内容 |
| --- | --- | --- | --- |

- `## 決定` の各項目に加え、`## 影響` の「移行・対応が必要な事項」や独立した追補節にも
  実質的な決定（運用ルール・設定値・登録状態）が書かれていることが多い。拾い漏らさないこと。
- 追補が別の追補を参照している場合（「SS-81 追補。SS-79 で更新: 下記参照」）は、
  **チェーンの末端まで**たどって現在の内容を決める。
- 「未着手」「今回スコープ外」「〜は別課題」の記述は、後の追補で実績に置き換わっていないか確認する。
- **「〜を検討する」「具体は実装タスク側で決める」のような未確定の記述を、要約で確定事項に格上げしない。**
  実装で確定しているなら手順3で裏取りして本文に注記してから要約に載せる。裏取りできなければ未確定のまま扱う。
- 要約で短く言い換えるとき、本文の**限定語（「開発識別子の」「E2E / staging のビルドでは」等）を落とさない**。
  「全経路」「すべて」のような語は、本文が何を指して言っているかを確認してから使う。

## 3. 必要に応じて裏取りする

本文だけで現在の状態が確定できないとき（「未実装」「未作成」と書かれているが時間が経っている、
他 ADR に後続の決定があるらしい、等）は、コード・他 ADR・`git log` で確認する。

- 裏取りの結果、**本文が現状と食い違っていた**場合は、要約だけを現状に合わせるのではなく、
  本文にも `adr-writing` の追補ルールに従って注記を入れる（要約と本文を食い違わせない）。
  どの課題で見つけた食い違いかを課題IDとして使う。
  本文に注記を入れた時点でそれは追補なので、`## 日付` にも `<日付> 追補（<課題ID>）` を追記する。
- 確認できなかった事項は要約に載せず、ユーザーへの報告に「未確認」として挙げる。

## 4. 要約セクションを書く

上記書式に従って書く。既に要約がある場合は、差分更新ではなく手順2の表をもとに**全体を書き直す**つもりで
見直す（部分更新を重ねると、要約自体が本文と同じく読みにくくなるため）。

**本文は変更しない。** 例外は手順3で見つけた食い違いの注記のみ。

## 5. 自己チェック

- [ ] `### 決定` の各項目に `（本文: …）` がある
- [ ] 各項目の `（本文: …）` が指す位置に、実際にその内容が書かれている
- [ ] 本文の追補（`追補` で検索）をすべて見て、要約に反映すべきものが漏れていない
- [ ] 要約に経緯（「〜に変更した」）が混ざっていない。経緯は `### 変更・撤回された決定` に分けた
- [ ] 本文と食い違う記述が無い
- [ ] 本文を（食い違いの注記以外で）変更していない
- [ ] 要約から `tmp/` を参照していない（`scripts/knowledge/check-tmp-references.sh` が通る）

可能であれば、要約を書いた本人ではない別のエージェントに、本文（とコード）と突き合わせて
要約を敵対的に検証させる。書いた本人は自分の読解に引きずられて、限定語の脱落や未確定事項の格上げを見落としやすい。

## 6. コミットと報告

追補と同時に行った場合は追補と同じコミットでよい。要約だけの場合は単独でコミットする
（コミットメッセージのルールは `docs/git-commit-guideline.md`）。

ユーザーへの報告には次を含める。

- 要約に載せた決定の数と、`### 変更・撤回された決定` / `### 未解決・持ち越し` の件数
- 手順3で裏取りした事項と結果、本文に注記を入れた箇所
- 確認できず要約に載せなかった事項
- ADR の分割を提案する場合はその理由
