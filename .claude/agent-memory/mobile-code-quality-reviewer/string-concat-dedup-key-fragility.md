name: string-concat-dedup-key-fragility
description: 単純な文字列連結（`${a}:${b}`）で作る重複判定キーは、区切り文字が値に含まれると衝突しうる。型だけでは守られないので生成元を確認する。
type: feedback
---

`${id}:${flag}` のような単純な文字列連結でキャッシュキー／発火済みキーを作るパターン
（例: SS-37 `src/features/walk/lib/walkSaveTrigger.ts` の `walkSaveFireKey`）は、
`id` に区切り文字（`:`）が含まれると異なる `(id, flag)` の組が同じキー文字列を生成しうる。
衝突すると「既に発火済み」と誤判定され、本来実行すべき処理がサイレントにスキップされる
（このケースでは保存 `POST /walks` が再送されない）。

**Why:** 型システムは `string` にこの不変条件（区切り文字を含まない）を強制しない。
`id` の生成元を変えた将来のリファクタで気づかれずに壊れるリスクがある。

**How to apply:**
- 指摘する前に、必ず `id` の実際の生成元（`randomUuidV4()` など）を grep で確認し、
  現時点で衝突が本当に起こり得るかを見極める。起こり得ない場合は Critical ではなく
  Medium/Low の「将来の保守性・型安全性」の指摘として書く（このケースは UUID 生成のため
  実害なしと判定し Medium suggestion に留めた）。
- 改善案としては、JSDoc で不変条件を明記する／タプルや専用オブジェクトの `useRef` に変えて
  区切り文字衝突を設計上不可能にする、の両方を提示する。
- 同種のパターン（`${a}:${b}` 形式のキー生成）は他の hook・store にも今後現れうるので、
  レビュー対象に文字列連結キーが出てきたら値の生成元をまず確認する習慣をつける。
