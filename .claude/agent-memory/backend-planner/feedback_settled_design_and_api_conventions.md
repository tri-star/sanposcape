### 1. 確定済みの設計・API 契約を再検討しない

ユーザーとの議論を経て ADR や API 契約が確定している場合、プラン作成時にそれを前提として扱い、設計の妥当性を蒸し返さない。指示に「設計方針を再検討・変更しないでください」と明示されることがある。

**Why:** 設計判断はユーザーとの往復で既にコストを払って合意済み。エージェントが選択肢を再提示すると議論がやり直しになる。
**How to apply:** 与えられた ADR / 先行プランを最初に全文読み、プラン冒頭に「前提ドキュメント（設計は確定済み。再検討しない）」として明記する。新しく決める必要がある事項（確定文書がカバーしていない部分）だけを「本プランで新たに決定した事項」として理由付きで表に起こし、判断に迷うものは末尾の「質問・確認事項」に回す。

### 2. API のフィールド命名は snake_case

レスポンスもリクエストも snake_case で統一する（`access_token` / `expires_in` / `id_token` / `user_key` / `display_name` / `photo_url`）。

**Why:** 既存の `SpotRead.created_at` に揃えるというユーザーの明示的な判断。モバイル側は `sessionMapper` などで吸収する方針。
**How to apply:** モバイル側のプランが camelCase で書かれていても snake_case に読み替える。読み替えによってモバイル側の修正が必要になる箇所（レスポンスだけでなく**リクエストボディの組み立て**も含む）は、プラン内に「モバイル側への伝達事項」として明示的に列挙する。

### 3. 開発専用エンドポイントは公開 OpenAPI 契約に載せない

`AUTH_MODE=dev` のときだけ有効になるような開発専用エンドポイントは、FastAPI の `include_in_schema=False` を指定して OpenAPI スキーマから除外する。

**Why:** 「本番に存在しないエンドポイントを公開 API 契約に載せない」というユーザーの判断。副次効果として OpenAPI 出力が実行時の環境変数に依存しなくなり、生成物が決定的になる。
**How to apply:** 「router が include されるか（ルーティング）」と「スキーマに載るか（契約）」は**独立した2軸**として整理して提示すること。前者はモード依存のままでよく、後者だけを常に false にする。トレードオフとして、そのエンドポイントの DTO はモバイル側で手書き維持になる点を伝達事項に含める。指定漏れで再発しうるので、「モードを変えても `app.openapi()` の出力が一致する」テストで不変条件を固定する。

### 4. PR は backend 先行 → mobile の2本に分割する

**Why:** backend がマージされてから mobile が dev モードで実動作確認する流れにするため。
**How to apply:** backend プランの完了条件は **backend 単独で満たせるもの**に限る（モバイルの `orval` 実行や typecheck を完了条件に入れない）。モバイルの Orval 生成物は gitignore 済みなので backend PR は `openapi.yaml` のコミットだけでよい。backend 単独で手動疎通確認できる手段（認証なら dev トークン + 認証必須エンドポイント）をプランに用意する。両プランが同じファイルの編集を計画している場合はどちらの PR で行うか明記して重複を消す。
