### 1. mobile プランの API 要求には1項目ずつ明示的に回答する

mobile プラン（`tmp/<issue-id>/mobile-plan.md`）に「backend に要求する API 情報」セクションがある場合、
backend プランに**要求 → 回答（受ける / 変更して受ける / 受けない）→ 理由**の表を必ず作る。
要求されていないが backend 判断で足す/変える項目は「mobile への伝達事項」として別立てで列挙する。

**Why:** mobile 側は backend のマージ後でないと `orval` 生成ができず着手できない。
「暗黙に受けなかった要求」があると mobile の実装分岐が後から増え、手戻りになる。
ユーザーから「各要求に対して明示的に回答すること」と直接指示された。
**How to apply:** 「変更して受ける」を選ぶときは *mobile 側の作業が増えるか* まで書く。
例: 「2点未満の leg は除外してよい」という許可は「loop なら必ず2件」という別要求と矛盾するので、
除外ではなくフォールバックに落とす、といった**要求同士の衝突の解消**は backend 側の責務。

mobile が「スキーマだけ先行マージできないか」と要求してくることがあるが、
`openapi.yaml` は `app.openapi()` から生成される（＝スキーマ定義そのものがコード）ため分離できない。
代案は「schemas.py + openapi 再生成を単独コミットにして早期にドラフト PR を立て、ブランチ名を共有する」。

### 2. 外部 API 依存で品質が机上判定できない方式は、スパイクをステップ0に置く

実装プランの最初に「捨てコードで実 API を叩き、合否を数値で判定する」ステップを置き、
**判定基準（しきい値）と、未達だった場合にユーザーへ再判断を求める分岐**をプランに明記する。

**Why:** SS-33 の周回ルート（Google Routes API に経由点を与えて周回を作る方式）で、
「経路が自然かどうかは机上では判定できない」という理由からユーザーが明示的に指示した。
**How to apply:** スパイクのプランには (1) API キーの入手/設定手順、(2) 実課金が発生する旨の事前承認依頼、
(3) 捨てコードの置き場（コンテナの bind mount から見える gitignore 済みディレクトリ）、
(4) 数値の合否基準、(5) 未達時の代替案、を必ず含める。
実測から決めた定数は、実装時にコードのコメントへ転記して由来を追えるようにする
（`tmp/` は gitignore 対象なので ADR やコードから参照してはいけない）。
