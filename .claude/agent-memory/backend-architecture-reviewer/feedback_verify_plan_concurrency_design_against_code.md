backend-planner が書く `backend-plan.md`（`packages/backend/AGENTS.md` が参照する
workflow の成果物）は、並行性・冪等性のエッジケース（例:「真に同時なリトライで
アップロード枠が既に使用済みなら、同じ冪等ターゲットへの再送として成功扱いにする」）を
かなり具体的に文章で設計することがある。SS-88（ピン登録、写真の先行アップロード→確定）の
レビューで、この種の記述の一部（複数のAPIエンドポイントから共有される1つのヘルパー
関数の中の1分岐）が実装から抜け落ちているのを見つけた。

**Why:** この種の欠落は、diff レビュー（変更行だけを見る）や通常のテストレビュー
（「そのテストは何を検証しているか」だけを見る）では気づきにくい。理由は3つ:
1. 実装は「一見それらしい」コード（アップロード枠の状態チェック、409を返す分岐）を
   ちゃんと書いているため、コードだけを読むと不自然に見えない。
2. 冪等性のテストは「逐次リトライ」（1回目が完全に commit してから2回目を呼ぶ）
   だけを書きがちで、「真に同時（1回目が commit する前に2回目がロック待ちに入る）」
   ケースは統合テストで再現しにくいため書かれないことが多い。
3. 該当のロジックが複数のエンドポイント（例: `POST /pins` と
   `POST /pins/{id}/photos`）から呼ばれる共有ヘルパーに実装されるべきなのに、
   片方の呼び出し元だけが個別に事前チェックを書いていて、共有ヘルパー自体には
   その分岐が無い、という分布になっていることがある。

**How to apply:**
- 冪等性・並行性に関わる機能（`client_*_id` 冪等キー、advisory lock、`FOR UPDATE`、
  presigned URL の確定処理など）をレビューする際は、backend-plan.md や ADR の
  該当セクションの記述を**箇条書き単位で実装コードの行と突き合わせる**。「この設計判断は
  どのファイルのどの分岐で実現されているか」を1つずつ指させないなら、実装漏れを疑う。
  [[backend-layering-conventions]]
- 特に「複数の呼び出し元から使われる共有ヘルパー」（例: `PinService._prepare_photos`）は、
  呼び出し元Aだけがテストされていて呼び出し元Bのテストが無い場合、Aで動くことを
  確認しただけでBも安全だと判断しない。
- 「真に同時なリクエスト」を再現するテストが無いことに気づいたら、それ自体を
  Suggestion / Warning として指摘してよい（テストが無いこと自体が、実装漏れを
  隠す一因になる）。
