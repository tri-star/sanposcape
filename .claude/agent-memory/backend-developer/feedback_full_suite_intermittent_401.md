backend 全体（800件超）の `uv run pytest` を通しで10回ほど流したうち2回、無関係なテストが
「有効なはずの JWT で 401」という形で落ちた（SS-111、2026-09-24）。落ちるテストは毎回違い、
該当ファイル・該当テストを単独で実行すると常に成功する（`pins/tests/test_router.py` を5回連続で
流して全件成功）。CI では再現していない。

原因は確認できていない。`conftest.py` の `_setup_schema`（autouse）がテスト関数ごとにスキーマを
`create_all`/`drop_all` しており、docker compose の `db` への負荷が高くなることが要因ではないかと
推測している。

**Why:** 自分の変更と無関係な 401 を見て、認証まわりを壊したと誤解して調査に時間を使いやすい。

**How to apply:**
- 全件実行で 401 が出たら、まず落ちたテストだけを単独で実行して再現するか確かめる。
- 単独で通り、同じテストが続けて落ちないなら、このメモの現象として扱い、報告に一言添える。
- 同じテストが3回以上続けて落ちる、または単独でも落ちるなら本物の不具合として調べる。
- 頻度が上がったら、スキーマ作成をセッション単位にしてテストごとにトランザクションを巻き戻す方式への
  変更を別チケットとして提案する。

**2026-09-28 追記（SS-141）**: 上記で推測していた原因（`_setup_schema` がテストごとに
`create_all`/`drop_all` していた）は SS-141 で解消した。スキーマ作成は session スコープで
1回だけになり、各テストの前は `DELETE FROM` でテーブルの中身を空にするだけになった
（[[project_ss141_test_db_reset_complete]]、`docs/adr/ADR-011-backend-test-db-isolation-by-table-reset.md`）。
全体の実行時間も中央値で約73%短縮（114.24s→30.52s）している。DB負荷が原因だった場合はこの
変更で自然に解消している可能性が高い。次に全件実行で 401 が再発した場合は、DB負荷起因という
仮説は見直し、別の原因を疑うこと。
