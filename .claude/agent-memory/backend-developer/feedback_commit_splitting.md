このプロジェクトの git commit ガイドライン（`docs/git-commit-guideline.md`）は「1ステップ完了ごとに
関連ファイルだけをコミットする」ことを求めている。レビュー対応など複数の独立した指摘に同時に着手すると、
同じファイル（例: `walks/tests/test_router.py`）に複数指摘分の変更が積み上がりがちだが、それでも
指摘単位でコミットを分けるべき。

**Why:** コミットを見ることで「この作業でどのファイルがどのように変更されたか」を追えるようにする
ため（ガイドライン本文の意図）。1コミットに複数の独立した指摘対応を混ぜると、後から特定の指摘だけを
revert/cherry-pick したい場合に困る。

**How to apply**: 変更がファイル内で非連続なブロック（＝別々の diff hunk）に分かれている場合、
`git reset <file>` で一旦アンステージしてから `printf 'n\ny\n' | git add -p <file>` のように
yes/no を標準入力で流し込んで hunk 単位でステージを選別できる（対話プロンプトが使えない環境でも
機能する）。`git diff --cached <file> | grep '^+'` でステージ内容を確認してから commit する。

一方、`router.py` の本体変更（例: `AwareDatetime` 化）とそれに対応する回帰テストは同じ指摘に属するため
1コミットにまとめてよい。「指摘（レビュー項目）単位」で分けるのが基準であり、「ファイル単位」ではない。

**How to apply（応用: `git add -p` では分割できないケース, PR #93 backend フォローアップで確立）**:
実装をすべて終えた後にまとめてレビュー指摘単位でコミットを割る場合、2つの指摘の追加箇所が
ファイル上で隣接していると `git diff` は1つの hunk にまとめてしまい、`git add -p` の hunk 単位
選別では割れない（`s`（split）は非連続な変更の間にしか効かない）。

1. まず `git diff -- <file> | grep -n '^@@'` で hunk 境界を確認する。もし本来別指摘の変更が
   同じ hunk に混ざっていたら、**ソースコード側で該当ブロックを（意味を変えずに）並べ替えて**、
   既存の unchanged な行（元からある関数・フィクスチャ等、最低でも context 分＝3行以上）を
   間に挟むことで2つの hunk に分離できる（例: 新規追加した2つの test fixture が隣接していたら、
   片方を離れた場所にある別の既存 fixture の後ろに移動する）。
2. 分離できないほど本質的に絡み合っている場合（例: 同じ関数内で片方の指摘が既存コードを書き換え、
   もう片方がすぐ後ろに新規コードを追加）は、無理に割らず「どちらの指摘のコミットに含めるか」を
   決めて commit message にその旨を明記する（例: 「main.py のこの hunk は T15 の変更に加えて
   T11 が追加する2つの新規ハンドラも含む」）。
3. 複数コミットに跨る変更をまとめて実装してしまった後で遡って割る場合は、`git diff -- <file> >
   /tmp/.../file.diff` で全体差分を保存し、`sed -n '<start>,<end>p'` で hunk 単位に切り出して
   （diff ヘッダー4行 + 対象 hunk 群）個別の patch ファイルを作る。`git checkout HEAD -- <file>`
   で該当ファイルを HEAD に戻してから、コミット順に `git apply <patch>` を積んでいく
   （`git apply` は行番号ではなく前後の unchanged context で照合するため、他ファイルが
   別コミットで進んでいても該当ファイル自身が正しい基点にあれば問題なく当たる）。
   `openapi.yaml` のような自動生成ファイルは、コード側の変更を段階的に commit した直後に
   毎回 `scripts/export_openapi.py` を再実行する方が、手動 patch より確実（実際にアプリが
   生成する内容と一致することを保証できる）。
4. 安全策として、作業前に全変更後の最終版ファイル一式を一時ディレクトリへバックアップしておき、
   全コミットが終わった時点で working tree とバイト単位で一致するか `diff` で確認する
   （分割作業中に内容を壊していないことの最終チェック）。
