# 章の解説テンプレート

`tmp/review-tour/<PR番号>/chapters/<章ID>.md` に、この構成で書く。
自由形式で書くと章ごとに濃淡が出て、ユーザーが「次に何を読まされるか」を予測できなくなる。
**節は省略せず、該当なしの場合は「なし」と書く。**

````markdown
# <章ID> <章タイトル>

## この章は何のための変更か

<1〜2文。コードの説明ではなく、ユーザー・運用にとって何が変わるかを書く>

## 変更の全体像

| ファイル | 役割 | 変更 |
| --- | --- | --- |
| `path/to/file.py:12` | この機能の入口 | 新規 |
| `path/to/other.py:88` | 保存処理 | 既存に分岐追加 |

読む順: `file.py` → `other.py` → `tests/test_file.py`

## 主要な変更

### 1. <小見出し> — `path/to/file.py:12-40`

<何をしているコードか。既存コードとの関係(どのパターンに倣ったか / どこが新しいか)>

```python
# 引用は10行以内。長い場合は要約し、行番号で参照する
```

**なぜこう書かれているか**: <設計意図。既存の慣習・ADR・制約との関係>

## 図

<必要な場合のみ。判断基準は references/diagram-recipes.md>

## レビューしてほしい観点

1. **<観点>** — `path:line`。<何を確認してほしいか、なぜ気になるか>
2. ...

<2〜3個。「ここが正しいか自信がない」「設計判断が分かれる」箇所を挙げる。
 機械的に検出できる指摘(lint/型)は書かない>

## 理解チェック

<ユーザーへの問いを1つ。答え合わせをして、ズレていれば補足説明する>
````

## 書くときの制約

- **コード引用は10行以内**。それ以上は要約し `file:line` で参照する。ユーザーは自分で開ける。
- **すべての主張に `file:line` を付ける**。付けられない主張は、確認していない推測なので書かない。
- **diff に無いことを書かない**。既存コードの説明を混ぜる場合は「(既存)」と明示する。
- **1章 5〜10分で読める量**に収める。超えるなら章を分割する。
- 未確認の点は「未確認」と書く。埋め合わせで断定しない。

## 横展開(同型変更)の章の書き方

`detect-repeated-changes.py` が検出した群は、通常の章立てではなく次の形にする。

````markdown
# <章ID> <何を何件に適用したか>

## 代表例 — `path/to/representative.py:20`

<1件だけ精読して、変更の意味を説明する>

## 同型の変更が適用された残り N 件

- `path/a.py:15`
- `path/b.py:22`
...

<必ずファイル名を全件読み上げる。「他 N 件」で省略しない。
 ユーザーが「そこも本当に同じか」を判断できなくなるため>

## 例外

<同型に見えて実は違う差分があれば、ここに挙げる。無ければ「なし」>
````
