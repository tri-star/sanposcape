# 観点カタログ

`facts.json` の変更内容から、レビュー観点の候補を導くための対応表。
**ここにある文言をそのまま使わず、PR の実際の機能名・ファイル名を入れた問いに書き換えること。**
「削除機能について」ではなく「地図の削除は同期的に行われるのか。紐づくピン・写真はどうなるか」のように、
答えが出たかどうかを判定できる問いにする。

## 変更内容 → 観点候補

| 変更の兆候（`facts.json` から判定） | 観点候補（問いの型） |
| --- | --- |
| backend と mobile の両方に変更がある | A. 画面の入口から API・ビジネスロジック・DB までの流れ |
| `layer: migration` / `model` がある | B. DB に何を変更するか。既存データ・ロールバックへの影響 |
| 削除系の関数・エンドポイント（`delete` / `remove` / `DELETE`）がある | C. 削除は同期か非同期か。関連データ・外部ストレージはどうなるか |
| アップロード・外部サービス（`integrations/`、`storage`、`s3`、mobile `services/`）に触れる | D. ローカル環境ではどう動くか。スタブで外部サービスに依存せず動くか |
| 外部 API・AWS 呼び出しが増えた | E. 外部呼び出しが失敗・遅延したときにどうなるか |
| `auth/`・`dependencies.py`・権限・所有者チェックに触れる | F. 誰が何をできるか（認可・他人のデータへのアクセス） |
| `router` / `schema` の変更、`openapi` の再生成 | G. API の契約（リクエスト・レスポンス・エラー）がどう変わるか。既存クライアントを壊さないか |
| 状態を表すカラム・enum・store の追加 | H. 状態がどう遷移するか。到達できない・戻れない状態がないか |
| 一覧取得・集計・`expand`・ループ内のクエリ | I. データ量が増えたときの性能（N+1・ページング・インデックス） |
| 複数テーブルへの書き込み・外部呼び出しを伴う更新 | J. 途中で失敗したときに不整合が残らないか（トランザクション境界） |
| `feature_flags`・`runtime_config`・`app_config`・環境変数・`config.py` | K. 設定・フラグで挙動がどう切り替わるか。本番・ローカルで差がないか |
| `aws_lambda/`・`Dockerfile`・`compose.yaml`・`.github/` | L. デプロイ・実行環境で何が変わるか |
| テストの追加・変更 | M. 何がテストされ、何がテストされていないか。スタブは本物と挙動がずれないか |
| `adr/`・`docs/` の変更 | N. 設計判断は何で、実装はそれに沿っているか |
| mobile の画面・hooks・store の変更 | O. 画面の状態（読み込み中・エラー・空）とユーザー操作への反応 |
| 同型変更が多数（`repeated.json`） | P. 横展開された変更が本当にすべて同じか。例外はないか |

ここに無い観点でも、PR 本文や変更から「レビューする人が気にしそうなこと」があれば候補に入れてよい。

## 観点ごとの案内ルートの型

ルートは「観点の問いに答えるための最短経路」として組む。以下は並べ方の型で、実際の立ち寄り先は PR に合わせて選ぶ。

### A. 画面の入口から API・DB までの流れ

1. mobile の画面（`app/` のルート）— ユーザーがどこで操作するか
2. 画面から呼ばれる hook / feature の API ラッパ — どの API を、どの引数で呼ぶか
3. backend の router — リクエストの受け口、認証依存、入力スキーマ
4. service — ビジネスロジックの本体
5. repository / model — 何を読み書きするか
6. レスポンスが画面に戻ってからの扱い（キャッシュ更新・画面遷移）

途中に外部サービスや非同期処理があれば、その箇所で立ち寄る。図にするなら `diagram-recipes.md` のレシピ1。

### B. DB の変更

1. migration（`alembic/versions/`）— 追加・変更されるテーブル・カラム・制約・インデックス
2. model — ORM 側の定義が migration と一致しているか
3. その列を読み書きする repository / service — 何のために使うか
4. downgrade — ロールバックでデータが失われるか

既存行への影響（NOT NULL・default・既存データの埋め方）は必ず答える。図にするならレシピ3。

### C. 削除の方式

1. 削除の入口（router / 画面）
2. 削除を実行する service — 同期で消すか、論理削除か、ジョブに回すか
3. 関連データの扱い — FK の `ondelete`・ORM の `cascade`・明示的な削除処理
4. 外部ストレージ（写真など）の扱い — 消すのか、残すのか、後で掃除するのか
5. 削除後の参照 — 一覧・詳細から見えなくなるか、404 になるか

### D. ローカル環境での動作

1. 外部サービスを抽象化している境界（interface・Protocol・依存性注入）
2. 本番用の実装（`integrations/` など）
3. ローカル・テスト用のスタブ実装（例: backend `pins/dev_storage_router.py`、mobile `services/<名前>/*.mock.ts` / `*.dev.ts`）
4. どちらを使うかを切り替える箇所（backend `config.py`・環境変数・DI の組み立て、mobile `services/<名前>/index.ts`）
5. ローカルでの確認手順があるか（`packages/backend/docs/local-development.md` など）

「ローカルで外部サービスなしに動くか」への答えを、切り替え箇所の `file:line` とともに出す。

### E. 外部呼び出しの失敗

1. 外部呼び出しの箇所
2. タイムアウト・リトライ・例外の捕捉
3. 失敗がユーザー（API レスポンス・画面）にどう見えるか
4. 途中まで進んだ処理の後始末

### F. 認可

1. 認証依存（`dependencies.py` など）がどのエンドポイントに付いているか
2. 所有者チェック・権限判定の箇所
3. 他人のリソース ID を指定したときの挙動（403 / 404）
4. 認可のテスト

### G. API の契約

1. router のシグネチャ・ステータスコード
2. リクエスト / レスポンススキーマ
3. エラー時のレスポンス
4. 再生成された OpenAPI・Orval 生成物（中身は読まず、何が変わったかだけ）
5. 既存クライアント（mobile）側の追従

### H〜P

上の型に倣い、「入口 → 判断・処理の本体 → 結果が表れる場所 → テスト」の順に組む。
M（テスト）では `diagram-recipes.md` のレシピ5（テスト観点の表）を使う。
P（横展開）では `repeated.json` の `representative` を1件精読し、`others` を**全件ファイル名で**示したうえで、例外があれば挙げる。
