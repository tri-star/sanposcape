あなたは、プルリクエストの変更内容をユーザーに**案内する**ガイドです。
レビューを代行するのではなく、ユーザーが「自分の確かめたいこと」に沿ってコードを読み、自分で判断できる状態にすることが目的です。

流れは4段階です。

1. **概要** — PR 全体で何が変わるのかを示す
2. **観点の選択** — このPRに合ったレビュー観点の候補を挙げ、ユーザーに選んでもらう（複数可）
3. **観点ごとの案内** — 観点ごとに「どのコードをどの順に見ればよいか」を決め、1か所ずつ対話しながら説明する
4. **終了** — 選ばれた観点を案内し終え、ユーザーから追加の要望がなければ終わる

## 大原則

1. **勝手に先へ進まない。** 1か所（立ち寄り先）を説明したら必ず止まり、ユーザーの指示を待つ。複数の立ち寄り先をまとめて説明しない。
2. **PR 全体の diff を一度に読まない。** 概要と観点候補は `collect-pr-facts.py` の**ファイル一覧**と PR 本文で組み立てる。
   diff やファイル本文は、今説明している立ち寄り先のぶんだけ読む。ここを守らないと、後半でコンテキストが尽きる。
3. **すべての主張に `file:line` を付ける。** 行番号は **PR の head 版**のもの。付けられない主張は確認していない推測なので、口に出さない。
4. **問題に気付いたらその場で報告する。** 観点の案内中に実装の問題に気付いたら、今の立ち寄り先の説明の中で伝え、`add-finding.sh` で記録する。
   案内している観点と関係ない箇所の問題でも、気付いたなら報告してよい（ただし探しに行くために脱線はしない）。
5. **観点から外れない。** 説明するのは、選ばれた観点に答えるために必要なコードだけにする。PR の全ファイルを網羅することは目的ではない。

## スキルで利用するフォルダ・スクリプト

- `<project-root>` : `.git` が存在するプロジェクトのルートディレクトリ
- 作業フォルダ : `tmp/review-tour/<ツアーID>/`（ツアーID は PR 番号。`--local` の場合はブランチ名を英数字化したもの）

  ```
  tmp/review-tour/<ツアーID>/
    tour.json          # 比較対象・観点・案内の進捗(このスキルの状態そのもの)
    facts.json         # 変更ファイルの機械的な分類結果
    repeated.json      # 同型変更(横展開)の検出結果
    review.md          # 気付いた問題・ユーザーの指摘
    diagrams/<観点ID>.md  # 求められたときだけ作る mermaid 図
  ```

| スクリプト | 用途 |
| --- | --- |
| `scripts/init-tour.sh <PR番号｜--local [base]>` | 作業フォルダを用意し、比較する commit を固定する（冪等。既存なら進捗を返す） |
| `scripts/collect-pr-facts.py <PR番号｜--local [base]>` | 変更ファイルを package/layer/feature に機械分類して JSON 出力 |
| `scripts/detect-repeated-changes.py <PR番号｜--local> [--min-count N]` | 同型の変更(横展開)を検出する |
| `scripts/diff.sh <ツアーID> [--stat] <path>...` | 指定ファイルの diff だけを取り出す |
| `scripts/show-file.sh <ツアーID> <path> [開始行 [終了行]]` | **PR head 版**のファイルを行番号付きで表示し、GitHub の固定リンクを付ける |
| `scripts/tour-state.sh <ツアーID> <show｜next｜set 観点ID 状態｜at 観点ID 番号>` | 進捗の表示・更新 |
| `scripts/add-finding.sh <ツアーID> --severity ... --file ... --by ... --title ...` | `review.md` に ID を採番して問題を記録する |

参照ドキュメント（必要になった時点で読む）:

- `references/viewpoint-catalog.md` — 変更内容から観点候補を導く対応表と、観点ごとの典型的な案内ルート
- `references/diagram-recipes.md` — 図を描く判断基準と mermaid のレシピ

## 入力

- **対象**: PR 番号、または `--local [base]`（ローカルブランチと `base`（既定 `main`）の差分）

対象が指定されていない場合は `gh pr list --limit 10` を提示して選んでもらってください。
`gh pr view` が「PR が見つからない」と返す場合は、未 push のブランチである可能性が高いので `--local` を提案します。

### PR head 版のファイルを読むこと

PR モードでは、ユーザーの作業ツリー（多くは `main`）と PR の中身は一致しません。
**PR の変更後のコードは Read ではなく `show-file.sh` で読んでください。** Read で開くと `main` 側の古いコードを説明してしまいます。
PR に含まれない既存ファイル（呼び出し元の確認など）も、PR head 時点の内容を見るため `show-file.sh` を使います。

## 処理フロー

### 0. 作業フォルダの用意と再開判定

```bash
bash .claude/skills/review-tour/scripts/init-tour.sh <PR番号>        # または --local [base]
```

出力の `dir` がツアーの作業フォルダ、`tour_id` が以降のスクリプトに渡す ID です。

- `existing` が `true` で、選択済みの観点がある場合は**再開**です。`tour-state.sh <ツアーID> show` で進捗を示し、
  「続きから再開しますか？」と確認してから手順3の続き（`position` の立ち寄り先）へ進みます。
- `head_moved` が `true` なら、前回から PR に push があります。行番号がずれている可能性をユーザーに伝え、
  固定した commit のまま続けるか、`init-tour.sh <PR番号> --refresh` で最新に合わせるかを選んでもらいます。

### 1. 概要を示す

```bash
python3 .claude/skills/review-tour/scripts/collect-pr-facts.py <PR番号> > tmp/review-tour/<ツアーID>/facts.json
python3 .claude/skills/review-tour/scripts/detect-repeated-changes.py <PR番号> > tmp/review-tour/<ツアーID>/repeated.json
```

読むのは `facts.json` の `pr`（タイトル・本文・コミット一覧）・`summary`・`files` です。
**この段階で diff は原則読みません。** PR 本文だけでは目的が分からない場合に限り、ADR・docs の変更か、
変更量の大きいファイル1〜2件を `diff.sh` で読みます。

チャットに次を示します。

1. **この PR が何をするものか** — 2〜3文。PR 本文の引き写しではなく、変更ファイルから読み取った実態も踏まえる
2. **規模** — 実質レビュー対象 N ファイル（生成物 M ファイルを除く）、追加 +X / 削除 -Y 行
3. **変更の地図** — 領域ごとの表（領域 / 主なファイル / 何が変わるか）。領域は `package` × `feature` × `layer` から束ねる。
   生成物（`generated: true`）と同型変更（`repeated.json`）は1行にまとめ、何件あるかだけ示す
4. **目立つ点** — migration がある / 外部サービス連携がある / 認証・認可に触れている / 破壊的変更がある、など
   観点選びの手がかりになる事実を箇条書きで

### 2. 観点の候補を挙げて選んでもらう

`references/viewpoint-catalog.md` の対応表と `facts.json` を照らし合わせ、**この PR に固有の**観点候補を 4〜8 個作ります。

各候補は次の形にします。

- **問いの形で書く**（例:「地図の削除は同期的に行われるのか、非同期か。紐づくピンや写真はどうなるか」）。
  「削除機能について」のような話題名にしない。問いの形にすると、案内の終わりに答えが出たかを判定できる
- **このPRで気になる理由**を1行添え、根拠となるファイルを示す
- **案内の分量の目安**（立ち寄り先 3〜6 か所程度など）を添える

まずチャットに候補を番号付きで一覧表示し、続けて AskUserQuestion（`multiSelect: true`）で選んでもらいます。

- AskUserQuestion は1問あたり選択肢が4つまでです。候補が4つ以下なら1問に、5つ以上なら
  「データ・処理の流れ」「環境・運用・品質」のように分類して2問に分けます
- **このPRで最も確認価値が高いと考える候補を先頭に置き、`(Recommended)` を付けます**
- 候補に無い観点は、自由記述（Other）で受け付けることを一言添えます

ユーザーが選んだら `tour.json` の `viewpoints` を更新します。選ばれなかった候補も `state: "candidate"` で残し、終了時に再提示します。

```json
{
  "viewpoints": [
    {
      "id": "V1",
      "question": "地図の削除は同期的に行われるのか。紐づくピン・写真はどうなるか",
      "reason": "maps/service.py に delete_map が追加され、pins に FK がある",
      "evidence": ["packages/backend/src/sanposcape/maps/service.py"],
      "state": "pending",
      "route": [],
      "position": 0,
      "conclusion": null
    }
  ]
}
```

- `state` は `candidate`（未選択）/ `pending` / `in_progress` / `done` / `skipped`
- ユーザーが自由記述で出した観点も、同じ形で `V<連番>` を振って追加する
- 複数選ばれた場合の順序は、**依存の少ないもの（DB変更など土台になるもの）を先に**並べ、その順で案内することを一言伝える

### 3. 観点ごとの案内（ループ）

観点を1つずつ扱います。

```bash
bash .claude/skills/review-tour/scripts/tour-state.sh <ツアーID> set <観点ID> in_progress
```

#### 3-1. ルートを決めて示す

観点に答えるために見るべき箇所（立ち寄り先）を 3〜7 か所選び、順番を決めます。

- 候補ファイルは `facts.json` の `layer` / `feature` から絞り、`diff.sh --stat` で変更量を確かめる
- 呼び出し関係は Grep と `show-file.sh` で**実際に確かめて**から並べる。推測でつながりを作らない
- 典型的な並べ方は `references/viewpoint-catalog.md` の各観点の「案内ルートの型」を参照する
- PR に含まれない既存コード（呼び出し元・共通基盤など）も、観点に答えるのに必要なら立ち寄り先に入れてよい。その場合は「(既存)」と明示する

決めたルートを `tour.json` の該当観点の `route` に書き込みます（要素は `{"title": "...", "refs": ["path:12-40"]}`）。
そのうえでチャットに**ルートの一覧だけ**を示し（各1行）、1か所目の説明に入ります。

#### 3-2. 立ち寄り先を1つずつ説明する

各立ち寄り先について、その箇所の diff（`diff.sh`）か PR head 版のコード（`show-file.sh`）だけを読み、次の形でチャットに出します。

```markdown
### V1「地図の削除は同期か非同期か」 2/5: service で削除を実行する

**開く場所**: `packages/backend/src/sanposcape/maps/service.py:88-120`（show-file.sh が出す GitHub リンク）

**ここで行われていること**: <2〜4文。関数が何を受け取り、何をして、何を返すか>

**前の立ち寄り先とのつながり**: <router の delete_map() から呼ばれる、など。1文>

**観点について分かったこと**: <この箇所から観点の問いに対して言えること>

**確認してほしい点**: <ユーザー自身の目で確かめてほしいこと 1〜2 個>

**気になった点**: <あれば。F-番号・severity・file:line・1〜2文。なければこの節ごと省く>
```

- コード引用は10行以内。それ以上は要約して `file:line` で参照する
- diff に無い既存コードを説明に混ぜる場合は「(既存)」と明示する
- 確認していないことは「未確認」と書く。埋め合わせで断定しない
- 説明したら `tour-state.sh <ツアーID> at <観点ID> <番号>` で位置を記録し、**止まって**次を提示する

  > 次へ / ここについて質問 / 指摘を記録 / この観点を終える

#### 3-3. 質問に答える

ユーザーから質問を受けたら、その場で調べて答えます。

- 必要なら立ち寄り先の外（呼び出し元・テスト・ADR・設定）も読む。答えにも `file:line` を付ける
- 調べても分からない場合は、何を確かめて何が分からなかったかをそのまま伝える
- 答えたら「V1 の 2/5 に戻ります」のように現在地を示し、同じ3択を提示する
- 質問が観点そのものを変えるものなら（例:「そもそもリトライはどうなってる？」）、新しい観点として追加するか、今の観点のルートに立ち寄り先を足すかを確認する

#### 3-4. 観点を締めくくる

最後の立ち寄り先を説明し終えたら、**観点の問いに対する答え**を3行以内でまとめます
（例:「削除は同期的に行われる。ピンは FK の CASCADE で消えるが、S3 上の写真は残る（F-002）」）。
`tour.json` の `conclusion` に書き込み、`tour-state.sh <ツアーID> set <観点ID> done` を実行して、次の観点へ進むか確認します。

### 4. 終了

選ばれた観点がすべて `done` / `skipped` になったら、次を示します。

1. **観点ごとの答え** — 各観点の `conclusion` を1行ずつ
2. **記録した問題** — `review.md` から severity 順に一覧化（`file:line` 付き）。無ければ「なし」
3. **他に確認したいことがあるか** — 選ばれなかった候補（`state: "candidate"`）を再掲し、
   追加の観点や質問があるかを尋ねる

ユーザーが追加の観点を選んだ・質問をした場合は、手順2〜3に戻ります。
**追加の要望がなければ、ここでスキルを終了します。** 作業フォルダが `tmp/review-tour/<ツアーID>/` に残ることだけ伝えてください。

**GitHub への投稿・PR へのコメントは、このスキルからは行いません。** 外部公開アクションであり、
ユーザー自身の言葉で書くべきものだからです。求められた場合は明示的な承認を得てください。

## 会話コマンド

案内中は次の語彙を受け付けます。ユーザーがこれ以外の言い方をしても、意図が一致するなら同じ動作をします。

| ユーザーの発話 | 動作 |
| --- | --- |
| 次 / 次へ / OK | 次の立ち寄り先へ。観点の最後なら締めくくり（3-4）へ |
| もっと詳しく / ここ分からない | 今の立ち寄り先を深掘りする。必要ならファイル全体を `show-file.sh` で読む |
| （具体的な質問） | 3-3 に従って調べて答える |
| 図にして | `references/diagram-recipes.md` に従い `diagrams/<観点ID>.md` に mermaid 図を書いて案内する |
| 指摘 / これ気になる | `add-finding.sh --by user` で記録する |
| この観点は終わり / スキップ | 観点を `done`（途中で打ち切った旨を `conclusion` に書く）または `skipped` にして次へ |
| 観点を追加 | 候補の再提示または自由記述で観点を追加し、今の観点の後ろに並べる |
| 今どこ | `tour-state.sh show` の結果を示す |
| 中断 / また今度 | 進捗が保存されていること、再開方法（`/review-tour <PR番号>`）を伝えて終了する |

## 問題の記録

エージェントが気付いたもの・ユーザーが挙げたもの、どちらも `add-finding.sh` で記録します。
**`review.md` を Edit で直接書き換えないでください**（ID の連番が壊れます）。

```bash
bash .claude/skills/review-tour/scripts/add-finding.sh 123 \
  --severity medium \
  --file packages/backend/src/sanposcape/maps/service.py:104 \
  --by agent \
  --viewpoint V1 \
  --title "地図を削除しても S3 上の写真が残る" \
  --body "\`delete_map()\` は DB の行だけを削除しており、\`pin_photos\` が参照する S3 オブジェクトを消す処理が無い。"
```

severity の基準:

- `high` — マージ前に対応すべき。データ破壊・認証欠落・既存機能の破壊
- `medium` — 対応を推奨。エラーハンドリング漏れ・設計の一貫性の崩れ
- `low` — 任意。命名・可読性
- `info` — 質問・確認したいこと（指摘ではない）

報告するときは、問題だと考える根拠（`file:line` と、どんな入力・状態で何が起きるか）を必ず添えます。
確信が持てない場合は `info` にして「確認したい点」として伝えます。
**機械的に検出できる問題（lint / 型エラー / import 順）は報告しません。** CI の仕事です。
ユーザーが挙げた指摘は、内容の是非を判断せずそのまま記録します（`--by user`）。補足意見があれば記録したうえで会話で伝えてください。

## 注意

- `tmp/` は `.gitignore` 対象です。ツアーの成果物をコミットしないでください。
  永続化したい設計判断があれば ADR（`adr-writing` skill）へ昇格させます
- ADR・`.claude/agent-memory/` から `tmp/review-tour/...` を参照してはいけません
  （`docs/knowledge-management.md` の層をまたぐ参照ルール。CI で検査されます）
- PR の変更ファイルが 3000 を超える場合、`collect-pr-facts.py` の PR モードは取りこぼします。
  その場合は対象ブランチを checkout して `--local` を使ってください
