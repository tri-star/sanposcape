# 文書の確認観点

`doc-maintainer` が読む。変更によって、ADR 以外の文書の記述が古くなっていないかを確かめる。
ADR との整合（設計判断に反していないか、追補が要るか）は `change-reviewer` の担当なので、ここでは扱わない。
CI（`scripts/knowledge/check-doc-references.py`）が機械的に見るのは、インラインのリンク、ルート相対（`packages/`・`docs/`・`scripts/` など）か `./`・`../` で始まるインラインコード単体のパス、`pnpm --filter` の package と script だけ。
package 相対のパス（`src/...`・`app/...` など）、コマンドの形のインラインコード、コードブロック内のパス、参照形式のリンクは CI が見ないので、ここで確かめる。

## 対象の文書

- `README.md`、`AGENTS.md`、`CLAUDE.md`
- `docs/**/*.md`（`docs/adr/` を除く）
- `packages/*/AGENTS.md`、`packages/*/README.md`、`packages/*/docs/**/*.md`（`packages/*/docs/adr/` を除く）
- `.claude/skills/**`、`.claude/agents/*.md`（ハーネスの変更や、手順・コマンド・パスが変わったとき）
- `.github/workflows/*.yml` のコメント、`scripts/**` の使い方の説明

## 探し方

文書を順に読むのではなく、差分から語を拾って逆引きする。

1. 差分から、変わった名前を拾う: ファイル・ディレクトリのパス、関数・クラス・コンポーネント名、コマンド・スクリプト名、
   環境変数・設定キー、API のパスとフィールド、テスト ID、CI のジョブ名、skill / agent 名
2. それぞれを `grep -rn` で対象の文書から探す。改名・削除なら旧名で、挙動の変更なら機能名でも探す
3. 当たった箇所を読み、変更後の動作と食い違っていないかを確かめる
4. プラン（`plan.md`）の「更新する文書」に挙がっている文書が、実際に更新されているかを確かめる
5. 設定・インフラの変更で書き換えた記述が、デプロイ前の時点で正しい時制か（「反映済み」「〜になっている」と書いていないか）を確かめる。マージとデプロイの間に読まれても誤解されないこと（SS-217 で見落とした）
6. LP にページ（恒久 URL）を足したら、`packages/lp/docs/deployment.md` の確認項目（`curl -sI`）に載っているかを確かめる。受け入れ条件の「本番で 200」を手順どおりに確かめると漏れる（SS-214 で見落とした）
7. プライバシーポリシー・規約の節を足して番号がずれたら、旧番号（例: `1-6`）で台帳・`docs/app-privacy-label.md`・skill の参照資料（`.claude` と `.agents` の両方）を grep する。番号は見出しの id ではなく本文で参照されるので、リンク切れの検査では見つからない（SS-220 で見落とした）
8. 文書の記述を削る・見出しを変える差分では、その文書名で grep して、コードのコメント・ADR・参照資料・agent-memory が引いている節名・文言が残っているかを確かめる。あわせて、削った規則が ADR・他の文書・コードに一次記録を持つかを確かめる（CI は節名の引用を見ない。SS-201 で削りすぎた規則がレビューで見つかった）
9. 正本（台帳・runbook など）の条件・数値を変える差分では、その条件を言い換えて写している箇所（ADR の要約・持ち越し・本文、`docs/app-privacy-label.md` など）を、変更前の条件の語（例: 「上げてから消す」）で grep して揃っているかを確かめる。リンクではなく言い換えなので、正本だけ直すと食い違う（SS-231 の再レビューで見つかった）
10. 運用の規則（いつ・何をするか）を変える差分では、その規則を案内する文言を、文書だけでなくワークフローの `::error::` の文言とコメントからも探す。
   エラーの案内は失敗したときに人やエージェントがそのまま従う手順なので、古いままだと新しい規則に反する行動を誘導する
   （SS-230 で、OTA の fingerprint 不一致の案内が「version を上げてストアで配布」のまま残っていた）

## 指摘の分類

- **文書の更新漏れ**: 変更後の動作・手順・設定・パスと記述が食い違う
- **実装の不具合の疑い**: 文書の記述（受け入れ条件・合意した振る舞い）の方が正しく、実装が外れているように見える
- **未確認**: 外部サービス・実機など、手元で確かめられない

## 指摘にしないもの

- 言い回しや書式の好み
- その文書に従った人やエージェントが誤った行動をとらない程度の不正確さ
- 今回の差分と無関係な、以前からの古い記述（後続課題の候補として最後に別枠で挙げてよい）
- `packages/*/docs/folder-structure.md` に、追加したファイル・関数・エンドポイントが載っていないこと。この文書は大まかな構造と配置のルールだけを持つ（SS-201）。新しいディレクトリ・配置のルールが増えた、または既存の記述と食い違うときだけ指摘する

## 守ること

- 永続する文書（docs・ADR・agent-memory）から `tmp/` を参照していないか（`scripts/knowledge/check-tmp-references.sh`）
