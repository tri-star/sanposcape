## 考え方

- **分けるのは層ではなく観点。** backend / mobile のように層で担当を分けると、API 契約のずれや、mobile 側が認証の前提を崩すといった
  層の境目の問題がどのレビュアーの担当にもならない。そのため基本のレビュアーは1体で変更全体を見る。
- **黙って飛ばせない形式にする。** 1体に多くの観点を持たせると、目立つ指摘を見つけた時点で残りの観点を流しがちになる。
  観点ごとに「何を確認したか／問題なしならその根拠」を必ず出力させる。
- **指摘は反証してから返す。** 「本当に問題が起きるか」（どの入力・状態・実行順で壊れるか）を確かめたものだけを指摘にし、確かめられなかったものは「未確認」として分ける。
- **レビュアーは読むだけ。** 編集・コミット・外部への投稿・サブエージェントの起動はさせない。修正はメインが行う。

## レビュアーの構成

| レビュアー | 起動する条件 | 見るもの |
| --- | --- | --- |
| `change-reviewer` | 毎回 | 変更全体・プラン・関連する ADR。要求との一致、層をまたぐ契約、設計と責務、正しさ、テスト、ADR との整合 |
| `doc-maintainer` | 毎回（`change-reviewer` と並列） | ADR 以外の文書（AGENTS.md・docs・README・skill / agent の定義）が、変更後の動作を正しく説明しているか |
| `security-reviewer` | 差分が下の「security の条件」に当たるとき | 変更全体を security の観点で見る |

誤字や書式だけの変更なら、レビュアーを起動せずメインが確認してよい。

### security の条件

差分が次のどれかに触れるとき、`security-reviewer` を追加で起動する（迷ったら起動する）。

- 認証・認可: ログイン・トークンの発行と検証・セッション、所有者の確認（他人のデータに届くか）、認証モードの切り替え
- 入力の扱い: リクエストのスキーマと検証、ファイルのアップロード、URL・ディープリンク・ルートのパラメータ、外部から受け取る値を SQL・シェル・HTML に渡す箇所
- 外部への公開範囲: 新しいエンドポイント、CORS、CloudFront・S3・Function URL の公開設定、CSP、ログや応答に出す情報（個人情報・内部 ID）
- 秘密情報: 環境変数・SSM・Secrets Manager・鍵、端末への保存（SecureStore / AsyncStorage）、CI の認証情報

観点別のレビュアーは今は security だけ。他の観点で取りこぼしが続いたら、ここに条件と agent を足す。

## 手順

1. **比較対象を決める。** PR なら base との merge-base から、ローカルならコミット済みの差分・未コミット・新規ファイルを区別して決める。対象のコミットを記録する。
2. **レビュアーを起動する。** 上の表に従い、並列で起動する。依頼文には次を書く（会話の文脈は引き継がれないので明示する）。
   - 要求: 課題の要点と受け入れ条件、`<task-root>/plan.md` と `<task-root>/handover-notes.md` のパス（あれば）
   - 比較対象: ブランチ・コミット範囲（例: `git diff <base>..HEAD`）
   - 差分の領域と、読むべき参照資料（下記）
   - 実施した検証とその結果
   - 実装者の結論や「ここは問題ない」といった誘導は書かない。実物を確かめさせる
3. **結果を保存して判断する。** 結果を `<task-root>/review.md` に保存する。指摘ごとに対応の要否を推奨案で判断し、判断と理由を `handover-notes.md` に記録する（承認は待たない）。
   - 依頼の範囲内の確かな不具合は、メインが直して関連する検証を行う。
   - 仕様の選択が要るものは、推奨案で進めたうえで選択肢と影響を記録し、PR の申し送り事項に載せる。
   - 根拠のない好みや、今回の変更と無関係な既存の問題は必須の修正にしない（後続課題の候補として記録してよい）。
4. **再レビューは絞る。** 直した箇所と未解決の論点だけを、同じレビュアーに続けて依頼する（`SendMessage` で同じエージェントへ）。懸念が解消したら終える。全観点のレビューを毎回やり直さない。
