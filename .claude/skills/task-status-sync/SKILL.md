## 目的

プロジェクト管理ツール上のタスクの状態(ステータス)が、実際の開発の進み具合とズレるのを防ぐスキルです。「着手したのにTodoのまま」「PRを作ったのにレビュー待ちに変わっていない」「マージ後も進行中のまま」といった、地味だが積み重なると状況把握を難しくするズレを解消します。

## このスキルが前提にしないこと

どのプロジェクト管理ツール(Plane、Jira、Linearなど)を使っているか、そのツール固有の状態名・状態ID・カスタム属性名は、このスキル自身では決め打ちしません。これらの知識は「[専門エージェントを探す](#専門エージェントを探す)」で見つけた専門エージェントに委ねます。理由は、プロジェクトによって使うツールも状態の呼び方も異なるため、ここで固定してしまうとプロジェクトを跨いで使い回せなくなるからです。

## パラメータ

- `<task-id>` : 対象タスクのID(例: `TCH-123`)。呼び出し元のスキルが会話文脈や作業ディレクトリ名などから特定して渡してください。渡されていない、あるいは特定できない場合はユーザーに確認してください。
- `<trigger>` : 状態遷移のきっかけ。次のいずれか。
  - `start` : タスクに割り当てられた作業に着手する時
  - `pr-created` : PRを作成した時
  - `review-fix` : PRレビューの指摘を受け、修正作業に入る時
  - `pr-merged` : PRがマージされた時
- `[pr-url]` : `pr-created` / `pr-merged` の場合に関係するPRのURL。省略された場合の扱いは各トリガーの説明を参照してください。

## 専門エージェントを探す

まず、その場で利用可能なエージェント一覧の中から、プロジェクト管理ツールを操作できる専門エージェントを探してください。「プロジェクト管理ツールを操作する」「WorkItem/Issueの作成・更新・検索を行う」といった説明を持つエージェントが該当します(このプロジェクトでは実際に探すと `plane-project-manager` に行き着きますが、それを最初から決め打ちで呼び出すのではなく、毎回この手順で探してください。ツールが変わった場合や別プロジェクトでもそのまま使い回せるようにするためです)。

見つからない場合は、ユーザーに「プロジェクト管理ツールを操作する専門エージェントが見つかりませんでした。どのツールを使っていますか?」と確認してください。

以降の状態更新・コメント追加・URL紐付けは、すべてこの専門エージェントに依頼してください。ツール固有の状態ID・プロパティ名の判断も専門エージェント側に任せ、このスキルの中では「進行中に相当する状態」「レビュー待ちに相当する状態」「完了に相当する状態」という抽象的な言い方で依頼してください。

## トリガーごとの処理

### `start` / `review-fix` : 進行中に相当する状態へ更新

専門エージェントに、`<task-id>` のタスクを「進行中(Inprogressに相当)」の状態に更新するよう依頼してください。`review-fix` の場合は、単なる着手ではなく「PRレビュー対応のための再着手」である旨を一言添えてください。専門エージェント側がコメント追加などに活用できる場合があります。

### `pr-created` : レビュー待ちに相当する状態へ更新 + PR URLの紐付け

1. `[pr-url]` が渡されていない場合、`gh pr view --json url --jq .url` で直近作成したPRのURLを取得してください。取得できない場合はユーザーに確認してください。
2. 専門エージェントに以下をまとめて依頼してください。
   - `<task-id>` のタスクを「レビュー待ち(Reviewに相当)」の状態に更新する
   - タスクにPRなど外部URLを保持できる属性(URL型・Link型のプロパティなど)が存在するか確認したうえで、存在すればそこにPRのURLを設定し、存在しなければタスクへのコメントとしてPRのURLを追記する(どちらの方法を採ったかも含めて依頼する)
3. 専門エージェントからの報告(状態更新の結果、URLをどちらの方法で記録したか)をユーザーに伝えてください。

### `pr-merged` : 完了に相当する状態へ更新

マージされていないのに完了扱いにしてしまう誤検知を避けるため、状態を更新する前に必ず実際のマージ状況を確認してください。

1. `[pr-url]` が渡されていればそのPRに対して、渡されていなければユーザーに確認したうえで対象PRに対して `gh pr view <pr-url> --json state,mergedAt` を実行してください。
2. `state` が `MERGED` でない場合は状態更新を行わず、現在のPRの状態をユーザーに伝えて終了してください。
3. マージが確認できたら、専門エージェントに `<task-id>` のタスクを「完了(Done相当)」の状態に更新するよう依頼してください。マージは常に正常完了として扱い、Cancelled等キャンセルに相当する状態には変更しないでください。

## 他のワークフローへの組み込み方

このプロジェクトでは、以下のタイミングで各スキルからこのスキルを呼び出す形で組み込み済みです(該当箇所は `backend-workflow` / `frontend-workflow` / `mobile-workflow` / `task-workflow` の SKILL.md を参照)。

- `backend-workflow` / `frontend-workflow` / `mobile-workflow` が実装エージェントを初めて起動する直前 → `start`
- `task-workflow` が、指示内容にGitHubのPR番号が含まれレビュー指摘対応と判断した直後 → `review-fix`
- `task-workflow` がPR作成後 → `pr-created`(取得したPR URLを渡す)
- ユーザーから「PRがマージされました」等の報告を受けた時 → `pr-merged`(この場合、他のワークフローを経由せずこのスキルが単体で呼ばれることが多い)

新しく開発ワークフロー系のスキルを作る場合も、対応するタイミングでこのスキルを呼び出してください。
