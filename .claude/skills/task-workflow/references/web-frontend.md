# 計画

## 調べ方
- 実際のファイルを読んでから計画する。構造・命名・既存のパターンを推測で書かない。
- プロジェクトで使っていないライブラリや、存在しないファイルを計画に出さない。
- 課題の範囲を超えた変更を計画に入れない。

## 計画で決めること
- 課題の概要（1〜3文）と背景・目的: なぜ必要か、完了時にユーザー体験・技術面がどう変わるか、関連する課題・依存関係。
- 作成・編集・削除するファイルの一覧（ツリーで、各ファイルに `[新規]` / `[編集]` / `[削除]`）。
- 新規ファイル: 置き場所と目的、Props の型、export する関数・コンポーネント、内部のロジック（例: 送信処理で何を呼び、成功時に何をするか。バリデーションの条件）、使うコンポーネント・hook とその import 元。完全なコードは要らず、例や箇条書きでよい。
- 編集ファイル: 何を追加・変更・削除するか。変えないものも明記すると取り違えを防げる。
- 削除ファイル: 削除する理由と、削除前に確かめる依存。
- 実装上の注意: プロジェクト固有の規約・パターン、既存コードとの整合、エラー処理の方針、必要ならパフォーマンス。
- テスト方針: テストするケースの一覧と、参考にする既存テストのパス。

## API との境界
- OpenAPI 定義は backend が自動生成する。フロント側では更新せず、orval でクライアントコードと MSW モックを生成する。
- backend に API 設計を伝える必要があれば、計画に「backend への伝達事項」として残す。

## 計画の点検
- 計画を読んだだけで、追加の質問なしに実装を始められるか。
- すべての新規ファイルに Props の型・関数のシグネチャ・ロジックの説明があるか。編集ファイルで「何を変えるか」が具体的か。
- 使うライブラリ・コンポーネント・hook の import 元が書いてあるか。既存の規約・命名に沿っているか。
- ファイルの一覧と各ファイルの詳細が一致しているか。

# 実装

## 始める前に
- `packages/frontend/AGENTS.md` と `packages/frontend/docs/` を読み、規約・技術スタック・コンポーネントのパターン・スタイリングの方針・テストの設定を把握する（lp なら `packages/lp/AGENTS.md` と ADR-012）。

## 実装の方針
- 既存のファイル構造と命名に従い、プロジェクトで定義された TypeScript の型・インターフェースを使う。
- スタイリングの方針（CSS Modules・styled-components・Tailwind 等のうちプロジェクトが採るもの）に従う。
- アクセシビリティ（ARIA 属性・セマンティックな HTML）を確保する。
- コンポーネントでローディング・エラー・空の状態を扱う。
- 判断が要る所にだけコメントを書き、保守しやすいコードにする。

## テスト
1. 対象を分析する: props・state・イベント・ユーザー操作をすべて洗い出し、エッジケースとエラー状態を把握する。
2. テストケースを計画する: 正常なレンダリング、props のバリエーション、ユーザー操作（クリック・入力・フォーム送信）、条件付きレンダリング、エラー状態とエッジケース、アクセシビリティ。
3. 環境を用意する: `packages/frontend/docs/` のテスト方針で、使うフレームワークとユーティリティを確かめる。モック・スタブ・テストデータと、必要なプロバイダー・ラッパーを用意する。
4. 書く: 既存のパターンに従い、1テスト1つの焦点で、期待する動作を表すテスト名にする。関連するテストをまとめる。
5. 見直す: 網羅性と正確さ、テストどうしが独立しているか、抜けたエッジケースが無いか、テスト名が意味を持つか。

## 完了前の確認
- 実装がプロジェクトの規約とスタイルに沿っているか。
- TypeScript のエラーや型の不一致が無いか。
- テストが重要な経路とエッジケースを覆っているか。
- import と依存が正しく参照されているか。
