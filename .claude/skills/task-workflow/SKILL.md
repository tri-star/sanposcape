## このスキルの考え方

計画・実装・検証はメインのエージェントが直接行う。領域ごとの規約は各 package の `AGENTS.md` から辿る docs・ADR が正本で、
このスキルには書き写さない。サブエージェントは、広い範囲の調査・独立したレビュー・大量の機械的な変更の3つにだけ使う。

## パラメータ

- `[issue-id]` : 課題ID（例: `SS-123`）
- `[instruction]` : 追加の指示。GitHub の PR 番号を含み、レビュー指摘への対応を求める場合は「レビュー指摘対応」として扱う

## フォルダ

- `<task-root>` : 課題IDがあれば `<project-root>/tmp/<issue-id>`、無ければ `<project-root>/tmp/<YYYYmmdd-HHMM>`

## 進め方の原則

- **承認を待たずに推奨案で進める。** ユーザーが「プランだけ」「プラン作成まで」のように止まる位置を指定した場合だけ、そこで終える。
- **判断を記録する。** 仕様の解釈やトレードオフの選択が必要になったら、推奨案で進めたうえで、判断と理由を
  `<task-root>/handover-notes.md` に追記する。後続課題への申し送りも同じファイルに書く。PR 作成時に PR 本文の「## 申し送り事項」へ載せる。
- **止まる条件。** 同じテスト・同じ手順で3回失敗したら、それ以上の試行をやめ、起きていること・試したこと・現在の状態・推奨する次の手をユーザーに報告する。
- **ブランチ。** ブランチの作成・切り替えはメインだけが行う。サブエージェントにはブランチを触らせない（worktree を Orca で管理しており、取り違えると作業場所を失う）。

## 手順

### 1. 課題を把握する

- プロジェクト管理ツールを操作できるエージェント（このプロジェクトでは `plane-project-manager`）で、課題の本文・受け入れ条件・関連課題・コメントを取得する。
- レビュー指摘対応の場合は、`summarize-pr-comments` skill で指摘をまとめて `<task-root>/pr-review-summary.md` に保存し（既にあれば上書き）、
  `task-status-sync` skill を `<issue-id>` `review-fix` で呼ぶ。以降はこのまとめを課題の内容として扱う。
- `<task-root>` に前回のプランや申し送りがあれば読み、現状のコードと照合して再開する。

### 2. 関係する正本を読む

- 対象の領域を判断し、その package の `AGENTS.md` と、そこから辿る docs・ADR を読む。作業前に読むよう指示されているメモリ（`.claude/agent-memory/<domain>/MEMORY.md`）も読む。
  - backend: `packages/backend/AGENTS.md`
  - mobile: `packages/mobile/AGENTS.md`
  - Web フロントエンド: `packages/lp/AGENTS.md`。補助として [Web フロントエンドの参照資料](references/web-frontend.md)（React 前提の旧資料。lp の正本と食い違えば正本に従う）
  - インフラ・CI: 対象の設定ファイルと関係する ADR
- 読む範囲が広い調査（既存の類似実装を探す、影響範囲を洗い出すなど）は、Explore エージェントを並列で使ってよい。結論だけを受け取る。

### 3. プランを書く

`<task-root>/plan.md` に短く書く。シグネチャや Props 型までは書かない（実装中にコードを読んで分かった事実と食い違い、手戻りになるため）。

- **方針**: 何をどう変えるか、採らなかった案とその理由
- **影響範囲**: 変えるファイル・モジュール、API / データの契約
- **更新する文書**: 変える名前・コマンド・パス・設定キーで grep し、記述が古くなる文書を列挙する
- **完了条件**: 受け入れ条件と、通すべき検証
- **判断の記録**: 迷った点と選んだ案

複数の領域にまたがる場合は、依存の順序（backend のスキーマ → OpenAPI の出力 → Orval の再生成 → クライアントの実装）をプランに書く。

「プランだけ」の指示ならここで、プランの要点をユーザーに提示して終える（手順4以降は行わない。`<task-root>` は後続の実装で使うので残す）。

### 4. 実装する

- `task-status-sync` skill を `<issue-id>` `start` で呼ぶ（レビュー指摘対応では不要）。
- メインが実装・テスト・動作確認を行う。コマンドの実行方法は各 package の docs に従う。`.env` が無ければ `local-env-setup` skill を使う。
- 区切りごとにコミットする（[Git コミットに関するガイドライン](../../../docs/git-commit-guideline.md)）。
- 意図が明確で量の多い機械的な変更（多数のファイルへの同じ置き換え、生成物に合わせた追随など）だけは、
  [委譲のテンプレート](references/delegation.md) に従って Sonnet のサブエージェントに任せてよい。
- プランから外れる判断をしたら、`plan.md` と `handover-notes.md` を更新する。

### 5. レビューを受ける

`change-review` skill に従う。基本のレビュアー `change-reviewer` と文書の乖離を見る `doc-maintainer` を並列で起動し、
差分が条件に当たれば観点別のレビュアー（`security-reviewer` など）も追加する。
指摘への対応と再レビューの範囲も同 skill に従う。

### 6. PR を作る

- テストが通り、変更がすべてコミットされていることを確かめて push し、PR を作る。
  - `handover-notes.md` があれば、内容を整理して PR 本文の末尾に「## 申し送り事項」として載せる。
  - レビュー指摘対応では新しい PR を作らず、既存の PR のブランチへ push する。
- PR の作成（またはレビュー指摘対応の push）の後、`mobile-pr-verification` skill を `<PR番号>` `<issue-id>` で呼ぶ。
  mobile の画面変更を含む場合だけ、エミュレータで確認してスクリーンショットを PR にコメントで添付する（判定と省略の条件は同 skill にある）。
  省略された場合も止めず、省略した旨と理由を最終報告に含める。スクリーンショットは `<task-root>` に置くので、手順8より前に行う。
- `task-status-sync` skill を `<issue-id>` `pr-created` `<PRのURL>` で呼ぶ（レビュー指摘対応でも push 後に呼び、レビュー待ちへ戻す）。

### 7. 知識を収穫する

- `knowledge-harvest` skill を `<issue-id>`（無ければ `<task-root>` のディレクトリ名）と「自動モード（task-workflow から呼び出し、PRあり）」で呼ぶ。
  決定事項の ADR への転記、agent-memory の仕分け、ベースラインの更新をコミットして PR へ push し、`<task-root>` と `tmp/<PR番号>-comments.md` を削除するところまで、承認を待たずに行う。
  - 手順6で `handover-notes.md` を PR 本文に反映した後に行う（収穫の後では tmp が消えている）。
  - 手順6の状態更新の後に行う（その過程で追記されたメモリも仕分けの対象に含めるため）。
- 収穫の結果（追補した ADR、昇格・削除・統合したメモリの内訳、削除した tmp）を `gh pr edit` で PR 本文の末尾に「## 知識の収穫」として追記する
  （レビュー指摘対応では既存の節に追記する）。収穫したものが無ければこの節は省く。

### 8. 作業記録をコミットして終える

- 未コミットのまま残ったエージェントの作業記録をコミットし、PR へ push する。
  対象は `.claude/memory-access-log/` 配下（メモリの本文を読むたびにフックが追記するアクセスログ）と、手順7以降に追加・変更された `.claude/agent-memory/` 配下のファイル。
  アクセスログはセッションごとの追記専用ファイルなので、今回のセッションに限らず配下の未コミットファイルをすべて含めてよい。
- この手順をワークフローの最後の操作とし、以降はメモリを読まない（読むとアクセスログが再び未コミットで残る）。最終報告は手元の情報だけで行う。
- コミット後、`git status --porcelain -- .claude/agent-memory .claude/memory-access-log` の出力が空で、`<task-root>` が存在しないことを確かめて終える（`tmp/` は `.gitignore` 対象のため `git status` には現れない）。
