## 目的

チケットで生まれた知識を、**文脈が残っているうち**に正しい層へ振り分けるスキルです。

定期的な棚卸し（`knowledge-review`）でも同じ仕分けはできますが、他人が書いた古いメモを
文脈なしで判断することになり精度が落ちます。チケットの作業を終えた直後(PR作成直後)が最も精度が高いため、
ここで仕分けを終わらせ、定期棚卸しは取りこぼしの回収に徹させます。

また、収穫したADR追補・メモリの変更を実装と同じPRに含めてレビューを受けられるようにするため、
原則としてマージ前に `task-workflow` から実行します。

前提となる3層モデルと front-matter 規約は [知識の置き場所ガイドライン](../../../docs/knowledge-management.md) を参照してください。

## パラメータ

- `<task-id>` : 対象チケットのID（例: `SS-42`）。渡されていない場合は、現在のブランチ名や
  `tmp/` 配下のディレクトリ名から推測し、ユーザーに確認してください。
- `[auto]` : 自動モードで実行するかどうか(後述)。

## 実行モード

| モード | 呼び出し元 | 承認 | コミット先 |
| --- | --- | --- | --- |
| **自動モード** | `task-workflow` のPR作成後(マージ前) | **取らない**。Step 3 の削除・統合、Step 4 の `tmp/` 削除も確認なしで実行する | 現在のPRのブランチにコミットし push する |
| **対話モード** | ユーザーからの直接指示、`task-status-sync` の `pr-merged` | Step 3・Step 4 の実行前にユーザーの承認を得る | PRがマージ済みの場合は、元のブランチではなく最新の `main` から新しいブランチを切ってコミットし、PRを作成する |

呼び出し元が `task-workflow` である、または `auto` が渡された場合は自動モード、それ以外は対話モードです。

自動モードで承認を省くのは、`task-workflow` を未コミットの作業記録や `tmp/` を残さない状態で完了させるためです。
agent-memory・ADR は git 管理下でPRのレビュー対象になるため、誤った削除・統合はレビューで気づけ、復元もできます。
その代わり、何を削除・統合したかは必ず報告に含め、呼び出し元がPR本文に残せるようにしてください。

## 手順

### Step 1: 対象を集める

以下を読み込み、このチケットで何が生まれたかを把握します。

```bash
ls tmp/<task-id>/                                   # プラン・レビュー結果・引き継ぎメモ
git log --oneline origin/main..HEAD                 # このチケットのコミット
git diff --name-only origin/main...HEAD -- .claude/agent-memory docs/adr
grep -rl 'source_issue: <task-id>' .claude/agent-memory
```

`tmp/<task-id>/` が存在しない場合でも、agent-memory 側に `source_issue: <task-id>` の
メモリが残っていることがあります。両方を対象にしてください。

### Step 2: 決定事項を ADR へ

`tmp/<task-id>/` のプラン・レビュー結果・引き継ぎメモを読み、**「なぜそう決めたか」に当たる記述**を
洗い出します。特に次のものは ADR に残す価値が高いです。

- 採用した設計と、**却下した代替案とその理由**
- しきい値・上限値・タイムアウトなどの数値と、その根拠
- 「今回はスコープ外」と判断したものと、その判断理由
- 既存 ADR の前提を変える結論

該当するものがあれば `adr-writing` skill を呼び出し、**既存 ADR への追補を優先**して記録します
（新規 ADR を作るかどうかの判断基準も `adr-writing` skill 側にあります）。

決定事項が一つも無いチケット（軽微な修正など）もあります。無理に ADR を作らないでください。

### Step 3: agent-memory を仕分ける

`source_issue: <task-id>` を持つメモリ、およびこのチケットで追加・変更されたメモリについて、
1件ずつ次を判断します。

| 判断 | 条件 | 処理 |
| --- | --- | --- |
| **昇格** | 他のチケットでも再利用できる手順・落とし穴 | `scope: durable` に変更。`type: project` なら `metadata.adr` に Step 2 の ADR を設定 |
| **削除** | このチケット固有の進捗・状況メモ | ファイルを削除し、`MEMORY.md` の該当行も削除 |
| **統合** | 既存メモリと内容が重なる | 既存メモリに追記し、新しい方を削除。`MEMORY.md` も1行に統合 |

判断に迷ったら「**次のチケットでこのメモを読んで嬉しいか**」を基準にしてください。
「SS-42 のバックエンドは実装完了した」のような進捗の記録は、チケットが閉じた時点で価値を失うため削除します。

本文が `tmp/` を参照しているメモリは、参照先が消えるため**必ず**この場で対処します
（要点を本文に書き写すか、ADR へ昇格させて ADR を参照する）。

対話モードでは、削除・統合は元に戻しにくいため、**実行前に対象の一覧をユーザーに提示して承認を得てください**。
agent-memory は git 管理下なので復元は可能ですが、承認を挟む方が安全です。
自動モードでは承認を取らずに実行し、対象の一覧を報告に含めます。

### Step 4: `tmp/<task-id>/` を破棄する

Step 2・3 で必要な知識を移し終えたことを確認したうえで削除します(対話モードではユーザーに確認してから、自動モードでは確認せずに削除します)。

`tmp/<task-id>/handover-notes.md` など、PR本文に反映すべき内容が残っていないことも確認してください
(`task-workflow` はPR作成時に反映済みの前提で、このスキルを呼び出します)。

```bash
rm -rf tmp/<task-id>
```

`tmp/` は `.gitignore` 対象で、チケット完了後にメンテナンスされることはありません。
残しておくと必ず陳腐化し、後続のエージェントが古い情報を読むノイズになります。

PRコメントのまとめ（`tmp/<PR番号>-comments.md`）も、対応が終わっていれば同時に削除します。

### Step 5: 検査とベースライン更新

```bash
scripts/knowledge/check-tmp-references.sh
python3 scripts/knowledge/check-memory-frontmatter.py --all
```

どちらも通ることを確認します。整備によってベースラインから外れたファイルがある場合は、
指示に従ってベースラインを再生成し、**減った件数をユーザーに報告してください**。

```bash
scripts/knowledge/check-tmp-references.sh --baseline
python3 scripts/knowledge/check-memory-frontmatter.py --baseline
```

### Step 6: コミット

ADR の追加・追補、agent-memory の変更、ベースラインの更新をコミットします。
コミットメッセージは [Git コミットに関するガイドライン](../../../docs/git-commit-guideline.md) に従ってください。

コミット先はモードによって異なります(「実行モード」参照)。自動モードでは現在のPRのブランチへ push し、
変更がPRに含まれた状態にしてください。

`.claude/memory-access-log/` のアクセスログは、このスキルの実行中にも増え続けるため、ここではコミットしなくて構いません。
自動モードでは呼び出し元の `task-workflow` が最後の操作としてまとめてコミットします。
対話モードでは、報告の直前に `.claude/memory-access-log/` 配下の未コミットファイルもコミット・push し、
作業記録が未コミットのまま残らないようにしてください。

## 報告

最後に、次の内容をユーザーに報告してください。

- ADR に転記した決定事項（どの ADR に何を追補したか）
- 昇格したメモリ / 削除したメモリ / 統合したメモリの件数と内訳
- 削除した `tmp/` ディレクトリ
- ベースラインの増減（例: `tmp/ 参照 27 → 25 ファイル`）

自動モードでは、呼び出し元がこの報告をPR本文の「## 知識の収穫」セクションに転記します。
そのまま貼り付けられるよう、Markdown の箇条書きでまとめてください。
