# ADR-M-021: ピンの訪問状況とアーカイブ（表示・編集・地図からの除外）

## 日付

2026-10-04

## ステータス

採用（SS-173）。

## コンテキスト

SS-173「ピンに訪問状況（未/済）・アーカイブ状態を追加する」で、ピンに「訪問済みか（`visited`）」と「アーカイブ済みか（`archived`）」を持たせた。
目的は2つある。閉店した店などを、場所・写真を残したまま地図から隠したい（アーカイブ）。「まだ行っていない場所」を区別したい（訪問状況）。
データモデル・権限・API 契約はルート [ADR-009](../../../docs/adr/ADR-009-sanpo-map-pin-data-model-and-photo-upload.md) の SS-173 追補（決定32）に記録した。
本 ADR は mobile 側の判断（どこに出すか・誰が変えられるか・地図からどう除外するか・登録時の初期値）を記録する。

後続の SS-174（地図上のフィルター UI）はこの2つのデータを前提にする。境界は次のとおり。

| 項目 | SS-173（本チケット） | SS-174 |
|---|---|---|
| データ（`visited` / `archived`）・API | 入れる（`GET /pins` の `archived` / `visited` フィルターも backend に入った） | 使うだけ |
| 地図表示からアーカイブ済みを除外 | **常に除外（固定）** | 「アーカイブ済みも表示」を選べるようにする |
| 未訪問だけ表示など | 入れない | フィルター UI として入れる |
| 地図詳細のピン一覧 | 全件（アーカイブ済みはバッジ） | 必要なら絞り込みを足す |

## 決定

- **D1: 訪問状況・アーカイブはピン単位の boolean（`visited` / `archived`）。** 訪問状況は地図のメンバーで共有し、ユーザーごとには持たない
  （MVP の実データは owner だけ。招待後に「自分が行ったか」を個別に持ちたくなればデータ移行を伴う）。
- **D2: 地図表示（`useRegisteredPins` を使うピンタブ・散歩中のナビタブの地図）はアーカイブ済みを常に除外する。**
  `buildListPinsParams` が `archived: false` を常に入れ、backend の `GET /pins?archived=false` で絞る。端末で捨てない
  （地図ごとの上限200件をアーカイブ済みが食い、表示中のピンが減るため。ADR-M-012 D3）。`visited` は送らない。
  切り替えは SS-174 で引数化する。**そのとき `pinListQueryKey` にもフィルターを入れること**（今は常に同じ条件なので key に含めていない）。
- **D3: 地図詳細のピン一覧は除外しない。** アーカイブ済みのピンを開いて解除できる唯一の導線なので、`buildSanpoMapPinListParams` は
  `archived` を送らない。行には状態バッジを出す（既定の状態＝未訪問・未アーカイブは出さない。訪問済み → アーカイブ済みの順）。
  行の読み上げにも状態を含める（名前の直後）。
- **D4: 変更は編集画面のスイッチ + 既存の「変更を保存」（`PATCH` の差分）。** 詳細画面は表示だけ（バッジ。アーカイブ済みなら
  「地図には表示されません」の案内）。詳細からのワンタップ切り替えは持ち越す（書き込み経路を増やさず、ADR-M-017 D1・D7 の規則に揃える）。
  差分は基準値と違うときだけ送る（値が同じなら権限判定を走らせず、無用な 403 を避ける）。
- **D5: 権限の出し分け。** `canEditVisited` はメンバー全員（追加系）、`canArchive` は地図 owner かピンの作成者（持ち主判定系）。
  不明な role は従来どおり editor 扱い。権限の無い項目はスイッチを無効にし（アーカイブは理由の案内文に替える）、
  `buildPinUpdateRequest` でも差分から除く（多層防御。最終の判定は backend の 403）。backend の割り当てが変わっても
  `lib/pinPermissions.ts` の2行だけ直せばよい。
- **D6: 登録時の初期値。** 散歩中の登録（`clientWalkId` あり）は「訪問済み」、ピンタブの長押しからの登録は「未訪問」で始め、
  登録画面のスイッチで変えられる（`resolveInitialVisited`）。散歩中の登録は現地にいるので訪問済みが自然で、常に未訪問だと
  散歩で撮ったピンが全部未訪問になり SS-174 の「未訪問だけ表示」が役に立たないため。backend の既存ピンの埋め戻し
  （`client_walk_id` あり → 訪問済み）と同じ規則。破棄確認は、初期値と違うときだけ「入力あり」とみなす。
  登録画面のスイッチは名前の直後（地図の選択の前）に素の `Switch` + 案内文で置く。アーカイブのスイッチは出さない（作成時にアーカイブする操作は無い）。
- **D7: フィーチャーフラグは新設せず `pin_registration` を流用する。** 登録・詳細・編集・地図詳細はすべてこのフラグのガード下にあり、
  「ピンは出るが訪問状況だけ OFF」の状態を作る要件が無い。代わりに **backend を先にデプロイしてから mobile をリリースする**
  （古い backend に `visited` を PATCH すると `extra="forbid"` で 422）。読み取りは `=== true` で変換し、フィールドの無い古い
  backend でも「未訪問・未アーカイブ」として描く。

## 検討した選択肢

- **アーカイブ済みを地図に出したままバッジだけ付ける**: 「地図から隠す」目的を満たさないため却下（D2）。
- **端末でアーカイブ済みを捨てる**: 上限200件を食うため却下（D2）。
- **ユーザーごとの訪問状況**: 別テーブルと「誰にとっての未訪問か」の意味付けが要る。要件が見えてから決めるため見送り（D1）。
- **訪問状況の enum（`visit_status`）**: チケットが「未/済」の2値で、SS-174 のクエリも `visited=false` と素直に書けるため boolean（D1）。
- **詳細画面でのワンタップ切り替え**: 店の前では編集→切替→保存→戻るの4操作かかるが、書き込み経路が増える。使ってみて重ければ別課題（D4）。

## 決定理由

ピンの編集は ADR-M-017 で「編集画面 + 保存1回 + 保存成功で `PINS_QUERY_ROOT` を invalidate」に固めてあり、新しい項目をそこに載せるだけで
地図のマーカー（アーカイブで消える／解除で戻る）・一覧・詳細のキャッシュが既存の処理で取り直される。除外を backend の絞り込みに寄せたのは、
上限（200件）の意味を「表示対象のうち」に保つため。

## 影響

- 追加: `features/pin/lib/pinStatus.ts`（バッジ・文言・初期値の純粋関数）、`PinStatusBadges`・`PinStatusFields` コンポーネント。
- 編集画面の項目順は「名前 → メモ → 状態 → タグ → 既存の写真 → 追加する写真」（ADR-M-017 D1 の「入力欄を先にまとめる」に沿い、短い状態欄をメモの後に置く）。SS-175 で状態とタグの間に地図を追加した（[ADR-M-017 SS-175 追補](./ADR-M-017-pin-edit-and-delete.md)）。
- ADR 番号: 020 は並行して進んでいた SS-158（外部 Web ページ。ADR-M-020）が使ったため、本 ADR は 021 にした。
- SS-174 への申し送り: 「アーカイブ済みも表示」を ON にすると、`PinSummary` に `archived` が無いため地図上でアーカイブ済みを見分けられない。見分ける必要があれば `PinSummary` に足す。
- タグ候補（`GET /sanpo-maps/{id}/tags`）にはアーカイブ済みのピンにしか付いていないタグも出る（backend の集計がアーカイブ済みも数えるため。変更しない）。
- **持ち越し**: 地図上のマーカーの見た目を訪問状況で変える・詳細からのワンタップ切り替え・訪問日時の表示・保存後のトーストの出し分け・
  招待後のユーザー単位の訪問状況。検索（`q` / `tags`）に `archived=false` を付けるかは、検索を作り直すときに決める
  （今の mobile には `q` / `tags` を送る画面が無い）。
- **E2E**: `.maestro/pin-edit-delete.yaml` に「登録直後は未訪問 → 編集で訪問済み・アーカイブ → 詳細のバッジと案内 → 地図詳細の一覧に
  アーカイブ済みが残る」を足した。アーカイブで地図上のマーカーが消えることは確かめない（Google Maps の描画面のマーカーは testID で
  触れない。ADR-M-012 D14。送信条件は単体テストで担保）。
- **移行・対応が必要な事項**: backend を先にデプロイしてから mobile をリリースする。dev では列追加のため「デプロイ → migrate」の間、
  ピン系 API が数分 500 になりうる（既存のエラー表示と再試行で回復する）。dev で E2E・手動確認をするときは migrate の後に行う。
- `src/api/generated/` は Orval の生成物（gitignore 済み）。mobile CI は `openapi.yaml` の変更でも起動し、再生成して typecheck する。
