# ADR-M-022: 位置情報の権限の求め方と、拒否・大まかな位置のときの挙動（独自の事前説明画面を置かない・文脈ごとの中立な案内・前面復帰での回復・大まかな位置の案内）

## 日付

2026-10-12

## ステータス

採用（SS-160）。[ADR-M-006](./ADR-M-006-location-service-real-mock.md)（`LocationService` に `getPrecision` を追加）と [ADR-M-018](./ADR-M-018-background-walk-location-tracking.md)（大まかな位置でも点を捨てない）に追補を入れている。

## コンテキスト

App Store 申請に向けて、位置情報の「許可の求め方」「拒否されたときの挙動」「設定アプリへの誘導」「『正確な位置情報』オフのときの挙動」を見直した（App Review Guidelines 5.1.1(iv)・5.1.5・2.5.4）。審査員は「許可しない」を押して挙動を見る。ローディングが止まる、画面がブロックされる、独自の事前説明画面が許可へ誘導している、といった挙動はリジェクトの対象になる。

調べた結果、次は既に要件を満たしていた。

- OS の許可ダイアログは、現在地を使う画面（ピンタブ・散歩開始画面）を開いた時点で `useCurrentLocation` が「使用中のみ」だけを求める。独自の事前説明画面は無い。利用目的文言は [ADR-M-018](./ADR-M-018-background-walk-location-tracking.md) 決定10〜13 のとおり具体的で、契約テストで守られている。
- 拒否すると `permission_denied` になり、ローディングは必ず止まる。ナビタブ・履歴・アカウント・設定・サインイン/アウト・アカウント削除は位置情報を一切読まない。ピンタブは代替の表示範囲の地図を出し、長押しでのピン登録が使える。
- 「設定を開く」（`Linking.openSettings()`）は `permission_denied` のときに出る。
- Android は1回目の拒否が `canAskAgain=true`（`undetermined` に写る）で、2回拒否すると OS がダイアログを出さなくなる。iOS は拒否で `denied`。再要求の回数は OS が制限する。

足りなかったのは次の点。

- 拒否時の案内文が全画面で「現在地の利用が許可されていません。設定から位置情報を許可してください。」の共通文言だった。位置情報なしでも使える着地点のピンタブに、許可を迫る調子のカードが常駐していた。
- 設定アプリで許可して戻っても、「再試行」を押すまで回復しなかった。
- 「正確な位置情報」（iOS の reduced accuracy / Android の approximate）のオフを扱っておらず、大まかな位置のまま「GPS良好」と表示していた。探索の起点が数 km ずれ、散歩の軌跡・距離・歩数が実態と合わなくなりうる。

制約: expo-location 57 には、iOS の `requestTemporaryFullAccuracyAuthorization`（一時的に正確な位置を求める API）が無い（57.0.15 のソースと 57.0.16〜57.0.20 の CHANGELOG で確認）。

## 決定

1. **独自の事前説明画面（pre-prompt）は置かない。**
   - 権限は、現在地を使う画面（ピンタブ・散歩開始）を開いた時点で OS のダイアログで求める。説明は利用目的文言（ADR-M-018 決定10）が担う。
   - 将来置くなら次を守る。ボタンは「次へ」などの中立な語を1つだけにする／閉じる・あとでなどの出口を置かない／押したら必ず OS のダイアログへ進む／「許可」「位置情報を設定」などの語をボタンに使わない。
2. **拒否されても、位置を使わない機能はすべて使える状態を保つ。**
   - 位置を使う画面は案内カードを出し、ローディングで止めない。
   - 再要求は OS の `canAskAgain` と利用者の操作（再試行・画面を開き直す）だけで行う。前面復帰時などに自動で要求しない。
3. **拒否時の案内は、画面の文脈ごとに中立に書く**（`src/components/location/locationNoticeMessage.ts`。`LocationPermissionNotice` の必須 prop `context`）。
   - 何ができないか・代わりに何ができるか・設定アプリで変えられることを事実として書き、「〜してください」と迫らない。この性質は単体テストで固定する。
   - explore（散歩開始）と tracking（散歩中）は「設定アプリで許可すると使えるようになる／記録できるようになる」。map（ピンタブ）は位置情報なしで使えるので「ピンは地図を長押しして登録できます」を書く。
   - `services_disabled` など `permission_denied` 以外のコードは従来の共通文言（`locationErrorMessage`）のまま。
   - 案内カードに閉じる手段は付けない。中立な文言なら常駐しても誘導ではないと判断した。
4. **設定アプリへの誘導は `Linking.openSettings()`（アプリの設定画面）で行う。** 対象は `permission_denied` と、大まかな位置の案内の2つ。`services_disabled`（端末全体の位置情報サービスがオフ）には出さない。
   - `openSettings` が開くのはアプリの設定画面で、端末全体の位置情報の画面ではない。
   - iOS にはシステムの位置情報の画面を開く公開 API が無い。Android は `Linking.sendIntent("android.settings.LOCATION_SOURCE_SETTINGS")` で開けるが、片方の OS だけの導線になる。文言で足りる。
   - iOS は端末全体がオフでも権限が denied として返るので、iOS ではこの場合も `permission_denied` の案内になる。
5. **拒否中に前面へ戻ったら、権限の状態だけを確かめ、`granted` なら取り直す**（`useCurrentLocation`。拒否中だけ `AppState` を購読する）。
   - 確認は `getPermissionStatus`（ダイアログを出さない）だけで行い、`requestPermission` は呼ばない。Android の1回目の拒否は `undetermined` に写るので、呼ぶと前面に戻るたびにダイアログが出る（「繰り返し求める」になる）。判定は `shouldRecheckPermissionOnForeground`（`src/lib/locationRefreshPolicy.ts`）。
   - 自動回復は `retry`（非 silent）と同じ扱いで、ピンタブの地図は現在地へ移動する。許可しに行った直後なので自然な動きとして維持する。
   - `services_disabled`（端末全体のオフ）は、権限 API では検知できないため対象外にする。再試行ボタンが担う。
   - 対象はピンタブ・散歩開始（`useCurrentLocation`）。散歩中画面は対象外にする。散歩中に `permission_denied` になるのは開始後に設定で取り消したときだけで頻度が低く、既存の「再試行」で足りる。
6. **`LocationService.getPrecision(): Promise<"precise" | "approximate" | null>` を追加する**（ADR-M-006 追補）。
   - expo-location の `getForegroundPermissionsAsync` の応答を使う（iOS は `ios.accuracy === "reduced"`、Android は `android.accuracy === "coarse"` で approximate）。判定は `expo-location` を import しない純粋関数 `toLocationPrecision`（`src/services/location/locationPrecision.ts`）。
   - 未許可・確認の失敗・想定外の値のときは null か precise にして、案内を出さない側に倒す。throw しない。
   - 既存の `getPermissionStatus` の戻り値を変える案は採らなかった。呼び出し元が多く、権限と精度は別の関心事のため。
   - iOS の一時的な正確な位置の要求は API が無いので使わない。`NSLocationDefaultAccuracyReduced` は設定しない（ダイアログの既定を「正確」のままにする）。
7. **大まかな位置のときは、散歩開始画面と散歩中画面に案内を出し、散歩中のバッジを「位置が大まか」（warning）にする。** 探索も記録も止めない。
   - 精度で点を捨てない（ADR-M-018 の方針を維持する）。精度で除外すると、大まかな位置の点はほぼすべて捨てられて軌跡が空になり、距離0の散歩になる。粗い軌跡を残すほうがよい。
   - 散歩の開始を禁止しない。5.1.1(iv)（同意の強制）に近いため。
   - 保存する記録に「大まか」の印は付けない（API の変更になる）。
   - ピンタブには出さない。ピンタブの現在地は初期の表示範囲と「現在地」ボタンにしか使わず、ピンの位置は長押しで利用者が選ぶ。着地点のタブに常駐する案内を増やさない。散歩中の「この場所にピンを追加」は散歩中画面の案内で足りる。
   - 精度は hook の `useState`（`features/walk/hooks/useLocationPrecision.ts`）に置き、前面復帰のたびに確かめ直す。ストアは作らない。
8. **フィーチャーフラグで包まない。** 審査で見られる挙動（拒否時の非ブロック・中立な案内・設定への誘導）を `/app-config` の状態に依存させない。取得に失敗するとフラグは全 OFF になり、審査に必要な挙動が消えるため（ADR-M-020 と同じ考え方）。文言の修正は不具合修正にも当たる。
9. **5.1.1(iv) の「代替手段」。**
   - ピンの登録は、地図の長押しが位置情報なしの代替になる。
   - 散歩の探索・記録には代替（探索の起点の手入力など）を作らない。記録は GPS の軌跡そのものが価値で、代替が成り立たない。探索の起点だけを手入力にしても、そのまま記録へ進めず中途半端な導線になる。「可能なら」の範囲として作らない。審査で指摘されたら別課題にする。

## 検討した選択肢

- **pre-prompt を置く**: 却下。App Review は pre-prompt に厳しく、ボタンの文言が「設定を構成する」系だったこと、「あとで」などの出口があることでリジェクトされた実例がある（関連情報）。置くほど審査で突っ込まれる面が増える。ダイアログは地図の画面で使う時点に出ており、利用目的文言も具体的。
- **前面復帰時に `requestPermission` を呼ぶ**: 却下。Android の1回目の拒否は `undetermined` に写るため、前面に戻るたびにダイアログが出る。
- **精度で点を除外する**: 却下（決定7）。
- **大まかな位置のとき散歩を開始させない**: 却下（決定7）。
- **ピンタブにも大まかな位置の案内を出す**: 却下（決定7）。
- **`services_disabled` に Android の位置情報設定を開くボタンを出す**: 却下（決定4）。片方の OS だけの導線になる。
- **探索の起点を手入力にする**: 却下（決定9）。
- **散歩中画面にも前面復帰での自動回復を入れる**: 却下（決定5）。

## 決定理由

- 審査員が「許可しない」を押した後の挙動を最優先にした。ピンタブは代替の範囲の地図＋中立な案内＋長押し登録、ナビ・アカウント・設定は通常どおり、散歩開始は案内だけ、という状態を保つ。
- 回復は利用者の操作（設定アプリで許可して戻る）に沿って自動化するが、ダイアログを自動で出し直す形にはしない。
- 精度は別の関心事として独立した API にし、既存の権限の呼び出しを変えない。

## 影響

### ポジティブな影響

- 位置情報を拒否しても、位置を使わない機能がすべて使える状態が文言と挙動の両方で明確になった。
- 設定アプリで許可して戻ると、再試行なしで回復する。
- 大まかな位置のときに、「GPS良好」と実態が食い違うことがなくなる。
- 判断のルール（pre-prompt を置く場合の条件など）が残り、後から審査対応で迷わない。
- JS だけの変更で、development build の作り直しは不要（`app.json` もネイティブ依存も変えない）。ただし `version` 0.1.0 のバイナリへ `eas update` を出さない運用（ADR-M-018）は守る。

### ネガティブな影響・トレードオフ

- サインイン直後（ピンタブへの着地）に、前置きなしで OS のダイアログが出る。拒否率が上がる可能性はあるが、審査の安全を優先した。
- 大まかな位置の散歩記録は不正確なまま保存される（記録に精度の印は付けない。API の変更が要るため）。
- 散歩中に権限を取り消した場合は、再試行ボタンが要る（前面復帰で自動回復しない）。
- E2E（Maestro）は変えない。E2E は `EXPO_PUBLIC_LOCATION_MODE=mock` で権限は granted・精度は precise に固定され、新しい案内は出ず既存の testID も変わらない。権限の拒否・精度は mock では再現できず（mock は OS の権限を見ない）、Maestro の `launchApp.permissions` で拒否しても検証にならないため、フローを足さない。確認は real モードの目視（`docs/app-startup-guide.md`）で行う。

### 移行・対応が必要な事項

- 実機での確認事項（SS-161 / 実機確認）:
  - iOS の大まかな位置での背景記録（点が届く頻度、1点目が届くまでの時間、保存した軌跡・距離の見え方、案内文言が実態と合っているか）。
  - iOS で設定アプリから許可・精度を切り替えて戻ったとき、アプリが終了されずに `AppState` の `active` で回復するか（終了される場合は、再起動後の通常の流れで回復する）。
  - iOS で端末全体の位置情報サービスをオフにしたときの案内（`permission_denied` / `services_disabled` のどちらか）。
  - Android で背景記録（FGS）が coarse だけで動くこと、散歩中画面の案内とバッジ「位置が大まか」。なお Android エミュレータ（API 35）では、拒否した状態から背景で `ACCESS_COARSE_LOCATION` だけを付与して前面に戻すと、再試行なしで回復し、散歩開始画面に大まかな位置の案内が出ることを確認済み（SS-160 の PR #154）。
  - 小さい画面で散歩中画面の案内と stats パネルがはみ出さないこと（散歩中画面は ScrollView ではない）。
- App Review（SS-161）:
  - 「許可しない」を押した後の挙動で通るか確認し、指摘されたら決定9（探索の代替）と決定3（案内を閉じられるようにする）を見直す。
  - `UIBackgroundModes` の `fetch`（expo-task-manager のプラグインが足すもので、アプリでは使っていない）を、審査メモで説明するか config plugin で除去するかを決める（2.5.4）。
  - 審査メモに「位置情報を拒否しても、ピンの登録（地図の長押し）・履歴・設定は使える。散歩の記録には位置情報が必須」と書く。
