# ADR-M-017: ピンの編集・削除（編集画面の構成・保存の順序と冪等性・権限による出し分け・削除後のキャッシュ）

## 日付

2026-10-02、2026-10-04 追補（SS-173。訪問状況・アーカイブの編集）、2026-10-05 追補（SS-175。地図の変更）

## ステータス

採用（SS-119、SS-173 追補、SS-175 追補）。

## コンテキスト

SS-118 でピン詳細画面（`/pins/[pinId]`）を作ったが、編集ボタンは SS-119 の範囲として出していなかった
（[ADR-M-012](./ADR-M-012-pin-map-display-and-detail.md) D11。ヘッダー右端にスペーサーだけを置いた）。
[ADR-M-013](./ADR-M-013-pin-tag-suggestions.md) は `PinTagEditor` を「SS-119 の編集画面がそのまま使える」形にし、
[ADR-M-014](./ADR-M-014-sanpo-map-list-and-detail.md) は「ピンを消したら `SANPO_MAPS_QUERY_KEY` も invalidate する」ことを
SS-119 への申し送りにしていた。

SS-119 では、ピンの名前・メモの更新、タグの追加・削除、写真の追加・削除、ピン自体の削除を実装する。
使う API は SS-112 で実装済みの `PATCH /pins/{id}`・`DELETE /pins/{id}`・`DELETE /pins/{id}/photos/{photo_id}`・
`POST /pins/{id}/photos`。**SS-119 時点では backend の変更は不要**（権限判定に必要な情報は既存の応答に揃っている）。
地図の変更（SS-175 追補）では `PATCH /pins/{id}` に `sanpo_map_id` が追加された（ルート ADR-009 決定33）。

権限はルート ADR-009 決定19 のマトリクスに従う。要点は次のとおり。

- 名前・メモの更新とピンの削除は、地図の owner か、ピンの作成者本人（editor）。
- タグの削除は、owner か、そのタグを付けた本人。写真の削除は、owner か、アップロードした本人。
- タグの追加・写真の追加は、メンバーなら誰でも可。
- 地図の変更（SS-175）は、移動元の地図の owner かピンの作成者本人（持ち主判定系）。移動先は owner/editor（追加系）。
  移動先が無い・メンバーでないときは 404 + `code: "sanpo_map_not_found"`（ピン側の 404 は `code: "pin_not_found"`）。
- PATCH は「送ったフィールド」ごとに権限を判定する（値が同じでも送れば権限が要る）。
  タグは差分（`add_tags` / `remove_tag_ids`）で送り、再送は安全。409 の本文は `code: "tag_limit_exceeded"`。
  PATCH の404は `code` で `pin_not_found` と `sanpo_map_not_found` を区別する（SS-175）。
- DELETE は 204。削除済みは 404 で、成功扱いでよい（決定21・伝達事項）。

## 決定

- **D1: 編集は別ルート `/pins/[pinId]/edit` にする（詳細画面下部の「このピンを編集」から push）。** 詳細ルートは
  `app/pins/[pinId].tsx` から `app/pins/[pinId]/index.tsx` へ `git mv` した（pathname `/pins/[pinId]` は変わらず、
  既存の呼び出し側は変更不要）。`[pinId].tsx` と `[pinId]/` を併存させると Expo Router の解決順に頼ることになるため避けた。
  保存後と破棄後は1段戻る。
  **モック（`isEdit`）との違い**: モックは保存をヘッダー右端に置き、項目を名前 → 写真 → タグ → メモの順に並べ、
  削除もこの画面に置いている。実装は、保存を本文末尾の「変更を保存」ボタンにし（進捗・エラー・案内文を隣に出すため。
  登録画面と同じ型）、項目を名前 → メモ → タグ → 既存の写真 → 追加する写真の順にし（入力欄を先にまとめる。SS-173 追補: 状態をメモの後に追加）、
  削除は詳細画面に置いた（D6）。SS-175 追補: 地図を状態の後に追加。
- **D2: 登録画面（`PinRegisterView` / `usePinRegister` / `usePinSave`）は流用せず、部品だけ再利用する。**
  再利用: `Input`、`PinTagEditor`（任意 prop `canRemove` を追加）、`PinPhotoGrid`（任意 prop `title` を追加）、
  `usePinPhotos`（変更なし）、`runPinSave`（既存ピン向けの入口 `runAttachPhotosToPin` を追加）。
  登録側は作成（`createPin`・`savedPinId`・地図の選択・位置）と密結合しているため。
- **D3: 保存は「変更を保存」1回で、PATCH（差分）→ 写真の削除 → 写真の追加の順に行う（`runPinEditSave`）。**
  - PATCH を最初にするのは、原子的で軽く、主要な変更だから。
  - 削除を追加より先にするのは、容量（アップロード者に計上。DB 集計で即時に空く）を先に空けて、写真の差し替えで
    `quota_exceeded` になりにくくするため。
  - 各段は冪等なので、失敗後は最初からやり直す。PATCH は差分、DELETE は 404 を成功扱い、写真の追加は紐付け済みからの
    再開。写真の削除は往復を省くため、成功した id を記録する。**PATCH だけは、成功したら再送しない**（D11）。
  - 自動再試行は最大2回（通信・5xx・503・不明。指数バックオフ）。その後は手動の「もう一度保存する」。
  - 同じキーのタグを消して付け直した場合は差分ゼロにする（backend の「削除してから追加」で作成者が自分に付け替わるのを
    避ける）。代償として、表記だけの変更（`Cafe` → `cafe`）は保存されない（消して保存してから付け直す）。
    ADR-M-013 D4 の「既存の表記に揃える」とは矛盾しない。
- **D4: 既存写真の削除は保存まで保留する（削除の印・元に戻す）。** キャンセルで何も消えない、1枚ごとの確認ダイアログが要らない、
  写真の削除が PATCH と同じ保存操作にまとまる、の3点のため。写真ごとに確認して即時に削除する案は、保存とキャンセルの意味が
  写真だけ違ってしまうので採らなかった。
- **D5: 権限による出し分けは、`GET /sanpo-maps` の role + `PinRead` の作成者 ID + セッションの user id で判定する。**
  - role は `useSanpoMaps` のキャッシュを `pin.sanpo_map.id` で引く。`PinRead.sanpo_map` に role が無く、ルート ADR-009
    決定24 は `PinRead` に role や `can_edit` を足さない方針のため、backend には依頼しない。
  - user id はルートが `useAuthSessionStore` の `user.id` を読み、`currentUserId` として props で注入する
    （`features/pin` は認証ストアを import できない）。
  - SS-175 追補: 編集画面の role は詳細キャッシュの地図ではなく**基準値の地図**で引く（部分保存後に詳細キャッシュが移動前のままになるため。追補参照）。
  - **role が分からないとき（一覧が未取得・失敗・地図が一覧に無い）は editor とみなす。** `GET /pins/{id}` が成功していれば
    メンバーで、メンバーの最小権限は editor だから。UI の出し分けは UX のためのもので、安全性は backend の 403 が担保する。
  - 出し分け: 名前・メモは disabled にして案内文を出す。削除できないタグは `x` の無い静的なチップ。削除できない写真には
    削除の印のボタンを出さない。ピンの削除ボタンは権限が無ければ出さない。編集ボタンはメンバーなら常に出す
    （タグ・写真の追加は誰でもできるため）。PATCH には変更したフィールドだけを載せ、権限が無い項目は多層防御として差分から除く。
    SS-175 追補: 地図のチップは権限が無ければ押せなくし、案内文（現在の地図名つき）を出す。
- **D6: ピンの削除は詳細ヘッダー右端のゴミ箱アイコン + 確認ダイアログで行い、編集は画面下部に固定したテキストボタン
  「このピンを編集」にする。** 編集は削除より使う頻度が高いので、片手で指の届きやすい画面下部に置き、写真が多くても
  スクロールせずに押せるよう本文の外に固定する。取り消せない削除は、届きにくいヘッダー右端に置いて誤って触れにくくし、
  確認ダイアログを必ず経由する（当初はヘッダーに鉛筆の編集ボタン、本文末尾に「このピンを削除」を置いていたが、
  エミュレータで使ってみたユーザーの判断で入れ替えた）。トーストは下部のボタンと重ならないよう、その分だけ上げる。ダイアログは `WalkDeleteDialog` と同じ構成（再試行できない失敗では削除ボタンを出さない、
  削除中は閉じない）。モックは削除を編集画面に置いているが、編集画面は破棄確認・保存の進捗・エラー行で既に込み入っており、
  保存と削除（取り消し不能）が同じ画面に並ぶと誤操作しやすいため、詳細画面に分けた。404 は成功扱い。削除後は1段戻り（戻れなければ `/(tabs)`）、「ピンを削除しました」を flash で出す。
- **D7: キャッシュの扱い。**
  - 編集の成功: 写真ページ（infinite）を `resetQueries` で先頭から読み直し、`PINS_QUERY_ROOT` を invalidate する
    （詳細・地図のマーカー・地図詳細の一覧・タグ候補）。地図一覧の件数は変わらないので触らない（地図を移したときだけ SS-175 追補のとおり取り直す）。
  - 削除の成功: 詳細と写真ページを `removeQueries` してから、`PINS_QUERY_ROOT` と `SANPO_MAPS_QUERY_KEY` を invalidate する。
    **順序が仕様**: 逆にすると、消したピンの詳細を取り直して 404 を踏む。さらに、成功を同期的に表すローカルの
    フラグを `onSuccess` の先頭で立てる（mutation の success 反映前に1回描画されて詳細が取り直されるのを防ぐ）。
    詳細の query は `deleted` の間 `enabled: false` にする。
  - 保存が途中で失敗した場合: その場では invalidate しない（編集中に詳細を取り直すと既存写真と追加写真が二重に見えるため）。
    画面を離れるとき（アンマウント）に、部分的に保存済みなら invalidate する。
  - 地図を移したとき（SS-175）は `SANPO_MAPS_QUERY_KEY` も invalidate する（移動元・移動先の `pin_count`、移動先の
    `mark_used()` による並び順。部分保存のまま離れた場合も同じ）。
  - 403 は地図一覧と詳細を取り直す（role や作成者が変わった可能性）。保存・削除の両方で行う。404 は詳細を invalidate する
    （戻った詳細を not-found にする）。SS-175: PATCH の `sanpo_map_not_found` はこの 404 から除き、地図一覧を取り直す（追補参照）。
  - 編集の成功時は、invalidate の前に、PATCH の応答で詳細のキャッシュを差し替える（詳細に戻った直後に旧データと
    「ピンを更新しました」が同時に出ないようにする）。写真の段の結果は含まないが、直後の invalidate で取り直される。
- **D8: flash トーストの消費先に、ピン詳細（「ピンを更新しました」）と地図詳細（「ピンを削除しました」）を加える。**（SS-175 追補: 地図を移したときの文言は「ピンを「◯◯」に移動しました」。判定は追補の「移動したとき」を参照）
  地図詳細は flash を消費していなかった。消費しないと、文言が残って後でピンタブに遅れて出る。
- **D9: E2E（Maestro）は名前・メモ・タグの編集とピンの削除だけにする**（SS-173 追補: 訪問状況・アーカイブの確認を足した）（`.maestro/pin-edit-delete.yaml`。SS-175 追補: 地図の変更は `.maestro/pin-move-sanpo-map.yaml` に分けた）。写真は mock が
  実ファイルを返さないため対象外（ADR-M-010 決定6）。フローが作った一意な地図とピンだけを消し、共有ユーザーの他のデータは
  壊さない。地図は残る（mobile に地図の削除が無い）。保存の成功はトーストではなく画面遷移と詳細の表示で確かめる（SS-152）。
- **D10: フィーチャーフラグは新設せず、既存の `pin_registration` を流用する。** 編集と削除はピン機能の一部で、ピン系の画面は
  すべて `pin_registration` で守られており、単独で ON/OFF を分ける要件が無い（「詳細は出るが編集だけ OFF」の状態数も増やさない）。

- **D11: 部分保存の後は、PATCH の成功応答で基準値を作り直す。** 保存が PATCH 成功・写真の段で失敗のとき、基準値が編集開始時の
  ままだと、入力を元の値へ戻したとき差分が0件になり、PATCH が送られない（サーバーは新しい値のまま）。そこで PATCH の成功応答
  （最新のピン）で基準値を作り直し、以降の差分は「保存済みの状態」との差にする。あわせて次を行う（`pinEditSync`）。
  - DELETE 済みの写真は、削除の印と既存写真の表示から外す（印を外すと通常の写真に見えるのを防ぐ）。
  - PATCH 済みなら、自動再試行でも再送しない。再送すると、古いスナップショットで他のメンバーの更新を上書きしうる
    （last-write-wins）。手動の再試行は、作り直した基準値から差分を取り直すので PATCH が空になる。
- **D12: 編集画面の基準値は、詳細の再取得が終わってから確定する。** invalidate 済みの古いキャッシュで確定すると、保存して詳細に
  戻った直後に再び編集を開いたとき、保存前の値が入力欄に出る。再取得の失敗時も古い値では確定せず、エラー（再試行）を見せる。
  確定後は、バックグラウンドの再取得の失敗（`not_found` 以外）でフォームを消さない（入力中の内容が失われるため）。
- **D13: 保存は同期的なラッチで二重送信を止める。** `usePinDelete` と同じく ref を立てて、`onSettled` で解除する
  （`status` は描画を待つため、ボタンの disabled だけでは同一フレーム内の連打を取りこぼす）。

## 検討した選択肢

- 詳細画面の中の編集モード: ビューア・削除ダイアログ・戻る処理（`onIntercept`）の分岐が膨らむため不採用（D1）。
- 登録画面 `/pins/new?pinId=` の流用: 位置調整・地図の選択・`client_pin_id` の冪等作成という登録固有の前提が編集と合わないため不採用（D1・D2）。
  （SS-175 追補で、このうち「地図の選択（既定地図・draft の扱い）」だけが編集に当てはまらない前提だと整理した。部品 `SanpoMapSelector` は共用する）
- 写真ごとの確認ダイアログによる即時削除: D4 のとおり不採用。
- PATCH に全項目を毎回載せる: 値が同じでも権限判定が走り、権限の無い項目で 403 になるため不採用（D5）。

## 影響

### ポジティブな影響

- 編集画面は `PinRegisterView` と同じ「入力画面の型」（`useScreenBack` の破棄確認・保存中は戻らない・進捗・エラー行）に収まる。
- 判定・差分・基準値の作り直し・失敗の分類・エラーと進捗の文言が `lib/` の純粋関数にあり、Vitest で網羅できる
  （画面固有の案内文は、他のピン画面と同じく `.tsx` に置く）。
- 各段が冪等なので、通信が不安定でも「もう一度保存する」で安全に続きから行える。

### ネガティブな影響・トレードオフ

- 編集画面で写真を追加して破棄すると、先行アップロード済みの未使用の枠が紐付け期限（6時間）まで残る。登録画面と同じ挙動で、今回は直さない。
- 削除した写真の expo-image のディスクキャッシュはサインアウトまで残る。キーは photo.id で二度と表示されないので実害は無い。
- editor の出し分けは、招待（BK-7）が無いため実データでは確認できない（単体テストのみ）。
- 将来 editor が現れると、地図一覧を取得できないとき owner でも一時的に editor 扱いになり、他人が作ったピンの編集・削除ボタンが
  出ない。ルート ADR-009 決定24 が予定する role の露出（例: `PinRead.sanpo_map.role` を expand で足す）が入れば、この依存を外せる。
- 表記だけのタグ変更（`Cafe` → `cafe`）は保存されない（D3）。

### 移行・対応が必要な事項

- 本 ADR により、ADR-M-012 D11（編集ボタンを出さない）、ADR-M-013（`PinTagEditor` の再利用の予告）、ADR-M-014 の
  SS-119 への申し送り（`SANPO_MAPS_QUERY_KEY` の invalidate）は決着した。
- `mobile-e2e` workflow は push トリガが無いので、マージ前に手動で実行する。
- 招待（BK-7）の導入時に、ピン削除の確認文（`lib/pinDeleteError.ts` の `PIN_DELETE_DIALOG_DESCRIPTION`）を見直す。
  ピンの削除では他のメンバーが付けた写真・タグも CASCADE で消える（ルート ADR-009 決定19）が、全員 owner で
  ピンの中身がすべて自分のものである今の文言はそれを伝えていない。あわせて、editor 向けの E2E で出し分けと 403 の経路を確かめる。
- 手動で再試行できない保存の失敗（写真の削除の 403 など）は、どの写真が原因かを示さない。必要になったら `PinEditError` に
  対象の写真 id を持たせて文言に出す。

## SS-173 追補: 訪問状況・アーカイブの編集（2026-10-04）

詳細は [ADR-M-021](./ADR-M-021-pin-visit-status-and-archive.md) に記録した。本 ADR への影響は次のとおり。

- D1 の項目順を「名前 → メモ → **状態** → タグ → 既存の写真 → 追加する写真」にした（「訪問済み」「アーカイブする」のスイッチと案内文。
  `PinStatusFields`）。短い状態欄をメモの直後に置き、入力欄を先にまとめる方針は変えない。
- PATCH の差分に `visited` / `archived` を足した（`buildPinUpdateRequest`）。基準値と違うときだけ送る
  （値が同じなら backend の権限判定を走らせない。コンテキストの「送ったフィールドごとに判定」への対応）。基準値・下書きにも2項目を持つので、
  D11 の部分保存後の基準値の作り直しや、スイッチを戻したときの「未保存なし」も既存の仕組みで効く。
- D5 の権限の出し分けに2項目を足した。`canEditVisited` はメンバー全員（追加系）、`canArchive` は地図 owner かピンの作成者（持ち主判定系）。
  権限が無ければスイッチを無効にし（アーカイブは案内文を差し替える）、差分からも除く。状態（アーカイブ済み）による編集のロックは無い。
- E2E（`pin-edit-delete.yaml`）に、状態の変更と詳細のバッジ・地図詳細の一覧への残り方の確認を足した（D9 の範囲の拡張）。
- 保存成功の invalidate（D7）は変えない。地図のマーカー（アーカイブで消える／解除で戻る）・地図詳細の一覧・詳細が既存の処理で取り直される。

## SS-175 追補: 地図の変更（2026-10-05）

編集画面でピンの地図（SanpoMap）を別の地図へ移せるようにした。地図はピン登録時にしか選べず、間違えると消して登録し直すしかなく、
写真・タグ・訪問状況・作成日時が失われていたため。本 ADR への影響は次のとおり。

- D1 の項目順を「名前 → メモ → 状態 → **地図** → タグ → 既存の写真 → 追加する写真」にした（タグ候補が地図に依存するため、
  地図をタグより先に置く）。タグ候補は選んでいる地図から取る（移動先の表記に揃う。ADR-M-013 D4）。
- 地図の選択は `SanpoMapSelector`（任意 `title` を追加。編集は `title="地図"`）を再利用し、選択肢は編集専用の
  `resolvePinEditSanpoMapChoices` で作る。登録の「既定地図は `sanpo_map_id` を送らない」「最初の地図の draft」は編集に当てはまらない
  （ピンは必ずどこかの地図に属す）ため（D2 の「部品だけ再利用」の延長）。
- PATCH の差分に `sanpo_map_id` を足した（基準値と違うときだけ。D3 の順序・冪等性は変えない。PATCH 済みなら再送しない D11 もそのまま効く）。
  一覧から消えた地図・一覧が未取得・取得失敗のときは今の地図に戻して送らない。
- 権限（D5 の拡張）: `canChangeSanpoMap` は移動元の地図 owner かピンの作成者（持ち主判定系。backend の `can_move_pin_from(role, *, is_creator)`）。
  移動先は `GET /sanpo-maps` に出る全地図（owner・editor のどちらでも。backend の `can_move_pin_to(role)`＝追加系）。
  backend は移動元・移動先で2関数に分けているが、mobile は移動先の判定を候補の絞り込みで満たすので項目は1つ。
  将来 viewer 等の role が増え `can_move_pin_to` が偽になりうるなら、そのとき候補の絞り込みに条件を足す。
  権限が無ければチップを押せなくし案内文を出す。**role は基準値の地図で引く**（部分保存で移動が済んだ後は詳細キャッシュがまだ
  移動前のままで、基準値だけが移動後を指すため）。owner が editor のピンを、その editor が参加していない地図へ移すことは
  mobile では制限しない（backend が許す。制限に変わっても backend の 403 を既存の `forbidden` で表示するだけ）。
- 同じ地図 ID を送った場合 backend は移動の権限判定だけを行い変更しない（決定33）。mobile は今の地図と違うときしか送らないので影響しない。
- キャッシュ（D7 の拡張）: 移動を含む PATCH が成功したら `SANPO_MAPS_QUERY_KEY` も invalidate する（両地図の `pin_count`、移動先の `mark_used()`
  による並び順。部分保存のまま離れた場合も同じ）。`sanpo_map_not_found` は地図一覧を取り直す（消えた地図を選択肢から外し、有効な選択は今の地図に戻る）。
  それ以外（詳細の差し替え・`PINS_QUERY_ROOT`）は既存の処理で、移動元・移動先の地図表示・地図詳細の一覧・タグ候補が取り直される。
- 保存後の遷移は変えない（1段戻って詳細）。トーストは移動したとき「ピンを「◯◯」に移動しました」。移動先の地図詳細へ遷移する案は採らなかった:
  編集はピン詳細からしか入らず、詳細の下は地図詳細（移動元）かピンタブなので、移動先へ飛ばすとスタックの組み替えが要り、入口ごとに挙動が割れる。
  いま見ているのは「このピン」なので詳細へ戻すのが自然で、詳細は PATCH の応答で差し替わり地図名は即座に移動先になる。移動元の地図詳細へさらに戻れば、
  そのピンが一覧から消えているので移動したことも分かる。
- 404 は `code` で区別する（`toPinEditErrorCode`）。`sanpo_map_not_found` は新しい `PinEditErrorCode`（「移動先の地図が見つかりませんでした。地図を選び直してください。」。
  自動・手動の再試行に入れない。地図を選び直す＝入力の変更でエラーが解除される）、それ以外の404（`code` 無しを含む）はピンが無いと読む。
  backend は全エンドポイントの404に `code` を付けるが、mobile が区別に使うのは PATCH の404だけ（写真の追加・他の画面の404の扱いは変えない）。
- レビュー指摘の修正（SS-175）:
  - 地図一覧の取得失敗時は、権限ロック中でも「再読み込み」を押せる（`SanpoMapSelector` の `retryDisabled`。登録画面は従来どおり `disabled` に従う）。
    失敗中は role が不明で editor 扱いのため権限判定が不確かで、再読み込みで回復しうるので、案内文は閲覧のみとは断定せず「再読み込みしてください」にとどめる。
  - `sanpo_map_not_found` で一覧から消えた地図が下書きに残らないよう、`ready` の一覧に下書きの地図が無ければ下書きを基準値へ戻す
    （`resolveDraftSanpoMapReset`）。エラー行は消さないので「地図を選び直してください」の案内は残る。
  - **「移動したとき」の判定**: `usePinEditSave` が編集画面の寿命の間 PATCH の成功を記録し（`PinEditUpdateRecord`）、成功時に最後の PATCH 応答を `onSaved` へ渡す。
    トーストは「編集を開いた時点の地図」と最後の応答の地図を比べる（A → B に部分保存した後の再保存は B、B → A に戻せば移動なし）。
    地図一覧を取り直すかは別基準で、`sanpo_map_id` を載せた PATCH が1回でも成功していれば取り直す（A → B → A でも移動先の `mark_used()` で並びが変わるため）。
    どちらも `lib/pinEditSanpoMap.ts` の純粋関数で、連鎖は Vitest で固定している。
- E2E は `.maestro/pin-move-sanpo-map.yaml` を足した（D9 の範囲の拡張。地図 A のピンを B へ移し、詳細の地図名と両方の地図詳細の一覧を確かめる）。
- 既知の限界: 同じ保存で「移動」と「他人の写真の削除」をすると、写真の削除は移動先の role で判定される（backend）。mobile の出し分けは移動元の role で行うので、
  移動先で editor のとき 403 になりうる（招待 BK-7 まで実データでは起きない。安全性は backend の 403）。
- 既知の限界（backend 由来。決定33）: 別の端末がそのピンを移動している最中（commit 待ち）に、この画面から同じピンを保存すると、
  移動先のメンバーであっても 404 `pin_not_found` になりうる。mobile は「このピンは削除されています」と「戻る」を出し、詳細を取り直す
  （取り直した詳細は移動先の地図で表示されるので、ピンが消えたわけではないと分かる）。2台の端末で同じピンを同時に操作しない限り起きないので、専用の扱いは作らない。
  mobile 自身の保存は PATCH の応答を待ってから写真の段に進むので、自分の移動とは重ならない。
- リリース順は backend → mobile（古い backend に `sanpo_map_id` を送ると `extra="forbid"` で 422。フィーチャーフラグでは包まない）。
