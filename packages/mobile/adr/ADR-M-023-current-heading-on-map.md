# ADR-M-023: 地図上に現在地の向き（端末の方位）を扇形で表示する

## 日付

2026-10-14

## ステータス

採用（SS-169）。[ADR-M-006](./ADR-M-006-location-service-real-mock.md)（`LocationService` に `watchHeading` を追加）に追補を入れている。

## コンテキスト

散歩中やピンを探すとき、地図上の現在地は分かっても、自分がどちらを向いているかが分からない。
地図と実際の道を見比べて、進む方向を決めにくい。課題（SS-169）は「地図上に、自分が向いている向きを表示する」。

前提と制約は次のとおり。

- 現在地は `showsUserLocation`（OS の青い点）ではなく、自前のマーカー（`MapPin category="current"`）で描いている。
  `EXPO_PUBLIC_LOCATION_MODE=mock` のとき OS の点と mock の点が2つ出るため（`WalkRouteMapView` の JSDoc）。
  自前で描いているのは、散歩中の地図（`WalkRouteMapView`）とピンの地図（`PinMapCanvas`。ピンタブと位置調整の全画面）。
- 地図の `provider` は指定していない（Android = Google Maps、iOS = Apple Maps）。
- 現在地ピンは「丸い頭 + 尾」の形で、尾の先が座標を指す（ADR-M-019）。ピンの頭は座標の真上にある。
- ピンの地図は、タップ・長押しで地点を選ぶ（ADR-M-011）。現在地のまわりもその対象になる。
- 向きは `expo-location`（既存の依存）の `watchHeadingAsync` で取れる。新しいネイティブ依存は要らない。

## 決定

1. **向きは `LocationService.watchHeading(listener)` で購読する**（ADR-M-006 追補）。`expo-location` の import は
   `location.real.ts` に閉じたまま。値は北を 0 とした時計回りの度数 [0, 360)。真北（`trueHeading`）を優先し、
   取れない（-1）ときは磁北（`magHeading`）を使う。
2. **ネイティブの購読は1本にまとめ、リスナーへ配る**（`services/location/headingMultiplexer.ts`）。
   Android の expo-location は方位の watch をプロセスで1本しか持てない（`watchDeviceHeading` が直前の watchId を上書きする）。
   地図はタブの裏でもマウントされたままなので、画面ごとに購読すると後から購読した側しか通知を受けない。
   最初の購読で始め、最後の `remove()` で止める。後から加わったリスナーには直近の方位をすぐ渡す。
3. **mock は固定の方位（北東 45°。`MOCK_TRACK` の進行方向）を1回だけ通知する**。E2E で揺れないようにするため。
4. **表示は、現在地を頂点に向いている方向へ開いた半透明の扇形を、地図上の図形（`Polygon`）で描く**
   （`components/ui/heading-beam/HeadingBeam.tsx`）。開きは 70°、色は `theme.map.route` を半透明にする。
   - 扇形は距離（m）で描く図形なので、画面上でおおよそ 64px に見えるよう、地図の高さ（px）と表示範囲の緯度方向の幅から
     半径を換算し直す（`useHeadingBeamRadius`）。ズームの確定（`onRegionChangeComplete`）で更新するので、ピンチの最中は地図と一緒に拡大縮小する。
   - Google Maps では図形は常にマーカーより下に描かれるので、現在地ピンは扇形の上に出る。散歩中の地図では `zIndex` 0 でルート線・軌跡より下に敷く。
   - 扇形は向きが取れない・フォーカスが無い間は描かない（増減する）ので、`MapView` の子の**末尾**（`mapLayers` の後ろ）に置く
     （[ADR-M-012](./ADR-M-012-pin-map-display-and-detail.md) D16）。重なり順は子の並びではなく `zIndex` で決める。
5. **方位は 5° 刻みに丸め、扇形のコンポーネント（`components/location/CurrentHeadingBeam.tsx`）に購読を閉じる**。
   向きが変わっても地図全体（`MapView` と他のマーカー）を再描画しない。
6. **画面にフォーカスがあり、アプリが前面にいて、現在地を描けている間だけ購読する**（`hooks/useDeviceHeading.ts`）。
   見えていない地図のためにセンサーを回さない。権限はリクエストしない（現在地を描けている = 権限がある前提）。
   方位が取れない（センサーが無い・開始に失敗した）ときは扇形を出さず、従来どおりの表示のままにする（診断ログだけ残す）。
7. **対象は、自前の現在地マーカーを持つ `WalkRouteMapView` と `PinMapCanvas`**。散歩開始画面の `SpotMapView` は
   `showsUserLocation`（OS の点）を使っているので対象外。

## 検討した選択肢

### 選択肢1: `Polygon` で扇形を描く（採用）

- **概要**: 現在地と方位から扇形の頂点列を計算し、地図上の図形として描く。
- **メリット**: 地図を回転・傾けても、地図に対する向きのまま両 OS で描ける。`onPress` を渡さなければタップを奪わない
  （Android の図形は既定で clickable でない。iOS は `AIRMapManager.handleMapTap` が図形のタップ判定の後に必ず地図の `onPress` も呼ぶ。
  新アーキテクチャの iOS は `onPress` を渡さなくても図形側のハンドラが常に入るので、「`onPress` が無いから素通しする」のではない点に注意。
  将来 `onPress` を渡すと、iOS では図形と地図の両方のタップが発火する）。
  ビットマップの再描画が無い。
- **デメリット**: 距離で描くので、画面上の大きさを保つには半径をズームに合わせて換算し直す必要がある。
  iOS の Apple Maps では図形を更新するたびに overlay が一番上に付け直されるので、ルート線・軌跡の上に来ることがある（半透明なので線は透けて見える）。

### 選択肢2: 扇形を別の `Marker` で描き、`rotation` で回す

- **概要**: 中心を基準点にした扇形の画像をマーカーにし、`flat` + `rotation` で方位に合わせて回す。
- **メリット**: 画面上の大きさが一定。Android では地図に対する角度で回せる。
- **デメリット**: `rotation` / `flat` は iOS の Apple Maps で効かない（型の注釈 `@platform iOS: Google Maps only`）。
  iOS は子 View を回すしかなく、地図の回転（カメラの向き）を `getCamera()` で取って差し引く必要がある。
  さらに Android では `Marker` の真上のタップが `MapView` に届かない（#1132）ので、半径 64px の扇形が現在地まわりの地点選択を塞ぐ。

### 選択肢3: 現在地ピン（またはピンの中の `navigation` アイコン）を回す

- **概要**: 新しい図形を足さず、既存のマーカーで向きを表す。
- **メリット**: 描くものが増えない。
- **デメリット**: ピンは尾の先で座標を指す形なので、ピンごと回すと指す地点がずれる。アイコンだけを回すには、
  `tracksViewChanges={false}` のマーカーを向きが変わるたびに作り直す（Android でビットマップを作り直す）必要があり、
  iOS では選択肢2と同じく地図の回転と合わない。

### 選択肢4: `showsUserLocation`（OS の現在地表示）に切り替える

- **概要**: OS の地図 SDK の現在地表示（iOS は向きの扇形を出せる）に任せる。
- **メリット**: 実装がほぼ要らない。
- **デメリット**: mock モードで点が2つ出る問題（上記）が戻る。Android の Google Maps の現在地表示は向きを扇形で出さない。

## 決定理由

- 両 OS で同じ見た目・同じ正しさ（地図の回転に追随）で描けて、既存のタップ・長押しの操作を壊さないのは選択肢1だけだった。
  選択肢2は iOS の補正とタップの問題、選択肢3はピンの形との不整合、選択肢4は mock の問題が残る。
- 画面上の大きさのずれ（ピンチ中）は、ズームの確定で戻るので許容した。

## 影響

### ポジティブな影響

- 散歩中・ピンを探すときに、自分の向きが地図上で分かる。
- 新しいネイティブ依存が無く、development build の作り直しが要らない。

### ネガティブな影響・トレードオフ

- 地図を表示している間、方位センサー（加速度・磁気）を動かす分の電池を使う。前面・フォーカス中だけに限っている。
- iOS の Apple Maps では、扇形がルート線・軌跡の上に重なることがある（半透明なので線は見える）。
- 端末の方位センサーの精度（較正の状態）は表示に反映していない。較正が悪いと向きがずれる。
- iOS は実機で未確認（SS-169 は Android エミュレータで確認した）。

### 移行・対応が必要な事項

- 端末の方位を新たに取得するので、データ取扱い台帳（3.1）とプライバシーポリシー 1-1 に「向きは端末の中だけで使い、送信・保存しない」を足した（SS-169）。
  App Privacy の申告は変えない（端末内だけで、収集にあたらない）。
- iOS 実機で、向き・地図の回転への追随・扇形の重なりを確認する。
- 散歩開始画面（`SpotMapView`）にも向きを出すなら、現在地を自前マーカーに揃えるかを含めて別の課題で決める。
