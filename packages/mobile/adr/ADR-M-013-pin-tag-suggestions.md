# ADR-M-013: ピンのタグ入力の候補（地図単位の既存タグ・端末での絞り込み・既存表記への統一）

## 日付

2026-09-29

## ステータス

採用（SS-136）。

## コンテキスト

ピン登録画面のタグ入力（`PinTagEditor`）は自由入力と「追加」ボタンだけで、表記ゆれ
（`カフェ` / `cafe` / `Cafe`）が起きやすかった。ピンを探すときの主な手がかりであるタグは
`GET /pins?tags=` で正規化後の完全一致で引くため、ゆれがあると検索に引っかからない。

そこで、保存先の地図で既に使われているタグを候補として出す入力にする。候補の元データには
backend の新しい API `GET /sanpo-maps/{sanpo_map_id}/tags` を使う（API 契約・代表表記・並び順は
ルート ADR-009 の SS-136 追補 決定30 が正本。本 ADR には重複して書かない）。

ピン編集画面（SS-119）は mobile にまだ無く、`PinTagEditor` を使っているのは登録画面だけ。

## 決定

本 ADR は mobile 固有の判断（端末での絞り込み・表記統一・見せ方）を記録する。

- **D1: 候補は保存先の地図単位で取る。** 既定地図の id は登録画面が既に取得している
  `GET /sanpo-maps` から決める（`resolveTagSuggestionSanpoMapId`）。選び直した地図が一覧から
  消えたときは既定地図に戻す。既定地図がまだ無い（初回登録）ときは取らない（ピンが無いので
  候補も無い）。地図を選び直すと取り直し、取得中は空にする（前の地図の語彙を混ぜない。
  `keepPreviousData` は使わない）。
- **D2: 取得は1回で上位100件をまとめて取り、絞り込みは端末で行う。** 1文字ごとの通信・
  デバウンスが要らず反応が速い。代償として101件目以降のまれなタグは候補に出ない（自由入力は
  できる）。
- **D3: 照合は `tagKey`（正規化 + 小文字化）同士の部分一致で、前方一致を先に並べる。** 日本語は
  「古民家カフェ」のように後ろに付く語が多く、前方一致だけだと取りこぼす。ひらがな/カタカナ・
  全角/半角の同一視はしない（backend の `label_key` が同一視しておらず、揃えないと
  「候補では同じに見えるのに別タグとして保存される」ため）。並び順（よく使う順）は backend の
  ものをそのまま使い、mobile では並べ替えない。
- **D4: 入力が既存タグとキーで一致したら、既存の表記に揃えて追加する。** タグマスタが無い
  （ピン単位の行）ため、端末で揃えないと `Cafe` / `cafe` が増え続ける。照合には画面に出ている
  6件ではなく取得済みの全候補を使う。
- **D5: 候補は入力欄の下のチップで出す（ドロップダウンにしない）。** `ScrollView` +
  `KeyboardAvoidingView` の中で浮いたリストは重なり順・キーボードとの位置・読み上げ順が難しい。
  既存の `Tag` の押しやすさと a11y をそのまま使える。空入力時は「よく使うタグ」、入力中は
  「候補」の見出しで最大6件。付与済みのタグは出さない。
- **D6: 上限（10個）に達したら入力欄を無効にし、候補を出さない。** 押しても必ず失敗する操作を
  出さない。helper で「削除すると追加できる」と案内する。
- **D7: 候補の取得に失敗してもエラーを UI に出さない。** 補助機能なので、自由入力での登録を
  妨げない。取得前・失敗時は候補が無いので、表記は既存タグに揃わない（D4 は候補が取れているときだけ効く）。backend 未デプロイの環境の 404 も同じ扱いになり、デプロイ順を問わなくなる。
- **D8: queryKey は `["pins","tag-suggestions",sanpoMapId]`。** `usePinSave` の
  `invalidateQueries(["pins"])` に乗せ、保存後に取り直す（SS-119 の invalidate にも乗る）。
- **D9: 送信キー（Enter / 完了）でも追加できる。** 文字があれば追加してキーボードは開いたまま
  （`submitBehavior="submit"`）にし、続けて入力できる。次の場合だけ `blurAndSubmit` に切り替える。
  (1) 入力が空: 追加せずキーボードを閉じるだけでエラーを出さない。(2) この追加で上限（10個）に
  達する: 直後に入力欄が `editable=false` になり、OS によってはキーボードだけ残るのを避ける。
  判定は `lib/pinTagSuggestions.ts` の純粋関数（`resolveTagSubmitBehavior`）。候補チップのタップ
  または追加ボタンで上限に達した場合は UI 側で `Keyboard.dismiss()` する（判定は同じく
  `reachesTagLimitAfterAdd`。PR #110 レビューで追加ボタンの経路を追加）。候補から追加したときは
  `AccessibilityInfo.announceForAccessibility` で追加を読み上げる（タップしたチップが消えるため）。
  追加ボタンは残す（送信キーに気づかない人・スクリーンリーダー利用者の導線）。
- **D10: 入力が変わったら前回のタグ追加エラーを消す。** 打ち直している間に
  「同じタグがすでにあります」が残らないようにする。
- **D11: 配置は `features/pin/`（`PinTagEditor` + 新規 `PinTagSuggestions`）。** `components/ui`
  には上げない（使うのはピン機能だけ）。`Input` プリミティブには送信キー関連の optional props
  だけを足す。フィーチャーフラグは新設しない（登録画面ごと `pin_registration` で守られている）。

## 検討した選択肢

### 選択肢1: ユーザー単位（自分が作ったタグ全部）の候補

- **メリット**: 地図に依存せず、既定地図が未作成でも候補が出る。
- **デメリット**: ピンは1つの地図に属し、地図ごとに語彙が違う（家族の地図・仕事の地図）。別の
  地図のタグが混ざり候補の質が落ちる。不採用（D1）。

### 選択肢2: 1文字ごとに backend へ絞り込みを問い合わせる（`q`）

- **メリット**: 101件目以降のタグも候補に出せる。
- **デメリット**: 通信とデバウンスが要り、反応が遅い。MVP 規模では上位100件で足りる。不採用（D2）。

### 選択肢3: 入力欄の下に浮かぶドロップダウン

- **メリット**: 一般的なオートコンプリートの見た目。
- **デメリット**: スクロール・キーボード回避との重なり順、読み上げ順の扱いが難しい。不採用（D5）。

## 決定理由

- 反応の速さと実装の単純さ（通信1回・端末での配列走査）を、まれなタグを候補に出せない
  こととの引き換えに採った。自由入力が残るので機能は欠けない。
- 表記の収束は backend の `label_key` と同じ規則に揃えて行い、端末と backend で「同じタグ」の
  判定がずれないことを優先した。
- 候補は補助機能と位置づけ、失敗時に登録を妨げない形にした。

## 影響

### ポジティブな影響

- タグの表記ゆれが減り、`GET /pins?tags=` で引っかかりやすくなる。
- `PinTagEditor` は登録固有の状態を持たない props にしたので、SS-119（編集画面）がそのまま使える。
- 同じ API は検索タブ（SS-120）のタグ候補にも使える。（`TagSuggestion.pinCount` は現状未使用で、その用途を想定して保持している。）

### ネガティブな影響・トレードオフ

- 101件目以降のタグは候補に出ない（自由入力はできる）。
- 既定地図が未作成の初回登録では候補が出ない。
- かな・全半角の違いは別タグのまま（候補にも出ない）。
- 候補の取得前・失敗時は入力が既存タグの表記に揃わないので、表記ゆれが残りうる。
- 保存でピンが作られた後（写真の送信待ちなど）にタグを変えても、`POST /pins` の冪等な再送は
  内容を無視するため反映されない。既存の制約で本 ADR の範囲外。

### 移行・対応が必要な事項

- なし。
