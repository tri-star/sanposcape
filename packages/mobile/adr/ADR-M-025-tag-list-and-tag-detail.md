# ADR-M-025: タグ一覧とタグ詳細（全地図のピンを端末で集計する）

## 日付

2026-11-07（SS-245）、2026-11-14 注記（SS-271: フラグ pin_registration・map_pin_visibility の削除）

## ステータス

採用（SS-245）。フラグなし（ピンの機能と同じ `pin_registration` のルートガードの内側）。（**SS-271 追補**: フラグ `pin_registration` は削除し、常に ON の挙動になった。ADR-008 SS-271 追補 D45）

## コンテキスト

タグを起点にピンを探せるようにするため、ピンタブの「地図一覧」の横に「タグ一覧」ボタンを置き、
タグ一覧（`/tags`）と、そのタグが付いたピンの一覧（タグ詳細。`/tags/detail?label=`）を足す。ピン詳細のタグからもタグ詳細へ移れるようにする。

決めることは次のとおり。

- **タグの範囲**: 地図ごとか、自分がメンバーの全地図をまたいだ全体か。全体にするなら、一覧の行でどの地図のタグかをどう見分けるか。
- **データの取り方**: 今の backend にあるのは、地図ごとのタグの集計 `GET /sanpo-maps/{id}/tags`（ADR-M-013。ピン数の多い順の上位 200 件のランキングで、続きは取れない）と、
  地図ごとのピン一覧 `GET /pins?sanpo_map_id=`（`tags` で絞り込める。地図詳細は全ページを 1000 件まで取る。ADR-M-014 D2）だけ。全地図をまたぐ API は無い。
- **並び順**、ピンのタップ先、アーカイブ済みのピン・自分が非表示にした地図（SS-266。ADR-M-021）のピンを含めるか。

## 決定

- **D1: タグの範囲は、自分がメンバーの全地図。** ピンタブが全地図のピンを1枚に描くので、そこから入る画面の範囲を揃える。
  同じタグは正規化キー（`tagKey`。backend の `tag_key` と同じ規則。ADR-M-013 D4）で1つにまとめる。
  表記は、同じキーのタグのうち、いちばん新しいピンに付いているものを出す。
  一覧の行には、ピン数と、そのタグが使われている地図（アイコン + 名前。先頭3件と「ほかN件」）を出して見分ける。
- **D2: 新しい API は作らない。地図詳細と同じ「地図ごとのピンの全件取得」を全地図ぶん取り、端末で集計する。**
  `fetchAllPinsInSanpoMap`（1地図あたり 200 件 × 5 ページ = 1000 件まで）を、地図詳細と同じ queryKey（`sanpoMapPinsQueryKey`）で
  `useQueries` に並べる（`hooks/tag/useAllSanpoMapPins.ts`）。タグの一覧・絞り込み・該当ピンの抽出は、すべて `lib/tag/` の純粋関数で行う。
  - 地図詳細とキャッシュを共有する。ピンの保存・編集・削除の `["pins"]` の invalidate で、タグ画面もそのまま新しくなる。
  - タグ一覧の件数と、タグ詳細の件数が必ず一致する（同じデータから数えるため）。
  - 打ち切られた地図（1000 件超え）が1つでもあれば、「ピンが多い地図は、新しい順に1000件までのピンから集めています」と出す。
  - 404 の地図（取得の間に削除された・外された）は飛ばす。地図一覧の取り直しで消える。
- **D3: タグ詳細は、開くたびに全地図のピンを取り直す**（`refetchOnMount: "always"`。タグ一覧は鮮度 60 秒のまま）。
  ピン詳細は開くたびに取るので、ほかのメンバーなどが直前に足したピンの詳細からタグを押すと、地図ごとのピンのキャッシュにそのピンが無く、
  「このタグが付いたピンはありません」と食い違う（SS-245 のエミュレータでの確認で見つけた）。
  取り直しの間に該当が0件なら、空表示ではなく読み込み中を出す（引っ張って更新の間は空表示のまま。読み込み表示に替えると、引っ張った ScrollView ごと外れるため）。
- **D4: 並び順。** タグ一覧はピン数の多い順 → 正規化キーの昇順（backend の `GET /sanpo-maps/{id}/tags` の第1・第3キーと同じ。最後に使われた日時は端末では持たないので使わない）。
  タグ詳細は作成日時の新しい順（地図詳細のピン一覧と同じ）。行は地図詳細の `SanpoMapPinListItem` に地図（アイコン + 名前）を出す任意の props を足して使い、タップでピン詳細へ。
- **D5: アーカイブ済みのピンと、自分が非表示にした地図（`pinsVisible: false`。SS-266）のピンも含める。**
  地図詳細のピン一覧と同じ扱い。タグ画面は地図に描く画面ではなく一覧の画面なので、ADR-M-021 の「非表示の地図のピンは取りに行かない」（地図に描く経路の決定）の対象外とする。
  フラグ `map_pin_visibility` にも依存しない。（**SS-271 追補**: フラグ `map_pin_visibility` は削除し、常に ON の挙動になった。ADR-008 SS-271 追補 D45）
- **D6: ルートと絞り込み。** タグ詳細は、タグの表記に `/` などが入りうるので、動的セグメント（`[label].tsx`）にせずクエリ `label` で受け、
  `parseTagLabelParam` で正規化・検証する（空・記号だけ・20 文字超えは「タグが見つかりませんでした」を出し、通信しない）。
  タグ一覧の絞り込みは、地図一覧と同じ `NameSearchField` と照合規則（`sanpoMapSearch.ts` の部分一致）で、端末で行う（ADR-M-014 D1）。
  ゲストは開けるが通信せず、サインイン案内を出す（ADR-M-014 D6 と同じ）。
- **D7: タグ詳細のピン名での絞り込みは入れない**（受け入れ条件に無い。必要になったら地図詳細と同じ `NameSearchField` で足せる）。

## 検討した選択肢

### 選択肢1: 地図ごとのピンの全件取得を全地図ぶん取り、端末で集計する（採用）

- **概要**: D2。
- **メリット**: backend の変更が無く、配布済みアプリとの互換の手当て（prod へのデプロイの後に配布）が要らない。
  地図詳細とキャッシュ・invalidate を共有でき、タグ一覧と詳細の件数が一致する。全件（1000 件まで）からタグを数えられる。
- **デメリット**: タグ一覧・詳細を開くと全地図のピンを最大 5 ページずつ取る。タグ詳細は開くたびに取る（D3）。地図・ピンが多い利用者では通信が増える。

### 選択肢2: 地図ごとの `GET /sanpo-maps/{id}/tags` と、`GET /pins?tags=` を地図ごとに呼ぶ

- **概要**: タグの一覧は tags API を全地図ぶん呼んで端末でまとめ、詳細は `tags` で絞った `GET /pins` を全地図ぶん呼ぶ。
- **メリット**: 一覧の通信が軽い。
- **デメリット**: tags API は上位 200 件のランキングで、全件が出ない。一覧と詳細で別のキャッシュになり、保存・編集・削除の後の invalidate を別に手当てする必要がある。
  一覧の件数と詳細の件数が食い違いうる。

### 選択肢3: backend に全地図をまたいだタグの集計 API・タグでのピン一覧 API を足す

- **概要**: `GET /tags`（自分がメンバーの全地図）と、地図をまたいだ `GET /pins?tags=` を新設する。
- **メリット**: 通信が少なく、地図・ピンが増えても重くならない。
- **デメリット**: 配布済みアプリとの互換（ADR-008。backend の prod へのデプロイの後に mobile を配布）の手間がかかる。今のデータ量では見合わない。

## 決定理由

- 今の利用者の地図・ピンの数なら、全件取得の通信量は問題にならない。地図詳細で既に同じ取得をしているので、新しい負荷の型を増やさない。
- タグ一覧と詳細が同じデータを数えるので、件数が食い違わない。キャッシュの手当ても既存のものがそのまま効く。
- backend を変えないので、mobile だけで配布でき、互換の手当てが要らない。

## 影響

### ポジティブな影響

- タグを起点に、地図をまたいでピンを探せる。ピン詳細のタグから、同じタグのピンへ移れる。
- backend・API・DB・フラグに触れない。

### ネガティブな影響・トレードオフ

- タグ一覧・詳細を開くと全地図のピンを取る。タグ詳細は開くたびに取る（D3）。
- 地図一覧（`GET /sanpo-maps`）の鮮度は 5 分なので、直前に招待された地図のピンのタグは、地図一覧が古い間は D3 でも出ない。
- 0件の空表示のときに裏で取り直しが走る（写真の失効・ほかの画面での保存による invalidate）と、空 → 読み込み → 空と入れ替わる。壊れはしないので許容した。
- タグ一覧・タグ詳細・地図一覧・地図詳細で、画面の骨組み（状態表示・引っ張って更新）が重複している（月次の code-health-review の候補）。

### 移行・対応が必要な事項

- 地図・ピンが大きく増えて、タグ画面の初回の取得が重くなったら、選択肢3（backend の集計 API）を検討する。
