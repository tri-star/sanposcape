# ADR-M-026: ピンタブの検索（住所・駅・施設名で探して地図に打つ）

## 日付

2026-11-14（SS-267）

## ステータス

採用（SS-267）。フラグなし（iOS の地図の切り替えと同じストアのビルドで届けるため。下の D6）。

## コンテキスト

ピンタブの上部には「地図を長押しすると、その場所にピンを登録できます…」というヒントを出していた（ADR-M-011 の SS-146 追補）。
課題は、ここを入力欄にして、入力した文字に合う場所を地図に出すこと。例として次の3つが挙がっていた。

- 「コンビニ」のような種類: 現在地付近の該当する場所に「検索用のピン」を打ち、タップで概要（店名・住所など）を出す。ピン一式をクリアできる。
  まず画面内で探し、無ければ範囲を広げて探す（1段階で止める）のでもよい。
- 「○○区○○1-2-3」のような住所: 合う場所にピンを打ち、そこまで地図を動かす。
- 「○○駅」: 最も近い該当する駅（広い範囲なら複数ありうる）にピンを打ち、画面の外なら動かす。

検索元は Google Places の Text Search (New) を backend 経由で使う（[ADR-001](../../../docs/adr/ADR-001-map-poi-google-maps-platform.md) の SS-267 追補。
API は `POST /explore/places/text-search`）。Google Maps Platform の規約 3.2.3(e) が Places の内容を Google 以外の地図に出すことを禁じているので、
iOS の地図も Google Maps にした（[ADR-M-007](./ADR-M-007-expo-config-and-maps-key-injection.md) の SS-267 追補）。ここでは mobile の画面の決定を書く。

## 決定

- **D1: 検索欄は情報カードの1行目（ヒントの行）を置き換える。** サインインしていて、地図が Google Maps のとき（`currentMapRenderer() === "google"`）だけ出す。
  それ以外（サインインしていない・iOS でキーを入れていないビルド）は従来のヒントを出す（testID `pin-tab-hint` は E2E が見るので変えない）。
  長押しの登録の説明は、地図の `accessibilityHint` に残す。プレースホルダは「住所・駅・施設名で検索」。
  送信はキーボードの検索キーだけで、ボタンは足さない（地図の上の面積を増やさない）。
- **D2: 1回の送信で backend を1回呼ぶ。範囲の広げ方は backend が持つ。** 送るのは検索語（前後の空白を除き 100 code point まで）と、
  今の表示範囲（ピンの取得 `GET /pins` と同じく外側へ小数4桁に丸める）。backend が表示範囲の中だけを探し、0件なら範囲の中心から半径 50km を
  優先して1回だけ広げ、`scope`（`visible_area` / `expanded`）で返す。
- **D3: 地図を動かすのは、表示範囲の外まで広げて見つけたとき（`expanded`）だけ。** 先頭の結果（Google の関連度の順。並べ替えない）の付近
  （`regionAroundPoint`）へ動かす。表示範囲の中で見つかったときは、利用者が見ている範囲を変えない。動かすのはクラスタのタップと同じ `regionRequest`。
- **D4: 結果は「検索結果のピン」として打つ。** 虫眼鏡のアイコンの `MapPin`（`sky`。選んだものは `goal` で大きく）で、登録済みピン（地図のアイコン）と見分ける。
  重なりは登録済みピンより上。タップで地図の下に概要のカード（名前・住所・閉じる）を出す。「ここにピンを登録」は置かない（D7）。
  案内は検索欄の下に1行: 0件（「「◯◯」に当てはまる場所は見つかりませんでした」）、広げて見つけた（「表示している範囲には無かったので、付近から探しました」）、
  失敗（429・503・通信・その他）。
- **D5: クリアは検索欄の ×。** 入力・結果のピン・案内をまとめて消す。入力を消した後でもピンが残っていれば × を出す。
- **D6: 結果はメモリだけに持つ。** TanStack Query の `useMutation` の状態に持ち、クエリのキャッシュ・端末のストレージには置かない
  （Places の内容を保存しない。古い要求の応答は、最後の `mutate` だけを映す v5 の挙動で捨てる）。ピンタブは常駐するので画面を離れても残るが、
  サインアウト（検索欄が消える）で捨てる。
- **D7: 検索結果からピンを登録する導線は作らない。** Places の座標をピンの位置として DB に無期限に残すことになり、規約（Places の内容の保存の制限）に
  触れうる。ピンの登録は従来どおり長押しで、利用者が選んだ位置を保存する。
- **D8: コード上の名前は `locationSearch`。** walk の探索に `placeSearch*`（`/explore/places`）があるので分ける。置き場所は
  `features/pin/{components,hooks,lib}/location-search/` と `features/pin/api/locationSearchApi.ts`。

## 検討した選択肢

### 範囲の広げ方を mobile が持つ（画面内で探して0件なら mobile がもう一度送る）

- **メリット**: backend の API が単純になる。
- **デメリット**: 往復が2回になり、レート制限（1ユーザー 30 回/分）を2回ぶん使う。「1段階で止める」の規則が mobile と backend に分かれる。採らない。

### 検索のたびに結果に合わせて地図を動かす（全件が入るように寄せる）

- **メリット**: 結果が必ず画面に入る。
- **デメリット**: 表示範囲の中の検索で、見ている範囲が勝手に変わる。広げた検索では遠くの結果が混ざると日本全体まで縮む。
  課題の「画面外の場合はスクロールして表示」に合わせ、広げたときだけ先頭へ動かす。

### 結果をリストでも出す

- **メリット**: 地図で重なった結果も選べる。
- **デメリット**: 地図の上の面積を取る。最大 20 件で、課題はピンとタップの概要を求めている。まずピンだけにした。

### 検索結果から「ここにピンを登録」

- D7 の理由で採らない。必要になったら、Places の座標を保存してよいか（規約の確認）と合わせて決め直す。

## 決定理由

- 課題の3つの例（種類・住所・駅）は Text Search の1回で扱え、範囲の広げ方を backend に寄せれば mobile は送るだけになる。
- 地図を勝手に動かさない（表示範囲の中の検索）ことと、見つけた場所まで連れていく（広げた検索）ことを、`scope` だけで切り替えられる。

## 影響

### ポジティブな影響

- 住所・駅・施設名から、その場所の付近の地図にすぐ移れる。長押しでピンを登録する起点にもなる。

### ネガティブな影響・トレードオフ

- ヒントの行が消えるので、長押しで登録できることは画面の文字では伝わらなくなる（スクリーンリーダーには `accessibilityHint` で伝わる）。
- 検索語（住所を含みうる）と表示範囲が backend を通って Google へ送られる（DB・ログには残さない。データ取扱い台帳 3.1）。
- iOS でキーを入れていないビルド（ローカルの dev build など）では検索欄が出ない。

### 移行・対応が必要な事項

- 検索結果のピンとカードは E2E で見ない（Google Maps の描画面で testID が安定して取れない。ADR-M-012 D14）。E2E は案内とクリアだけを見る（`.maestro/pin-tab-search.yaml`）。
- iOS の実機での確認（検索欄・ピン・カード・地図を動かす）。
